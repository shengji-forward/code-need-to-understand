## Key Concepts

- **Data processing** transforms raw input through a sequence of discrete operations to produce meaningful output, following the pattern: source, transform, aggregate.
- **Sequential data streams** process elements one at a time rather than loading an entire dataset into memory, enabling work with datasets too large to fit in RAM.
- **Implicit sequences** represent potentially infinite sequences by computing values on demand rather than storing them all upfront.
- **Data pipelines** compose independent, reusable stages where each stage performs a single transformation and passes its output to the next stage.
- **Declarative query systems** describe *what* data to retrieve rather than *how* to retrieve it, separating intent from implementation.
- **Distributed and parallel processing** split work across multiple workers to handle larger datasets than a single machine can process alone.

### Chapter 4: Data Processing

The first three chapters established the foundations of programming: functions (Chapter 1), data structures (Chapter 2), and interpreters (Chapter 3). This chapter shifts focus from *how* to compute to *how to process data at scale*. The central question is no longer "how do I write a function?" but "how do I transform large, evolving, or even unbounded streams of data?"

Data processing pervades modern computing. A social media feed, a web server log, a database query, and a sensor network all produce sequences of data that must be filtered, transformed, combined, and summarized. The techniques in this chapter -- implicit sequences, declarative querying, logic programming, and distributed computation -- provide the conceptual tools for reasoning about these tasks.

### 4.1.1 The Source-Transform-Aggregate Pattern

Most data processing follows a three-stage pattern:

1. **Source**: Produce or receive raw data elements.
2. **Transform**: Apply one or more operations to each element -- filtering, mapping, enriching.
3. **Aggregate**: Combine the transformed elements into a final result -- a sum, a collection, a grouped summary.

Consider processing a log of website visits:

```javascript
const visits = [
  { page: "/", time: 1, user: "alice" },
  { page: "/about", time: 2, user: "bob" },
  { page: "/contact", time: 3, user: "alice" },
  { page: "/", time: 4, user: "carol" },
  { page: "/about", time: 5, user: "alice" },
];
```

An imperative approach processes this data with loops and accumulators:

```javascript
function countHomepageVisitsImperative(visits) {
  let count = 0;
  for (const v of visits) {
    if (v.page === "/") {
      count += 1;
    }
  }
  return count;
}

countHomepageVisitsImperative(visits);  // 2
```

A pipeline approach composes reusable stages:

```javascript
function pipe(...fns) {
  return (input) => fns.reduce((val, fn) => fn(val), input);
}

function mapStage(fn) {
  return (data) => data.map(fn);
}

function filterStage(predicate) {
  return (data) => data.filter(predicate);
}

function reduceStage(reducer, initial) {
  return (data) => data.reduce(reducer, initial);
}

function runPipeline(input, stages) {
  return pipe(...stages)(input);
}

const countHomepageVisits = runPipeline(
  visits,
  [
    filterStage((v) => v.page === "/"),
    reduceStage((acc, _) => acc + 1, 0),
  ]
);

countHomepageVisits;  // 2
```

Both produce the same result. The pipeline version is more modular: each stage is an independent function that can be tested, reused, and reordered. This modularity becomes essential as data processing grows in complexity.

### 4.1.2 Sequential Data and Unbounded Streams

Not all data fits in memory. A real-time sensor produces readings continuously. A web server receives requests indefinitely. A database query may return millions of rows. Processing such data requires a different mental model: instead of loading everything into an array, we process elements **one at a time** as they arrive.

This leads to the concept of an **implicit sequence**: a sequence whose elements are computed on demand rather than stored in memory. An implicit sequence can represent:

- A finite but large dataset (a file too big for RAM).
- A potentially infinite sequence (the natural numbers, real-time events).
- A sequence whose later elements depend on earlier computations (the Fibonacci sequence).

JavaScript provides several mechanisms for implicit sequences:

| Mechanism | Description | Example |
|-----------|-------------|---------|
| Iterator | An object with a `next()` method that produces values one at a time | `{ next() { return { value: 1, done: false }; } }` |
| Iterable | An object that can produce an iterator via `[Symbol.iterator]()` | Arrays, Sets, Maps, custom objects |
| Generator | A function declared with `function*` that yields values lazily | `function* naturals() { let n = 1; while (true) yield n++; }` |
| Stream | A lazy linked list where the rest is a thunk evaluated on demand | `stream(1, () => stream(2, () => ...))` |

These mechanisms share a common principle: **values are produced only when requested**. This laziness allows programs to work with sequences that are too large or infinite, as long as only a finite prefix is consumed.

### 4.1.3 Pipelines as Composable Abstractions

A pipeline is a sequence of processing stages where each stage receives input from the previous stage and passes output to the next. Pipelines appear throughout computing:

- **Unix pipes**: `cat log.txt | grep ERROR | wc -l`
- **Array method chains**: `visits.filter(...).map(...).reduce(...)`
- **Stream processing**: source.pipe(transform).pipe(sink)
- **Database queries**: `SELECT ... FROM ... WHERE ... GROUP BY ...`

The power of pipelines comes from **composition**: each stage is an independent function with a clear input/output contract. Stages can be added, removed, or reordered without modifying the others.

```javascript
function summarizeEvents(events) {
  const counts = Object.create(null);
  for (const event of events) {
    const prev = Object.hasOwn(counts, event.type) ? counts[event.type] : 0;
    counts[event.type] = prev + 1;
  }
  return counts;
}

const events = [
  { type: "click", target: "button" },
  { type: "scroll", target: "page" },
  { type: "click", target: "link" },
  { type: "click", target: "button" },
  { type: "hover", target: "image" },
];

summarizeEvents(events);
// { click: 3, scroll: 1, hover: 1 }
```

The `summarizeEvents` function is an aggregator: it consumes a stream of events and produces a summary. It does not need to know where the events came from (a DOM listener, a log file, a network socket) or how many there are (three or three million). This separation of source, transform, and aggregate is the architectural pattern that runs through this entire chapter.

## Python vs JavaScript Notes

| Topic | Python | JavaScript |
|-------|--------|------------|
| **Iterator protocol** | `__iter__()` returns self; `__next__()` raises `StopIteration` | `[Symbol.iterator]()` returns iterator; `next()` returns `{ value, done }` |
| **Generator functions** | `def gen(): yield x` | `function* gen() { yield x; }` |
| **Lazy sequences** | Built-in `range()`, generator expressions | No built-in lazy range; implement with generators or custom streams |
| **Pipeline style** | Generator chaining, `itertools` | Array method chaining, generator delegation (`yield*`) |
| **SQL in standard library** | `sqlite3` module built in | No built-in SQL; Node.js has `node:sqlite` (experimental) |
| **Parallelism** | `threading`, `multiprocessing`, `concurrent.futures` | Worker threads (`worker_threads`), Web Workers (browser) |
