## Key Concepts

- **Parallelism vs. concurrency**: Concurrency is about *interleaving* multiple tasks on a single core (the event loop in JavaScript); parallelism is about executing them *simultaneously* on multiple cores.
- **Shared mutable state** is the root cause of most parallel-programming bugs. When two threads or workers read and write the same data without coordination, the result depends on the order of execution -- a **race condition**.
- **Locks (mutex)** serialize access to a critical section so that only one task at a time can mutate shared data. A lock must always be released, even if the protected code throws.
- **Barriers** divide a parallel program into phases: all tasks must reach the barrier before any of them can proceed, ensuring that reads and writes to shared data happen in separate, non-overlapping phases.
- **Message passing** avoids shared-state bugs entirely by communicating through channels. Each task owns its own data and exchanges values via `send` / `receive`.
- **Deadlock** occurs when two or more tasks wait on each other in a cycle and none can make progress. It arises from circular waits on locks, channels, or other blocking primitives.
- JavaScript is single-threaded by design; true parallelism in Node.js requires `worker_threads` (or `SharedArrayBuffer` / `Atomics`). The examples below use **promise-based simulations** to stay deterministic and runnable in a single thread.

## Content

### 4.8.1 Parallelism in JavaScript

JavaScript executes on a **single-threaded event loop**. Code runs to completion before the next event is processed. This means that within one JavaScript realm, two functions never truly run at the same time -- they are *concurrent* (interleaved) but not *parallel*.

**Concurrency** means multiple tasks make progress by taking turns. **Parallelism** means they run at the same instant on separate CPU cores. The distinction matters because shared-state bugs only arise when operations are truly simultaneous.

Node.js provides the `worker_threads` module for true parallelism. Each worker runs in its own V8 isolate with its own memory. Workers can share `SharedArrayBuffer` memory (accessed through `Atomics` for safe reads and writes), or they can communicate through message passing via `parentPort.postMessage()`.

```javascript
// Conceptual: real worker_threads (not runnable in a single-thread example)
const { Worker, isMainThread, parentPort, workerData } = require("worker_threads");

if (isMainThread) {
  const worker = new Worker(__filename, { workerData: { start: 0, end: 100 } });
  worker.on("message", (result) => console.log("Worker result:", result));
  // Main thread continues its own work concurrently
} else {
  // Runs in a separate thread with true parallelism
  const sum = /* ...compute with workerData... */ 0;
  parentPort.postMessage(sum);
}
```

Because `worker_threads` examples are nondeterministic -- execution order depends on OS scheduling -- the rest of this section uses **promise-based simulations** that interleave operations in a controlled, deterministic way. This lets us demonstrate every concept without flaky tests.

```javascript
// Helper: simulate two "threads" interleaving their steps deterministically
async function simulateRace(steps, taskA, taskB) {
  const genA = taskA();
  const genB = taskB();
  let doneA = false;
  let doneB = false;
  const results = [];

  while (!doneA || !doneB) {
    if (!doneA) {
      const { value, done } = genA.next();
      if (done) doneA = true;
      else results.push(value);
    }
    if (!doneB) {
      const { value, done } = genB.next();
      if (done) doneB = true;
      else results.push(value);
    }
  }
  return results;
}
```

The generator-based `simulateRace` above interleaves the yields of two generator functions step-by-step, giving us a fully deterministic model of concurrent execution.

### 4.8.2 The Problem with Shared State

When two concurrent tasks read and write the same mutable variable, the final value depends on how their operations are interleaved. This is a **race condition**.

Consider a shared counter that both tasks increment:

```javascript
function* incrementTask(counter, label) {
  for (let i = 0; i < 3; i++) {
    const old = counter.value;           // read
    yield `${label} read ${old}`;
    counter.value = old + 1;             // write
    yield `${label} wrote ${old + 1}`;
  }
}

// Race condition demo
const counter = { value: 0 };
const log = simulateRace(
  6,
  () => incrementTask(counter, "A"),
  () => incrementTask(counter, "B")
);
// log includes entries like:
// "A read 0", "B read 0", "A wrote 1", "B wrote 1", ...
// Both tasks read 0, so both write 1 -- a lost update!
// Final counter.value is far less than 6.
```

The problem is that *read-then-write* is not atomic. Between a task reading `counter.value` and writing it back, the other task can read the same stale value. Each increment should add 1, but because the reads and writes overlap, some increments are lost.

The expected final value is 6 (3 increments from each task), but due to interleaving the actual value can be as low as 2. The exact result depends on the interleaving order -- making the bug intermittent and hard to reproduce.

### 4.8.3 When No Synchronization is Necessary

Not all concurrent code requires synchronization. Operations are safe when:

- **Data is immutable.** If no task mutates a value, all tasks read the same data regardless of timing. `const` declarations, frozen objects, and strings are naturally safe.
- **Computations are independent.** When each task works on its own private data with no overlap, there is nothing to coordinate.
- **Functions are pure.** Pure functions have no side effects and depend only on their arguments. Two pure-function calls can execute in any order without affecting each other's results.

```javascript
// Safe: each task computes independently, no shared mutable state
function* squareTask(nums, label) {
  for (const n of nums) {
    yield `${label}: ${n}^2 = ${n * n}`;
  }
}

const log = simulateRace(
  6,
  () => squareTask([1, 2, 3], "A"),
  () => squareTask([4, 5, 6], "B")
);
// Order of results varies, but every result is correct.
// No synchronization needed.
```

Functional programming, as discussed in the MapReduce section (4.7), naturally avoids synchronization issues because it avoids shared mutable state. Unfortunately, not all problems can be solved efficiently with pure functions -- some genuinely require shared mutable state.

### 4.8.4 Synchronized Data Structures

The simplest way to avoid race conditions is to use a data structure that handles synchronization internally. In Python, the `queue.Queue` class does this. In JavaScript we can build a **safe counter** that serializes increments:

```javascript
class SafeCounter {
  constructor() {
    this._value = 0;
    this._queue = Promise.resolve(); // serializes operations
  }

  increment() {
    this._queue = this._queue.then(() => {
      this._value++;
    });
    return this._queue;
  }

  get value() {
    return this._value;
  }
}
```

The trick is the `Promise.resolve()` chain: each `increment()` appends a `.then()` to the chain, so operations execute one at a time in order. No two increments overlap.

```javascript
const safe = new SafeCounter();

async function incrementN(n) {
  for (let i = 0; i < n; i++) {
    await safe.increment();
  }
}

// Run two concurrent increment loops
await Promise.all([incrementN(500), incrementN(500)]);
safe.value; // Always 1000, never less
```

For the deterministic simulation, we can show the same idea with generators:

```javascript
function* safeIncrementTask(counter, label) {
  for (let i = 0; i < 3; i++) {
    // The counter's increment method handles its own synchronization
    counter.increment();
    yield `${label} incremented to ${counter.value}`;
  }
}

class SimpleSafeCounter {
  constructor() { this._value = 0; }
  increment() { this._value++; }
  get value() { return this._value; }
}

const safeCounter = new SimpleSafeCounter();
const log = simulateRace(
  6,
  () => safeIncrementTask(safeCounter, "A"),
  () => safeIncrementTask(safeCounter, "B")
);
// Because each increment is atomic (single statement), the value
// is always correct -- as long as the operation truly cannot be
// interrupted between read and write.
```

A `Queue` data structure with synchronized `put` and `take` methods follows the same principle: the class internally serializes access so that no item is lost or duplicated.

### 4.8.5 Locks (Mutex)

When a synchronized data structure is not available, a **lock** (also called a **mutex** -- mutual exclusion) protects shared data. A lock can be *held* by at most one task at a time. Any other task that tries to acquire it must wait.

```javascript
class Mutex {
  constructor() {
    this._locked = false;
    this._queue = [];
  }

  acquire() {
    return new Promise((resolve) => {
      if (!this._locked) {
        this._locked = true;
        resolve();
      } else {
        this._queue.push(resolve);
      }
    });
  }

  release() {
    if (this._queue.length > 0) {
      const next = this._queue.shift();
      next(); // pass ownership to the next waiter
    } else {
      this._locked = false;
    }
  }

  // Convenience: acquire, run fn, then release (even if fn throws)
  async runExclusive(fn) {
    await this.acquire();
    try {
      return await fn();
    } finally {
      this.release();
    }
  }
}
```

The `runExclusive` method is critical: it uses `try / finally` to guarantee that the lock is **always released**, even if the protected function throws an error. Without this, a thrown exception would leave the lock permanently held, freezing any task waiting on it.

```javascript
const mutex = new Mutex();
const sharedList = [];

async function addItem(item) {
  await mutex.runExclusive(() => {
    sharedList.push(item);
  });
}

async function unsafeAddItem(item) {
  // No lock -- race condition possible if shared by multiple tasks
  sharedList.push(item);
}
```

Using the lock with our simulation:

```javascript
function* lockedIncrementTask(counter, mutex, label) {
  for (let i = 0; i < 3; i++) {
    yield `${label} acquiring lock`;
    // In simulation, we track that the task intends to acquire
    // In real async code: await mutex.runExclusive(...)
    const old = counter.value;
    yield `${label} read ${old}`;
    counter.value = old + 1;
    yield `${label} wrote ${old + 1}, releasing lock`;
  }
}
```

A lock only works if **every** task accessing the shared data acquires it first. If even one task bypasses the lock, the race condition returns. Operations that must be synchronized with each other must use the same lock. However, two independent sets of operations should use two different locks to avoid over-serialization.

### 4.8.6 Barriers

A **barrier** coordinates N tasks so that all of them must reach the barrier before any can proceed. This divides a parallel program into **phases**: code before the barrier completes in one phase, and code after it starts in the next phase.

```javascript
class Barrier {
  constructor(parties) {
    this._parties = parties;   // total number of tasks
    this._waiting = 0;         // how many are currently waiting
    this._resolve = null;      // resolves when all parties arrive
    this._generation = 0;      // increments each cycle to handle reuse
  }

  async wait() {
    const gen = this._generation;
    this._waiting++;

    if (this._waiting === this._parties) {
      // Last to arrive: release everyone
      this._waiting = 0;
      this._generation++;
      if (this._resolve) {
        this._resolve();
        this._resolve = null;
      }
      return; // proceed immediately
    }

    // Wait until the last party arrives
    return new Promise((resolve) => {
      this._resolve = resolve;
    }).then(() => {
      // Ensure we only proceed for the current generation
      if (gen !== this._generation - 1) {
        return this.wait(); // stale generation, try again
      }
    });
  }
}
```

Example: two tasks that take turns reading and writing shared counters:

```javascript
const counters = [0, 0];
const barrier = new Barrier(2);

async function count(threadNum, steps) {
  for (let i = 0; i < steps; i++) {
    // Phase 1: read (both read before either writes)
    const other = counters[1 - threadNum];
    await barrier.wait(); // wait for reads to complete

    // Phase 2: write (disjoint writes are safe in the same phase)
    counters[threadNum] = other + 1;
    await barrier.wait(); // wait for writes to complete
  }
}

async function threadedCount(steps) {
  await Promise.all([count(0, steps), count(1, steps)]);
  return counters;
}

// After running threadedCount(10), both counters are always 10.
```

The barrier ensures that reads and writes never overlap. Both tasks read in phase 1, then both write in phase 2. Because the writes are disjoint (each task writes its own index), they do not conflict within the same phase.

A real-world use of barriers is a particle simulator: in each timestep, all threads read particle positions (read phase), then all threads update their own particles' velocities and positions (write phase). The barrier between phases prevents a thread from reading stale positions while another thread is mid-update.

### 4.8.7 Message Passing

Message passing avoids shared-state bugs by eliminating shared state entirely. Each task owns its own data, and tasks communicate by sending and receiving messages through a **channel**.

In Node.js, the real API is `parentPort.postMessage()` / `worker.on("message", ...)` from the `worker_threads` module. Our deterministic `Channel` class simulates the same pattern:

```javascript
class Channel {
  constructor() {
    this._buffer = [];
    this._waiters = [];
  }

  // Send a value into the channel (non-blocking)
  send(value) {
    if (this._waiters.length > 0) {
      const resolve = this._waiters.shift();
      resolve(value);
    } else {
      this._buffer.push(value);
    }
  }

  // Receive a value from the channel (blocking / async)
  receive() {
    if (this._buffer.length > 0) {
      return Promise.resolve(this._buffer.shift());
    }
    return new Promise((resolve) => {
      this._waiters.push(resolve);
    });
  }
}
```

A producer-consumer example using the channel:

```javascript
const ch = new Channel();

async function producer() {
  for (let i = 0; i < 5; i++) {
    ch.send(i);
    console.log("sent:", i);
  }
  ch.send(null); // sentinel: signals end
}

async function consumer() {
  while (true) {
    const item = await ch.receive();
    if (item === null) return; // done
    console.log("received:", item);
  }
}

// Both run concurrently; the channel ensures no item is lost.
await Promise.all([producer(), consumer()]);
```

Message passing is the idiomatic way to coordinate `worker_threads` in Node.js. Each worker owns its data, communicates via `postMessage`, and never touches another worker's memory. This eliminates entire classes of race conditions and deadlocks -- at the cost of copying data (or using `SharedArrayBuffer` for large buffers).

```javascript
// Conceptual: real worker_threads message passing
// Main thread:
//   worker.postMessage({ type: "compute", data: largeArray });
//   worker.on("message", (result) => { ... });
//
// Worker thread:
//   parentPort.on("message", (msg) => {
//     const result = heavyComputation(msg.data);
//     parentPort.postMessage(result);
//   });
```

### 4.8.8 Synchronization Pitfalls

Synchronization mechanisms are powerful but easy to misuse. The three main pitfalls are **under-synchronization**, **over-synchronization**, and **deadlock**.

**Under-synchronization.** Synchronizing operations individually is not enough -- they must be synchronized *together*. For example, checking if an item is in a set and then adding it must happen as one atomic operation:

```javascript
// WRONG: checking and adding are separate critical sections
function alreadySeenBad(item, set, mutex) {
  let result;
  await mutex.runExclusive(() => { result = set.has(item); }); // check
  if (!result) {
    await mutex.runExclusive(() => { set.add(item); });        // add
  }
  return result;
  // Bug: another task can add the same item between the two locks!
}

// CORRECT: check and add in the same critical section
async function alreadySeen(item, set, mutex) {
  return mutex.runExclusive(() => {
    if (set.has(item)) return true;
    set.add(item);
    return false;
  });
}
```

**Over-synchronization.** Holding a lock for too long prevents other tasks from making progress, reducing parallelism. In the extreme case, a task acquires a lock at startup and never releases it, serializing the entire program.

```javascript
// Over-synchronization: everything runs sequentially
async function overSync(data, mutex) {
  await mutex.runExclusive(async () => {
    await readInput(data);    // holds lock while reading
    await process(data);      // holds lock while processing
    await writeOutput(data);  // holds lock while writing
  });
  // Better: only lock around the shared-data mutation, not I/O.
}
```

**Deadlock.** Two or more tasks wait on each other in a cycle, and none can proceed. The classic scenario is two locks acquired in opposite orders:

```javascript
const lockA = new Mutex();
const lockB = new Mutex();

// Task 1: lockA then lockB
async function task1() {
  await lockA.acquire();
  await lockB.acquire();
  // ... critical section ...
  lockB.release();
  lockA.release();
}

// Task 2: lockB then lockA (opposite order!)
async function task2() {
  await lockB.acquire();
  await lockA.acquire();
  // ... critical section ...
  lockA.release();
  lockB.release();
}

// If task1 holds lockA and waits for lockB,
// while task2 holds lockB and waits for lockA,
// both wait forever -- deadlock.
```

**Preventing deadlock.** Always acquire multiple locks in a consistent global order:

```javascript
// Enforce ordering by lock name or ID
class OrderedLocks {
  static async acquireBoth(lock1, lock2) {
    // Always acquire in a deterministic order
    const [first, second] = lock1.id < lock2.id
      ? [lock1, lock2]
      : [lock2, lock1];
    await first.acquire();
    await second.acquire();
    return [first, second];
  }
}
```

Deadlock can also occur with channels. If two tasks both try to receive before either sends, both block forever:

```javascript
const ch1 = new Channel();
const ch2 = new Channel();

// Task 1: receive from ch1, then send to ch2
async function deadlockedTask1() {
  const msg = await ch1.receive(); // blocks...
  ch2.send(msg + 1);
}

// Task 2: receive from ch2, then send to ch1
async function deadlockedTask2() {
  const msg = await ch2.receive(); // blocks...
  ch1.send(msg + 1);
}

// Neither sends first; both wait forever.
```

The fix is to align operations so that one side sends before the other receives, or to use non-blocking sends followed by receives.

### 4.8.9 Conclusion

Parallel computing is essential as hardware continues to add cores rather than increasing single-core speed. The key principles are:

| Primitive | When to Use |
|-----------|-------------|
| **Immutable data / pure functions** | Always prefer when possible. Eliminates synchronization needs entirely. |
| **Synchronized data structures** | When a standard structure (queue, counter) fits the problem. Easiest to use correctly. |
| **Locks (mutex)** | When you need to protect arbitrary shared mutable state. Ensure `try/finally` release. |
| **Barriers** | When work naturally divides into phases (read phase, write phase). |
| **Message passing** | When tasks can work independently and communicate results. The idiomatic approach for `worker_threads`. |

The fundamental trade-off is between **safety** (no race conditions) and **performance** (maximal parallelism). Start with the safest approach (message passing or immutable data) and add shared-state synchronization only when performance measurements justify the added complexity.
