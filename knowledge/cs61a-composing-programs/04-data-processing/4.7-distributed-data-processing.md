## Key Concepts

- **MapReduce** is a programming paradigm for processing large datasets across multiple machines. It separates the application logic (pure map and reduce functions) from the complexity of distributed coordination.
- **Map phase** applies a mapper function to each input item, emitting zero or more intermediate `[key, value]` pairs. Multiple mappers run in parallel on different partitions of the input.
- **Shuffle phase** (also called the sort phase) groups all intermediate key-value pairs by key so that pairs sharing the same key can be reduced together. This is the communication bottleneck but enables the decoupling of map and reduce tasks.
- **Reduce phase** applies a reducer function to the grouped values for each key, producing aggregated output. Multiple reducers run in parallel, each handling a subset of keys.
- **Pure functions** are required for both map and reduce. Because pure functions have no side effects and depend only on their inputs, the framework can reorder, parallelize, and retry computations without affecting correctness.
- **Partition** splits the input dataset into chunks that can be assigned to separate workers. Deterministic partitioning ensures the same item always goes to the same partition.
- **Combiner** is an optional local pre-aggregation step on the mapper side that reduces the volume of intermediate data before the shuffle, improving network efficiency.

## Content

### 4.7.1 MapReduce

MapReduce was designed to process datasets too large for a single machine. The core insight is that many data processing tasks can be decomposed into two pure-function stages:

1. **Map**: Transform each input item into zero or more intermediate `[key, value]` pairs.
2. **Shuffle**: Group all intermediate pairs by key.
3. **Reduce**: Aggregate the values for each key into a final result.

The conceptual flow is:

```
input -> partition -> map -> shuffle -> reduce -> output
```

Consider the problem of counting vowels across a large text corpus. Each line of text is an input item. The mapper emits `[vowel, count]` pairs for each vowel found in the line. The shuffle groups all counts by vowel. The reducer sums the counts for each vowel.

```javascript
// Mapper: emit [vowel, count] for each vowel in a line
function countVowelsMapper(line) {
  const vowels = ["a", "e", "i", "o", "u"];
  const pairs = [];
  for (const vowel of vowels) {
    let count = 0;
    for (const ch of line) {
      if (ch === vowel) count++;
    }
    if (count > 0) {
      pairs.push([vowel, count]);
    }
  }
  return pairs;
}

// Reducer: sum all values for a key
function sumReducer(key, values) {
  return values.reduce((a, b) => a + b, 0);
}
```

Running on a haiku:

```javascript
const lines = [
  "Google MapReduce",
  "Is a Big Data framework",
  "For batch processing",
];

// Map phase: apply mapper to each line
const mapped = lines.flatMap(countVowelsMapper);

// Shuffle phase: group by key
const grouped = shuffle(mapped);

// Reduce phase: sum each group
const result = reduceGroups(grouped, sumReducer);

// Sorted output for deterministic display
Object.entries(result).sort(([a], [b]) => a.localeCompare(b));
// [ ["a", 6], ["e", 5], ["i", 2], ["o", 5], ["u", 1] ]
```

The principal advantage of MapReduce is that it **separates concerns**:

1. The developer specifies *what* to compute (the pure map and reduce functions).
2. The framework handles *how* to distribute it (partitioning, communication, fault tolerance, monitoring).

Because both functions are pure, the framework can execute them in any order, on any machine, and retry failed tasks -- all without the developer writing any coordination logic. This is horizontal scaling: adding more machines linearly increases throughput.

### 4.7.2 Local Implementation

We build a complete local MapReduce pipeline in JavaScript. This implementation runs on a single machine but follows the same partition-map-shuffle-reduce structure as a distributed system.

**Partition** splits items into N chunks deterministically:

```javascript
function partition(items, partitionCount) {
  const parts = Array.from({ length: partitionCount }, () => []);
  for (let i = 0; i < items.length; i++) {
    parts[i % partitionCount].push(items[i]);
  }
  return parts;
}
```

Items are assigned to partitions by their index modulo the partition count, so the assignment is deterministic and repeatable.

**MapPartition** applies the mapper to each item in one partition, returning an array of `[key, value]` pairs:

```javascript
function mapPartition(part, mapper) {
  const pairs = [];
  for (const item of part) {
    pairs.push(...mapper(item));
  }
  return pairs;
}
```

**Shuffle** groups all `[key, value]` pairs by key into an object mapping each key to its array of values:

```javascript
function shuffle(mappedPairs) {
  const groups = Object.create(null);
  for (const [key, value] of mappedPairs) {
    if (!Object.hasOwn(groups, key)) {
      groups[key] = [];
    }
    groups[key].push(value);
  }
  return groups;
}
```

**ReduceGroups** applies the reducer to each key's values, returning a new object with one result per key:

```javascript
function reduceGroups(groups, reducer) {
  const result = Object.create(null);
  for (const key of Object.keys(groups).sort()) {
    result[key] = reducer(key, groups[key]);
  }
  return result;
}
```

**MapReduce** composes the full pipeline:

```javascript
function mapReduce(items, mapper, reducer, partitionCount = 2) {
  // 1. Partition the input
  const parts = partition(items, partitionCount);

  // 2. Map each partition
  const mapped = parts.flatMap((part) => mapPartition(part, mapper));

  // 3. Shuffle: group by key
  const grouped = shuffle(mapped);

  // 4. Reduce each group
  return reduceGroups(grouped, reducer);
}
```

#### Word Count

The classic MapReduce example counts how many times each word appears across a collection of text lines.

```javascript
function wordCountMapper(line) {
  const words = line.toLowerCase().split(/\s+/).filter((w) => w.length > 0);
  return words.map((word) => [word, 1]);
}

function wordCountReducer(key, counts) {
  return counts.reduce((a, b) => a + b, 0);
}

function wordCount(lines) {
  return mapReduce(lines, wordCountMapper, wordCountReducer);
}
```

Running word count on a small corpus:

```javascript
const lines = [
  "the quick brown fox",
  "jumps over the lazy dog",
  "the fox was quick",
];

wordCount(lines);
// {
//   "brown": 1,
//   "dog": 1,
//   "fox": 2,
//   "jumps": 1,
//   "lazy": 1,
//   "over": 1,
//   "quick": 2,
//   "the": 3,
//   "was": 1,
// }
```

The mapper emits `[word, 1]` for each word. The shuffle collects all the `1`s for each word. The reducer sums them.

#### Inverted Index

An inverted index maps each word to the list of document IDs that contain it -- the core data structure behind search engines.

```javascript
function invertedIndexMapper(document) {
  const words = document.text
    .toLowerCase()
    .split(/\s+/)
    .filter((w) => w.length > 0);
  const unique = [...new Set(words)];
  return unique.map((word) => [word, document.id]);
}

function invertedIndexReducer(key, docIds) {
  // Deduplicate and sort for deterministic output
  return [...new Set(docIds)].sort();
}

function invertedIndex(documents) {
  return mapReduce(documents, invertedIndexMapper, invertedIndexReducer);
}
```

Running the inverted index:

```javascript
const documents = [
  { id: "doc1", text: "map reduce distributed" },
  { id: "doc2", text: "distributed data processing" },
  { id: "doc3", text: "map data filter" },
];

invertedIndex(documents);
// {
//   "data": ["doc2", "doc3"],
//   "distributed": ["doc1", "doc2"],
//   "filter": ["doc3"],
//   "map": ["doc1", "doc3"],
//   "processing": ["doc2"],
//   "reduce": ["doc1"],
// }
```

Each document's mapper emits `[word, docId]` for each unique word. The shuffle collects all document IDs per word. The reducer deduplicates and sorts the ID lists.

#### Combiner Optimization

In a distributed setting, mappers may emit a very large number of intermediate pairs. A **combiner** is a local pre-aggregation function run on each mapper's output before the shuffle. For associative and commutative operations like summation, the combiner is identical to the reducer:

```javascript
// Without combiner: mapper emits [word, 1] for every word occurrence
//   "the the the" -> [["the", 1], ["the", 1], ["the", 1]]

// With combiner: pre-aggregate locally before shuffle
function wordCountCombiner(pairs) {
  const local = Object.create(null);
  for (const [key, value] of pairs) {
    local[key] = (local[key] || 0) + value;
  }
  return Object.entries(local);
}

// After combiner: "the the the" -> [["the", 3]]
// The shuffle then receives far fewer pairs, reducing network traffic.
```

The combiner is optional and purely an optimization. It does not change the final result -- it only reduces the volume of data that must be shuffled across workers.

### 4.7.3 Distributed Implementation

The local implementation above mirrors the structure of a real distributed MapReduce system. Here is how each piece maps to a multi-machine deployment.

**The distributed mental model:**

| Local Concept | Distributed Equivalent |
|---|---|
| `partition(items, N)` | Input data is split across N machines in a distributed file system (e.g., HDFS) |
| `mapPartition(part, mapper)` | Each machine runs a mapper task on its local data shard |
| `shuffle(mappedPairs)` | The framework sorts and transfers intermediate pairs across the network so that all pairs for key K arrive at the same reducer machine |
| `reduceGroups(groups, reducer)` | Each reducer machine processes its assigned keys and writes output to distributed storage |

**What the framework handles (that our local version does not):**

1. **Data distribution.** Input files are split into blocks (typically 128 MB) and replicated across machines in a distributed file system. Each mapper reads from a local or nearby replica to minimize network transfer.

2. **Fault tolerance.** When a machine fails mid-computation, the framework reassigns its tasks to another machine and re-executes them. Because map and reduce functions are pure, re-execution always produces the same result. This is a key reason MapReduce mandates pure functions.

3. **Network communication.** The shuffle phase requires transferring intermediate key-value pairs from every mapper to the correct reducer. In the local implementation this is an in-memory group-by; across machines it involves sorting, partitioning by key hash ranges, and streaming data over the network.

4. **Progress monitoring.** The framework tracks task completion, retries slow tasks (speculative execution), and provides a user interface showing job progress.

**Real-world frameworks:**

- **Hadoop** is the original open-source MapReduce implementation. It uses a distributed file system (HDFS) and a job tracker that assigns map and reduce tasks to worker nodes. Hadoop's streaming interface allows mapper and reducer programs written in any language -- the original text's Python programs can be used directly with Hadoop.
- **Apache Spark** extends the MapReduce model with in-memory computation and a richer set of transformations (filter, join, aggregate). Spark's resilient distributed datasets (RDDs) keep intermediate results in memory across stages, avoiding the disk I/O bottleneck of Hadoop's map-shuffle-reduce cycle.

**Conceptual distributed pipeline** (not runnable -- for illustration only):

```
                    +----------+
                    |  Input   |
                    | Dataset  |
                    +----+-----+
                         |
              +----------+----------+
              |          |          |
         +----+----+ +----+----+ +----+----+
         | Mapper  | | Mapper  | | Mapper  |    Map Phase
         |  (M1)   | |  (M2)   | |  (M3)   |    (parallel)
         +----+----+ +----+----+ +----+----+
              |          |          |
         +----+----+ +----+----+ +----+----+
         | Combine | | Combine | | Combine |    Optional
         |  (C1)   | |  (C2)   | |  (C3)   |    Combiner
         +----+----+ +----+----+ +----+----+
              |          |          |
              +----------+----------+
                         |
                   Shuffle / Sort         Group by key
                   (network I/O)          across machines
                         |
              +----------+----------+
              |          |          |
         +----+----+ +----+----+ +----+----+
         | Reducer | | Reducer | | Reducer |    Reduce Phase
         |  (R1)   | |  (R2)   | |  (R3)   |    (parallel)
         +----+----+ +----+----+ +----+----+
              |          |          |
              +----------+----------+
                         |
                    +----+-----+
                    |  Output  |
                    | Dataset  |
                    +----------+
```

In practice, a distributed MapReduce job is launched by submitting the mapper and reducer code to a cluster manager. The framework handles partition assignment, task scheduling, data movement, failure recovery, and result collection. The developer's job remains the same: write pure map and reduce functions.

The connection to message passing (section 4.6) is that distributed MapReduce uses inter-process communication to transfer intermediate data between mappers and reducers. However, the MapReduce abstraction hides this communication behind a functional interface -- the developer never explicitly sends or receives messages.

## Python vs JavaScript Notes

| Topic | Python (Original) | JavaScript (This Adaptation) |
|-------|--------------------|------------------------------|
| **Local implementation** | Unix pipes: `cat input \| ./mapper.py \| sort \| ./reducer.py` | In-memory pipeline: `partition -> mapPartition -> shuffle -> reduceGroups` |
| **Standard I/O** | `sys.stdin` / `sys.stdout` for streaming lines | Not used; all data is in-memory arrays |
| **Emit function** | `emit(key, value)` writes tab-separated output | Mapper returns an array of `[key, value]` pairs |
| **Grouping** | `values_by_key()` reads sorted stdin and yields `(key, iterator)` | `shuffle()` groups `[key, value]` pairs into `{ key: [values] }` |
| **Partitioning** | Implicit in Hadoop's input splits | Explicit `partition(items, count)` using index modulo |
| **Combiner** | Hadoop combiner class or Unix `sort \| uniq -c` | Local `wordCountCombiner` function that pre-aggregates pairs |
| **Distributed execution** | Hadoop streaming interface with Python scripts | Conceptual only; no runnable distributed code |
| **Sorting** | Unix `sort` command between map and reduce | `Object.keys(groups).sort()` for deterministic output order |
| **Pure functions** | Required by the MapReduce contract | Same requirement; all mapper/reducer functions are pure |
