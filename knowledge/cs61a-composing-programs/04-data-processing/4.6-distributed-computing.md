## Key Concepts

- **Distributed computing** coordinates multiple independent computers that do not share memory, communicating instead through **messages** transferred over a network.
- **Messages** are sequences of bytes that follow a **message protocol** -- a set of rules for encoding and interpreting messages that both sender and receiver agree upon.
- **Serialization** converts structured data into a byte or text representation for transmission; **deserialization** reconstructs the original structure on the receiving end.
- **Client/server architecture** divides participants into servers that provide a service and clients that consume it. The server is a central point of contact.
- **Peer-to-peer systems** distribute labor equally among all participants. Every node can send, receive, and forward messages, and all contribute processing power and memory.
- **Message forwarding** in peer-to-peer systems passes messages through neighboring peers toward a destination, using a visited set to prevent routing loops.

## Content

### 4.6.1 Messages

Messages are the fundamental unit of communication in distributed systems. A message is a sequence of bytes transferred from one computer to another over a network. The purpose varies: requesting data, sending data, or instructing another computer to perform a computation.

A **message protocol** defines the rules for encoding and interpreting messages. Both the sender and the receiver must agree on the protocol for communication to succeed. Protocols are not tied to a specific programming language -- any program that conforms to the protocol can participate.

In practice, real distributed systems use protocols like TCP/IP for reliable byte-stream delivery and HTTP for request/response communication between web browsers and servers. These topics are important but outside the scope of this conceptual introduction. Here we focus on the structure of messages themselves.

**Constructing messages.** A message is a plain object with fields that identify its origin, destination, type, and payload:

```javascript
function makeMessage({ from, to, type, payload }) {
  return { from, to, type, payload };
}
```

For example, a client might construct a request message:

```javascript
const request = makeMessage({
  from: "client-1",
  to: "server",
  type: "query",
  payload: { key: "temperature" },
});
// { from: "client-1", to: "server", type: "query", payload: { key: "temperature" } }
```

**Serialization and deserialization.** Before a message can be transmitted, it must be converted to a format suitable for transfer -- a process called **serialization**. On the receiving end, **deserialization** reconstructs the original data structure. In JavaScript, `JSON.stringify` and `JSON.parse` provide these operations:

```javascript
function serializeMessage(message) {
  return JSON.stringify(message);
}

function deserializeMessage(text) {
  return JSON.parse(text);
}
```

Round-tripping a message through serialization preserves its structure:

```javascript
const wire = serializeMessage(request);
// '{"from":"client-1","to":"server","type":"query","payload":{"key":"temperature"}}'

const restored = deserializeMessage(wire);
// { from: "client-1", to: "server", type: "query", payload: { key: "temperature" } }

restored.from === request.from;  // true
restored.payload.key === request.payload.key;  // true
```

Serialization constrains what can be sent: only JSON-compatible values (strings, numbers, booleans, null, plain objects, and arrays) survive the round trip. Functions, `Map` instances, `undefined` properties, and circular references are lost or cause errors. This is a design feature -- it forces messages to be self-contained, serializable data that any language can process.

### 4.6.2 Client/Server Architecture

The client/server architecture is a way to dispense a service from a central source. A **server** provides a service and multiple **clients** communicate with the server to consume that service. The server responds to requests; the client issues requests and uses the response.

This model is powerful because of its **modularity**: clients do not need to know how the server produces its results, and the server does not need to know how clients will use them. The World Wide Web is the most influential application of this architecture -- a web browser (client) requests pages from a web server, which responds with HTML content.

A drawback is that the server is a **single point of failure**: if it goes down, no client can be served. Another drawback is that computing resources become scarce as the number of clients grows, because clients increase demand without contributing resources.

**Conceptual note on real networking.** In a real distributed system, client and server communicate over a network using TCP sockets, HTTP, or similar protocols. Node.js provides the `net` module for raw TCP, the `http` module for HTTP servers, and `fetch` for HTTP clients. Our examples below use a deterministic, in-memory `MessageBus` that simulates the routing of messages without any actual network access. This keeps the examples runnable and testable.

**The MessageBus.** A `MessageBus` acts as the communication infrastructure. It accepts message handlers registered under string identifiers and routes serialized messages to the correct handler:

```javascript
class MessageBus {
  constructor() {
    this._handlers = Object.create(null);
    this._log = [];
  }

  register(id, handler) {
    this._handlers[id] = handler;
  }

  send(message) {
    const wire = serializeMessage(message);
    const delivered = deserializeMessage(wire);
    this._log.push(delivered);
    const handler = this._handlers[delivered.to];
    if (handler) {
      return handler(delivered);
    }
    return undefined;
  }

  broadcast(from, type, payload) {
    const results = [];
    for (const id of Object.keys(this._handlers)) {
      if (id !== from) {
        const msg = makeMessage({ from, to: id, type, payload });
        const result = this.send(msg);
        if (result !== undefined) {
          results.push({ to: id, result });
        }
      }
    }
    return results;
  }

  getLog() {
    return this._log;
  }
}
```

Every message is serialized and deserialized as it passes through the bus, simulating the real-world constraint that only serializable data crosses a network boundary.

**Server.** A server registers with the bus and handles incoming request messages:

```javascript
class Server {
  constructor(id, bus, data = {}) {
    this.id = id;
    this.data = data;
    bus.register(id, (message) => this.handle(message));
  }

  handle(message) {
    if (message.type === "query") {
      const value = this.data[message.payload.key];
      if (value !== undefined) {
        return makeMessage({
          from: this.id,
          to: message.from,
          type: "response",
          payload: { key: message.payload.key, value },
        });
      }
      return makeMessage({
        from: this.id,
        to: message.from,
        type: "error",
        payload: { code: 404, text: `Key not found: ${message.payload.key}` },
      });
    }
  }
}
```

**Client.** A client registers with the bus and sends request messages to a server:

```javascript
class Client {
  constructor(id, bus) {
    this.id = id;
    this.bus = bus;
    bus.register(id, () => {});
  }

  request(serverId, type, payload) {
    const message = makeMessage({
      from: this.id,
      to: serverId,
      type,
      payload,
    });
    return this.bus.send(message);
  }
}
```

**Using the system.** Setting up the bus, a server, and two clients:

```javascript
const bus = new MessageBus();

const weatherServer = new Server("weather", bus, {
  temperature: 72,
  conditions: "sunny",
  humidity: 45,
});

const phone = new Client("phone", bus);
const laptop = new Client("laptop", bus);

// Client sends a query to the server
const response = phone.request("weather", "query", { key: "temperature" });
// { from: "weather", to: "phone", type: "response",
//   payload: { key: "temperature", value: 72 } }

response.payload.value;  // 72

// Another client queries the same server
const response2 = laptop.request("weather", "query", { key: "conditions" });
response2.payload.value;  // "sunny"

// Querying a nonexistent key
const response3 = phone.request("weather", "query", { key: "wind" });
response3.type;  // "error"
response3.payload.code;  // 404

// The bus recorded every message
bus.getLog().length;  // 3
bus.getLog()[0].type;  // "query"
```

The server does not know or care whether the request came from `phone` or `laptop`. The clients do not know how the server stores its data. This separation of concerns is the essence of the client/server abstraction.

### 4.6.3 Peer-to-Peer Systems

In a client/server system, the server is the sole provider of a service, and clients only consume. In a **peer-to-peer** system, labor is divided among all participants. Every computer (called a **peer** or **node**) can send and receive data, and all contribute processing power and memory. As the system grows, its capacity grows with it.

Peer-to-peer systems need an organized network structure so that messages reach their intended destinations. Each peer knows the location of a small number of neighbors. When a message must reach a non-neighbor, it is **forwarded** from peer to peer until it arrives.

A challenge in peer-to-peer forwarding is avoiding **routing loops** -- situations where a message circulates endlessly among a cycle of peers. The standard solution is to attach a **visited set** to the message, listing every peer that has already handled it. A peer that sees its own identifier in the visited set knows the message has looped and stops forwarding.

**Peer node.** A peer can both handle messages addressed to it and forward messages toward their destination:

Forwarding requires two addressing fields. The `to` field names the **next hop** so the `MessageBus` can deliver the message to the correct neighbor. A separate `finalDest` field names the **ultimate destination** so each peer knows whether to handle the message or keep forwarding it.

```javascript
class Peer {
  constructor(id, bus) {
    this.id = id;
    this.bus = bus;
    this.neighbors = [];
    bus.register(id, (message) => this.receive(message));
  }

  addNeighbor(peerId) {
    if (!this.neighbors.includes(peerId)) {
      this.neighbors.push(peerId);
    }
  }

  receive(message) {
    // If we are the final destination, handle it
    if (message.finalDest === this.id) {
      return this.handle(message);
    }

    // Otherwise, forward it toward the destination
    return this.forward(message);
  }

  handle(message) {
    if (message.type === "ping") {
      return makeMessage({
        from: this.id,
        to: message.from,
        type: "pong",
        payload: { echo: message.payload },
      });
    }
    return undefined;
  }

  forward(message) {
    const visited = message.payload._visited || [];

    // Stop if we have already seen this message (loop detected)
    if (visited.includes(this.id)) {
      return undefined;
    }

    // Add ourselves to the visited set and forward to neighbors
    const newVisited = [...visited, this.id];
    for (const neighborId of this.neighbors) {
      if (!newVisited.includes(neighborId)) {
        const forwarded = makeMessage({
          from: this.id,
          to: neighborId,          // addressed to the next hop
          type: message.type,
          payload: { ...message.payload, _visited: newVisited },
        });
        forwarded.finalDest = message.finalDest; // carry ultimate destination
        const result = this.bus.send(forwarded);
        if (result !== undefined) {
          return result;
        }
      }
    }
    return undefined;
  }

  sendTo(targetId, type, payload) {
    const message = makeMessage({
      from: this.id,
      to: null,                    // no next hop yet; forward() will set it
      type,
      payload: { ...payload, _visited: [] },
    });
    message.finalDest = targetId;
    return this.forward(message);
  }
}
```

`sendTo` starts with an empty visited set. When `forward` runs, it adds the sender to the visited set, then addresses each forwarded message to a neighbor (`to: neighborId`) while preserving the ultimate destination (`finalDest`). The bus delivers to the neighbor because `MessageBus.send` routes by `delivered.to`.

**Building a peer-to-peer network.** Creating a small network with a linear topology:

```javascript
const bus = new MessageBus();

const peerA = new Peer("A", bus);
const peerB = new Peer("B", bus);
const peerC = new Peer("C", bus);
const peerD = new Peer("D", bus);

// Linear topology: A -- B -- C -- D
peerA.addNeighbor("B");
peerB.addNeighbor("A");
peerB.addNeighbor("C");
peerC.addNeighbor("B");
peerC.addNeighbor("D");
peerD.addNeighbor("C");
```

Peer A can send a message to peer D even though they are not direct neighbors. The message is forwarded hop by hop through B and C:

```javascript
const result = peerA.sendTo("D", "ping", { greeting: "hello" });
// Forwarding chain: A -> B -> C -> D
// A.forward sends { to: "B", finalDest: "D", _visited: ["A"] }
// B.forward sends { to: "C", finalDest: "D", _visited: ["A","B"] }
// C.forward sends { to: "D", finalDest: "D", _visited: ["A","B","C"] }
// D sees finalDest === "D", handles the ping, and returns a pong

result.type;                  // "pong"
result.payload.echo.greeting; // "hello"
result.from;                  // "D"

bus.getLog().length;           // 3 messages on the wire: A->B, B->C, C->D
bus.getLog().map(m => m.from); // ["A", "B", "C"]
bus.getLog().map(m => m.to);   // ["B", "C", "D"]
```

**Loop detection.** If we create a cycle in the topology, the visited set prevents infinite forwarding:

```javascript
// Add an edge to create a cycle: A -- B -- C -- D -- A
peerA.addNeighbor("D");
peerD.addNeighbor("A");

// Send to a non-existent peer: the message traverses the entire cycle
// but the visited set prevents any peer from processing it twice
const result2 = peerA.sendTo("E", "ping", { test: "loop" });
result2;  // undefined (E does not exist)

// The bus log shows every peer was visited exactly once:
bus.getLog()
  .filter(m => m.payload.test === "loop")
  .map(m => `${m.from}->${m.to}`);
// ["A->B", "B->C", "C->D", "A->D", "D->C", "C->B"]
// A explores B first (depth-first); after that branch exhausts, A tries D.
// The visited set in each branch prevents revisits.
```

Without the visited set, a message traveling from A to B to C to D could be forwarded back to A (because D is now A's neighbor), creating an infinite loop. The visited set ensures each peer processes the message at most once, so even a fully connected cycle terminates after every peer has been tried.

**Comparing architectures.** The key difference between client/server and peer-to-peer:

- In **client/server**, there is one server and many clients. The server is a single point of failure. Resources do not scale with the number of clients.
- In **peer-to-peer**, every node is both a client and a server. There is no single point of failure. Resources scale with the number of participants. The tradeoff is greater complexity in routing and coordination.

Real peer-to-peer systems like BitTorrent for data transfer and distributed hash tables for data storage apply these principles at large scale. Some systems use **supernodes** -- specialized peers that handle coordination tasks like logging users in and maintaining network topology -- making them hybrid rather than pure peer-to-peer.
