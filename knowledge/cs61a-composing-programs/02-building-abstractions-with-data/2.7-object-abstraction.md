## Key Concepts

- **Generic functions**: Functions that operate on values of multiple different types, enabling polymorphic behavior across diverse data representations.
- **String conversion with `toString()`**: JavaScript uses a single `toString()` method for string representation, unlike Python which has both `__str__` and `__repr__`. Custom `toString()` implementations extend the domain of string conversion to new types.
- **Special methods and protocols**: Python's dunder methods (`__bool__`, `__len__`, `__getitem__`, `__call__`, `__add__`) do not have direct operator-overloading equivalents in JavaScript. Instead, JS uses named methods (`.add()`, `.mul()`, `get length()`), `valueOf()`, and `Symbol.toPrimitive`.
- **Multiple representations via interfaces**: Different classes can represent the same abstract data (e.g., complex numbers in rectangular or polar form) as long as they share a common interface of attribute names and behaviors.
- **Type dispatching and type coercion**: Two strategies for implementing cross-type operations -- inspecting type tags to select behavior, or converting one type into another before performing the operation.
- **Getters as computed properties**: JavaScript `get` accessors are the equivalent of Python's `@property` decorator, enabling on-the-fly computation of attribute values.

## Content

The object system allows programmers to build and use abstract data representations efficiently. It is also designed to allow multiple representations of abstract data to coexist in the same program.

A central concept in object abstraction is a *generic function*, which is a function that can accept values of multiple different types. We will consider three different techniques for implementing generic functions: shared interfaces, type dispatching, and type coercion. In the process of building up these concepts, we will also discover features of the JavaScript object system that support the creation of generic functions.

### 2.7.1 String Conversion

To represent data effectively, an object value should behave like the kind of data it is meant to represent, including producing a string representation of itself. String representations of data values are especially important in an interactive language that automatically displays the string representation of values.

String values provide a fundamental medium for communicating information among humans. Sequences of characters can be rendered on a screen, printed to paper, read aloud, converted to braille, or broadcast as Morse code. Strings are also fundamental to programming because they can represent program expressions.

**Python vs JavaScript -- a key difference.** Python stipulates that all objects should produce two different string representations: one that is human-interpretable text (`str()`, backed by `__str__`) and one that is a Python-interpretable expression (`repr()`, backed by `__repr__`). JavaScript has a single standard method: `toString()`. When JavaScript needs to convert an object to a string (e.g., in template literals, string concatenation, or `console.log`), it calls the object's `toString()` method.

Python example (two representations):

```python
# Python has both str() and repr()
from datetime import date
tues = date(2011, 9, 12)
repr(tues)   # 'datetime.date(2011, 9, 12)'  -- a Python expression
str(tues)    # '2011-09-12'                   -- human-readable
```

JavaScript equivalent (single `toString()`):

```javascript
// JavaScript uses toString() for string conversion
const d = new Date(2011, 8, 12);  // months are 0-indexed in JS
d.toString();     // 'Mon Sep 12 2011 00:00:00 GMT+0000 (...)' -- human-readable
d.toISOString();  // '2011-09-12T00:00:00.000Z'                -- machine-readable

// For a "repr-like" representation, you must implement it yourself
d.constructor.name; // 'Date'
```

Defining a string conversion function presents a challenge: we would like it to apply correctly to all data types, even those that did not exist when the conversion was first implemented. We would like it to be a *generic* or *polymorphic* function, one that can be applied to many (*poly*) different forms (*morph*) of data.

The object system provides an elegant solution: JavaScript automatically invokes the `toString()` method when converting an object to a string. By implementing `toString()` in user-defined classes, we extend the applicability of string conversion to any class we create.

```javascript
class Account {
  constructor(holder) {
    this.holder = holder;
    this.balance = 0;
  }

  // Override toString to provide a meaningful string representation
  toString() {
    return `Account(${this.holder}, balance: ${this.balance})`;
  }
}

const acc = new Account("Jack");
console.log(String(acc));  // "Account(Jack, balance: 0)"
console.log(`${acc}`);     // "Account(Jack, balance: 0)" -- template literal calls toString()
```

Without a custom `toString()`, JavaScript falls back to `"[object Object]"`:

```javascript
class Bare {}

const b = new Bare();
console.log(`${b}`); // "[object Object]"
```

These polymorphic functions are examples of a more general principle: certain functions should apply to multiple data types. Moreover, one way to create such a function is to use a shared method name (`toString`) with a different definition in each class.

For advanced use cases, JavaScript also provides `Symbol.toPrimitive`, which lets you control conversion to string, number, and default types:

```javascript
class Temperature {
  constructor(celsius) {
    this.celsius = celsius;
  }

  // Symbol.toPrimitive controls all type conversions
  [Symbol.toPrimitive](hint) {
    if (hint === "string") {
      return `${this.celsius}°C`;
    } else if (hint === "number") {
      return this.celsius;
    }
    return this.celsius; // default
  }
}

const t = new Temperature(25);
console.log(`${t}`);    // "25°C"   (string hint)
console.log(t + 5);     // 30       (default hint → number)
```

### 2.7.2 Special Methods

In Python, certain *special names* (dunder methods) are invoked by the interpreter in special circumstances -- `__init__` on construction, `__str__` on print, `__repr__` in interactive sessions. JavaScript does not have operator overloading for custom classes, so there is no way to make `a + b` invoke a custom method on user-defined objects. Instead, JavaScript relies on named methods and a smaller set of built-in protocols.

Below we translate Python's special methods to their JavaScript equivalents.

**Truthiness.** In Python, `__bool__` determines an object's truth value. In JavaScript, objects are *always* truthy -- there is no way to override this behavior for custom classes. You can, however, define a `toBoolean()` method or use `valueOf()` for certain numeric comparisons.

Python example:

```python
# Python: __bool__ controls truthiness
class Account:
    def __init__(self, holder):
        self.holder = holder
        self.balance = 0
    def __bool__(self):
        return self.balance != 0

if not Account('Jack'):
    print('Jack has nothing')  # prints because balance is 0
```

JavaScript equivalent -- no `__bool__` override is possible:

```javascript
// JavaScript: objects are ALWAYS truthy, no override possible
class Account {
  constructor(holder) {
    this.holder = holder;
    this.balance = 0;
  }
  // Cannot override truthiness -- all objects are truthy in JS
  // Workaround: provide an explicit method
  toBoolean() {
    return this.balance !== 0;
  }
}

const acc = new Account("Jack");
// Boolean(acc) === true always, but:
console.log(acc.toBoolean()); // false
if (!acc.toBoolean()) {
  console.log("Jack has nothing"); // "Jack has nothing"
}

// Using valueOf() works for numeric comparisons, NOT for boolean context
class NumericAccount {
  constructor(holder, balance) {
    this.holder = holder;
    this.balance = balance;
  }
  valueOf() {
    return this.balance;
  }
}

const na = new NumericAccount("Jack", 0);
// na == 0 is true (valueOf is called for loose equality with primitives)
console.log(na == 0);  // true
// But Boolean(na) is still true (objects are always truthy)
console.log(Boolean(na)); // true
```

**Sequence operations.** Python's `__len__` is invoked by `len()`. JavaScript uses a `length` property (or `get length()` accessor for custom classes). Python's `__getitem__` is invoked by the `[]` operator; JavaScript has no operator overloading for custom classes, so we use a `.get(index)` method instead.

Python example:

```python
# Python: __len__ and __getitem__
class MyString:
    def __init__(self, chars):
        self.chars = chars
    def __len__(self):
        return len(self.chars)
    def __getitem__(self, index):
        return self.chars[index]

s = MyString("Go Bears!")
len(s)    # 9
s[3]      # 'B'
```

JavaScript equivalent:

```javascript
// JavaScript: get length() accessor and .get() method
class MyString {
  constructor(chars) {
    this.chars = chars;
  }
  // Equivalent of __len__: use a getter
  get length() {
    return this.chars.length;
  }
  // Equivalent of __getitem__: named method (no operator overloading)
  get(index) {
    return this.chars[index];
  }
  toString() {
    return this.chars;
  }
}

const s = new MyString("Go Bears!");
console.log(s.length);   // 9
console.log(s.get(3));   // 'B'

// Built-in strings already have length and []
const builtin = "Go Bears!";
console.log(builtin.length);  // 9
console.log(builtin[3]);      // 'B'
```

**Callable objects.** In Python, `__call__` makes an object callable like a function. JavaScript has no direct equivalent -- objects cannot be "invoked" with `()`. However, you can define a `.call()` or `.apply()` method, or use a function-wrapper pattern.

Python example:

```python
# Python: __call__ makes objects callable
def make_adder(n):
    def adder(k):
        return n + k
    return adder

add_three = make_adder(3)
add_three(4)  # 7

class Adder:
    def __init__(self, n):
        self.n = n
    def __call__(self, k):
        return self.n + k

add_three_obj = Adder(3)
add_three_obj(4)  # 7
```

JavaScript equivalent -- use a function wrapper pattern:

```javascript
// JavaScript: functions are first-class; objects are not callable
function makeAdder(n) {
  return function adder(k) {
    return n + k;
  };
}

const addThree = makeAdder(3);
console.log(addThree(4)); // 7

// Option 1: A class with an explicit .call() method
class Adder {
  constructor(n) {
    this.n = n;
  }
  call(k) {
    return this.n + k;
  }
}

const addThreeObj = new Adder(3);
console.log(addThreeObj.call(4)); // 7

// Option 2: A factory that returns a function with properties (function-object)
function makeAdderObj(n) {
  function adder(k) {
    return n + k;
  }
  adder.n = n;
  adder.call = adder; // alias for clarity
  return adder;
}

const addThreeFn = makeAdderObj(3);
console.log(addThreeFn(4));    // 7 -- works as a function
console.log(addThreeFn.n);    // 3 -- has properties like an object
```

**Arithmetic.** Python's `__add__` and `__radd__` let custom classes define `+` behavior. JavaScript has no operator overloading for custom classes. You must use explicit named methods like `.add()` and `.mul()`.

Python example:

```python
# Python: __add__ and __radd__ define + behavior
class Number:
    def __add__(self, other):
        return self.add(other)
    def __mul__(self, other):
        return self.mul(other)
```

JavaScript equivalent:

```javascript
// JavaScript: no operator overloading -- use explicit methods
class Number {
  add(other) {
    throw new Error("add() not implemented");
  }
  mul(other) {
    throw new Error("mul() not implemented");
  }
}

// Usage: a.add(b) instead of a + b
// This is the idiomatic JS approach for custom numeric types
```

### 2.7.3 Multiple Representations

Abstraction barriers allow us to separate the use and representation of data. However, in large programs, it may not always make sense to speak of "the underlying representation" for a data type in a program. For one thing, there might be more than one useful representation for a data object, and we might like to design systems that can deal with multiple representations.

To take a simple example, complex numbers may be represented in two almost equivalent ways: in rectangular form (real and imaginary parts) and in polar form (magnitude and angle). Sometimes the rectangular form is more appropriate and sometimes the polar form is more appropriate. Indeed, it is perfectly plausible to imagine a system in which complex numbers are represented in both ways, and in which the functions for manipulating complex numbers work with either representation.

We will begin our implementation at the highest level of abstraction and work towards concrete representations. A `Complex` number is a `Number`, and numbers can be added or multiplied together. How numbers can be added or multiplied is abstracted by the method names `add` and `mul`.

```javascript
class Number {
  add(other) {
    return this.add(other);
  }
  mul(other) {
    return this.mul(other);
  }
}
```

Wait -- that would cause infinite recursion. In Python, `__add__` delegates to `add`, and subclasses implement `add`. In JavaScript, we use the same pattern: the base class defines the public interface, and subclasses provide the concrete implementation.

```javascript
// Base class -- subclasses must override add() and mul()
class Number {
  // These will be overridden by subclasses
  add(other) {
    throw new Error("add() must be implemented by subclass");
  }
  mul(other) {
    throw new Error("mul() must be implemented by subclass");
  }
}
```

The `Complex` class inherits from `Number` and describes arithmetic for complex numbers:

```javascript
class Complex extends Number {
  add(other) {
    return new ComplexRI(this.real + other.real, this.imag + other.imag);
  }
  mul(other) {
    const magnitude = this.magnitude * other.magnitude;
    return new ComplexMA(magnitude, this.angle + other.angle);
  }
}
```

This implementation assumes two classes exist for complex numbers:

- `ComplexRI` constructs a complex number from real and imaginary parts (rectangular form).
- `ComplexMA` constructs a complex number from a magnitude and angle (polar form).

**Interfaces.** Object attributes, which are a form of message passing, allow different data types to respond to the same message in different ways. A shared set of messages that elicit similar behavior from different classes is a powerful method of abstraction. An *interface* is a set of shared attribute names, along with a specification of their behavior. In the case of complex numbers, the interface needed to implement arithmetic consists of four attributes: `real`, `imag`, `magnitude`, and `angle`.

For complex arithmetic to be correct, these attributes must be consistent. That is, the rectangular coordinates (`real`, `imag`) and the polar coordinates (`magnitude`, `angle`) must describe the same point on the complex plane.

**Properties (Getters).** Python's `@property` decorator allows functions to be called without call expression syntax. JavaScript's `get` accessors serve the same purpose. The `ComplexRI` class stores `real` and `imag` attributes and computes `magnitude` and `angle` on demand using getters.

```javascript
// Using Math.atan2 for the angle calculation

class ComplexRI extends Complex {
  constructor(real, imag) {
    super();
    this.real = real;
    this.imag = imag;
  }

  // Equivalent of Python @property -- computed on access, no parentheses needed
  get magnitude() {
    return Math.sqrt(this.real ** 2 + this.imag ** 2);
  }

  get angle() {
    return Math.atan2(this.imag, this.real);
  }

  toString() {
    return `ComplexRI(${this.real}, ${this.imag})`;
  }
}
```

As a result of this implementation, all four attributes needed for complex arithmetic can be accessed without parentheses, and changes to `real` or `imag` are reflected in `magnitude` and `angle`:

```javascript
const ri = new ComplexRI(5, 12);
console.log(ri.real);      // 5
console.log(ri.magnitude); // 13.0
ri.real = 9;
console.log(ri.real);      // 9
console.log(ri.magnitude); // 15.0
```

Similarly, `ComplexMA` stores `magnitude` and `angle`, but computes `real` and `imag` whenever those attributes are accessed:

```javascript
class ComplexMA extends Complex {
  constructor(magnitude, angle) {
    super();
    this.magnitude = magnitude;
    this.angle = angle;
  }

  // Computed on access
  get real() {
    return this.magnitude * Math.cos(this.angle);
  }

  get imag() {
    return this.magnitude * Math.sin(this.angle);
  }

  toString() {
    return `ComplexMA(${this.magnitude}, ${(this.angle / Math.PI).toFixed(1)} * pi)`;
  }
}
```

Changes to `magnitude` or `angle` are reflected immediately in `real` and `imag`:

```javascript
const ma = new ComplexMA(2, Math.PI / 2);
console.log(ma.imag);   // 2.0
ma.angle = Math.PI;
console.log(ma.real);   // -2.0
```

Our implementation of complex numbers is now complete. Either class implementing complex numbers can be used for either argument in either arithmetic method:

```javascript
// In Python: ComplexRI(1, 2) + ComplexMA(2, pi/2) uses +
// In JavaScript: use .add() explicitly
const sum = new ComplexRI(1, 2).add(new ComplexMA(2, Math.PI / 2));
console.log(sum.toString()); // ComplexRI(1, 4)

const product = new ComplexRI(0, 1).mul(new ComplexRI(0, 1));
console.log(product.toString()); // ComplexMA(1, 1.0 * pi)
```

The interface approach to encoding multiple representations has appealing properties. The class for each representation can be developed separately; they must only agree on the names of the attributes they share, as well as any behavior conditions for those attributes. The interface is also *additive*. If another programmer wanted to add a third representation of complex numbers to the same program, they would only have to create another class with the same attributes.

### 2.7.4 Generic Functions

Generic functions are methods or functions that apply to arguments of different types. We have seen many examples already. The `Complex.add` method is generic, because it can take either a `ComplexRI` or `ComplexMA` as the value for `other`. This flexibility was gained by ensuring that both `ComplexRI` and `ComplexMA` share an interface. Using interfaces and message passing is only one of several methods used to implement generic functions. We will consider two others in this section: type dispatching and type coercion.

Suppose that, in addition to our complex number classes, we implement a `Rational` class to represent fractions exactly. The `add` and `mul` methods express the same computations as the `addRational` and `mulRational` functions from earlier in the chapter.

```javascript
// GCD helper function
function gcd(a, b) {
  a = Math.abs(a);
  b = Math.abs(b);
  while (b !== 0) {
    [a, b] = [b, a % b];
  }
  return a;
}

class Rational extends Number {
  constructor(numer, denom) {
    super();
    const g = gcd(numer, denom);
    this.numer = numer / g;
    this.denom = denom / g;
  }

  toString() {
    return `Rational(${this.numer}, ${this.denom})`;
  }

  add(other) {
    const [nx, dx] = [this.numer, this.denom];
    const [ny, dy] = [other.numer, other.denom];
    return new Rational(nx * dy + ny * dx, dx * dy);
  }

  mul(other) {
    return new Rational(
      this.numer * other.numer,
      this.denom * other.denom
    );
  }
}
```

We have implemented the interface of the `Number` superclass by including `add` and `mul` methods. As a result, we can add and multiply rational numbers:

```javascript
const r1 = new Rational(2, 5).add(new Rational(1, 10));
console.log(r1.toString()); // Rational(1, 2)

const r2 = new Rational(1, 4).mul(new Rational(2, 3));
console.log(r2.toString()); // Rational(1, 6)
```

However, we cannot yet add a rational number to a complex number, although in mathematics such a combination is well-defined. We would like to introduce this cross-type operation in some carefully controlled way.

**Type dispatching.** One way to implement cross-type operations is to select behavior based on the types of the arguments to a function or method. The idea of type dispatching is to write functions that inspect the type of arguments they receive, then execute code that is appropriate for those types.

In JavaScript, `instanceof` checks if an object is an instance of a class (including inheritance):

```javascript
const c = new ComplexRI(1, 1);
console.log(c instanceof ComplexRI); // true
console.log(c instanceof Complex);   // true
console.log(c instanceof ComplexMA); // false
```

A simple example of type dispatching is an `isReal` function that uses a different implementation for each type of complex number:

```javascript
function isReal(c) {
  if (c instanceof ComplexRI) {
    return c.imag === 0;
  } else if (c instanceof ComplexMA) {
    return c.angle % Math.PI === 0;
  }
  return false;
}

console.log(isReal(new ComplexRI(1, 1))); // false
console.log(isReal(new ComplexMA(2, Math.PI))); // true
```

Type dispatching is not always performed using `instanceof`. For arithmetic, we will give a `typeTag` property to `Rational` and `Complex` instances. When two values `x` and `y` have the same `typeTag`, then we can combine them directly with `x.add(y)`. If not, we need a cross-type operation.

```javascript
// Assign type tags
Rational.prototype.typeTag = "rat";
Complex.prototype.typeTag = "com";

console.log(new Rational(2, 5).typeTag === new Rational(1, 2).typeTag); // true
console.log(new ComplexRI(1, 1).typeTag === new ComplexMA(2, Math.PI / 2).typeTag); // true
console.log(new Rational(2, 5).typeTag === new ComplexRI(1, 1).typeTag); // false
```

To combine complex and rational numbers, we write functions that rely on both of their representations simultaneously:

```javascript
function addComplexAndRational(c, r) {
  return new ComplexRI(c.real + r.numer / r.denom, c.imag);
}

function mulComplexAndRational(c, r) {
  let rMagnitude = r.numer / r.denom;
  let rAngle = 0;
  if (rMagnitude < 0) {
    rMagnitude = -rMagnitude;
    rAngle = Math.PI;
  }
  return new ComplexMA(c.magnitude * rMagnitude, c.angle + rAngle);
}

// Both operations are commutative, so swap argument order:
function addRationalAndComplex(r, c) {
  return addComplexAndRational(c, r);
}

function mulRationalAndComplex(r, c) {
  return mulComplexAndRational(c, r);
}
```

The role of type dispatching is to ensure that these cross-type operations are used at appropriate times. Below, we rewrite the `Number` class to use type dispatching for its `add` and `mul` methods. We use the `typeTag` attribute to distinguish types of arguments:

```javascript
// Cross-type operation registries
const adders = {
  "com,rat": addComplexAndRational,
  "rat,com": addRationalAndComplex,
};

const multipliers = {
  "com,rat": mulComplexAndRational,
  "rat,com": mulRationalAndComplex,
};

class Number {
  add(other) {
    const key = `${this.typeTag},${other.typeTag}`;
    if (this.typeTag === other.typeTag) {
      return this._add(other);
    } else if (key in adders) {
      return adders[key](this, other);
    }
    throw new Error(`Cannot add ${this.typeTag} and ${other.typeTag}`);
  }

  mul(other) {
    const key = `${this.typeTag},${other.typeTag}`;
    if (this.typeTag === other.typeTag) {
      return this._mul(other);
    } else if (key in multipliers) {
      return multipliers[key](this, other);
    }
    throw new Error(`Cannot multiply ${this.typeTag} and ${other.typeTag}`);
  }

  // Subclasses override these for same-type arithmetic
  _add(other) {
    throw new Error("_add() must be implemented by subclass");
  }

  _mul(other) {
    throw new Error("_mul() must be implemented by subclass");
  }
}
```

Now `Complex` and `Rational` override `_add` and `_mul` instead of `add` and `mul`:

```javascript
class Complex extends Number {
  _add(other) {
    return new ComplexRI(this.real + other.real, this.imag + other.imag);
  }
  _mul(other) {
    return new ComplexMA(this.magnitude * other.magnitude, this.angle + other.angle);
  }
}

class Rational extends Number {
  _add(other) {
    return new Rational(
      this.numer * other.denom + other.numer * this.denom,
      this.denom * other.denom
    );
  }
  _mul(other) {
    return new Rational(this.numer * other.numer, this.denom * other.denom);
  }
}
```

This dictionary-based approach to type dispatching is extensible. New subclasses of `Number` could install themselves into the system by declaring a type tag and adding cross-type operations to the `adders` and `multipliers` registries.

Now we can mix types in addition and multiplication:

```javascript
const result1 = new ComplexRI(1.5, 0).add(new Rational(3, 2));
console.log(result1.toString()); // ComplexRI(3, 0)

const result2 = new Rational(-1, 2).mul(new ComplexMA(4, Math.PI / 2));
console.log(result2.toString()); // ComplexMA(2, 1.5 * pi)
```

**Coercion.** In the general situation of completely unrelated operations acting on completely unrelated types, implementing explicit cross-type operations is the best that one can hope for. Fortunately, we can sometimes do better by taking advantage of additional structure in our type system. Often the different data types are not completely independent, and there may be ways to view objects of one type as being of another type. This process is called *coercion*.

For example, if we are asked to arithmetically combine a rational number with a complex number, we can view the rational number as a complex number whose imaginary part is zero. After doing so, we can use `Complex._add` and `Complex._mul` to combine them.

A typical coercion function transforms a rational number to a complex number:

```javascript
function rationalToComplex(r) {
  return new ComplexRI(r.numer / r.denom, 0);
}
```

The coercion-based version of `Number` performs cross-type operations by attempting to coerce both arguments to the same type:

```javascript
const coercions = {
  "rat,com": rationalToComplex,
};

class Number {
  add(other) {
    const [x, y] = this.coerce(other);
    return x._add(y);
  }

  mul(other) {
    const [x, y] = this.coerce(other);
    return x._mul(y);
  }

  coerce(other) {
    if (this.typeTag === other.typeTag) {
      return [this, other];
    } else if (`${this.typeTag},${other.typeTag}` in coercions) {
      return [coercions[`${this.typeTag},${other.typeTag}`](this), other];
    } else if (`${other.typeTag},${this.typeTag}` in coercions) {
      return [this, coercions[`${other.typeTag},${this.typeTag}`](other)];
    }
    throw new Error(`Cannot coerce ${this.typeTag} and ${other.typeTag}`);
  }

  _add(other) {
    throw new Error("_add() must be implemented by subclass");
  }

  _mul(other) {
    throw new Error("_mul() must be implemented by subclass");
  }
}
```

This coercion scheme has advantages over defining explicit cross-type operations. Although we still need to write coercion functions to relate the types, we need only one function for each pair of types rather than a different function for each pair and each generic operation. What we are counting on is that the appropriate transformation between types depends only on the types themselves, not on the particular operation to be applied.

Despite its advantages, coercion does have potential drawbacks. Coercion functions can lose information when they are applied. In our example, rational numbers are exact representations, but become approximations when they are converted to complex numbers with floating-point real and imaginary parts.

Some programming languages have automatic coercion systems built in. JavaScript itself performs implicit type coercion extensively (e.g., `"3" + 4` gives `"34"`, `"3" - 1` gives `2`). However, these built-in coercions apply only to primitive types, not to user-defined classes.

## Python vs JavaScript Notes

| Feature | Python | JavaScript |
|---|---|---|
| String representation | `__str__()` (human-readable) and `__repr__()` (unambiguous) | Single `toString()` method; `Symbol.toPrimitive` for advanced control |
| Default object string | `<ClassName object at 0x...>` or class-defined | `"[object Object]"` |
| Truthiness override | `__bool__()` method | Not possible; all objects are truthy |
| Length protocol | `__len__()` invoked by `len()` | `length` property or `get length()` accessor |
| Indexing protocol | `__getitem__()` invoked by `[]` operator | No operator overloading; use `.get(index)` method |
| Callable objects | `__call__()` method makes objects callable | Not possible; use function wrapper pattern or `.call()` method |
| Operator overloading | `__add__`, `__radd__`, `__mul__`, etc. | Not available for custom classes; use named methods (`.add()`, `.mul()`) |
| Computed properties | `@property` decorator | `get` accessor in class or object literal |
| Type checking | `isinstance(obj, ClassName)` | `obj instanceof ClassName` |
| Type tags | Custom class attribute | Custom prototype property or instance property |
| Implicit coercion | Removed from Python 3 | Extensive for primitives only (`"3" + 4` => `"34"`) |
| `valueOf()` | No equivalent | Returns primitive value for numeric/loose-equality contexts |
| `Symbol.toPrimitive` | No equivalent | Controls conversion to string/number/default with hint |
