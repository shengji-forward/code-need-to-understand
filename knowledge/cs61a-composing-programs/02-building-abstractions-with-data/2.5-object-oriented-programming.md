## Key Concepts

- **Object-oriented programming (OOP)** organizes programs around objects that bundle local state and behavior, building on ideas from data abstraction, dispatch dictionaries, and mutable data.
- A **class** serves as a template for creating objects; each object is an **instance** of a particular class with its own instance attributes.
- **Methods** are functions defined inside a class that operate on the object via `this`; they are invoked using dot notation.
- **Class attributes** (static properties) are shared across all instances of a class, while **instance attributes** belong to each object individually.
- **Inheritance** lets a subclass specialize a base class by overriding some attributes and inheriting the rest via the `extends` and `super` keywords.
- JavaScript does not support **multiple inheritance** natively; the **mixin pattern** serves as the idiomatic alternative for composing behavior from multiple sources.

## Content

Object-oriented programming (OOP) is a method for organizing programs that brings together many of the ideas introduced in this chapter. Like the functions in data abstraction, classes create abstraction barriers between the use and implementation of data. Like dispatch dictionaries, objects respond to behavioral requests. Like mutable data structures, objects have local state that is not directly accessible from the global environment. JavaScript's class syntax promotes the use of these techniques for organizing programs. Much of this syntax is shared among other object-oriented programming languages.

The object system offers more than just convenience. It enables a new metaphor for designing programs in which several independent agents interact within the computer. Each object bundles together local state and behavior in a way that abstracts the complexity of both. Objects communicate with each other, and useful results are computed as a consequence of their interaction. Not only do objects pass messages, they also share behavior among other objects of the same type and inherit characteristics from related types.

The paradigm of object-oriented programming has its own vocabulary that supports the object metaphor. We have seen that an object is a data value that has methods and attributes, accessible via dot notation. Every object also has a type, called its *class*. To create new types of data, we implement new classes.

### 2.5.1 Objects and Classes

A class serves as a template for all objects whose type is that class. Every object is an instance of some particular class. The objects we have used so far all have built-in classes, but new user-defined classes can be created as well. A class definition specifies the attributes and methods shared among objects of that class. We will introduce class syntax by revisiting the example of a bank account.

When introducing local state, we saw that bank accounts are naturally modeled as mutable values that have a balance. A bank account object should have a `withdraw` method that updates the account balance and returns the requested amount, if it is available. To complete the abstraction: a bank account should be able to return its current balance, return the name of the account holder, and accept an amount for deposit.

An `Account` class allows us to create multiple instances of bank accounts. The act of creating a new object instance is known as *instantiating* the class. In JavaScript, we instantiate a class using the `new` keyword followed by the class name and constructor arguments.

```javascript
const a = new Account('Kirk');
```

An *attribute* of an object is a name-value pair associated with the object, which is accessible via dot notation. The attributes specific to a particular object, as opposed to all objects of a class, are called *instance attributes*. Each `Account` has its own balance and account holder name, which are examples of instance attributes. In the broader programming community, instance attributes may also be called *fields*, *properties*, or *instance variables*.

```javascript
a.holder
// 'Kirk'
a.balance
// 0
```

Functions that operate on the object or perform object-specific computations are called *methods*. The return values and side effects of a method can depend upon and change other attributes of the object. For example, `deposit` is a method of our `Account` object `a`. It takes one argument, the amount to deposit, changes the `balance` attribute of the object, and returns the resulting balance.

```javascript
a.deposit(15)
// 15
```

We say that methods are *invoked* on a particular object. As a result of invoking the `withdraw` method, either the withdrawal is approved and the amount is deducted, or the request is declined and the method returns an error message.

```javascript
a.withdraw(10)  // The withdraw method returns the balance after withdrawal
// 5
a.balance       // The balance attribute has changed
// 5
a.withdraw(10)
// 'Insufficient funds'
```

As illustrated above, the behavior of a method can depend upon the changing attributes of the object. Two calls to `withdraw` with the same argument return different results.

### 2.5.2 Defining Classes

User-defined classes are created using the `class` keyword. A class declaration defines the class name and a body enclosed in curly braces that contains the class's methods:

```javascript
class <Name> {
  // class body
}
```

When a class declaration is evaluated, a new class is created and bound to `<Name>` in the current scope. The class body typically contains a `constructor` method for initializing new instances, along with other method definitions.

Classes are organized around manipulating instance attributes -- the name-value pairs associated with each instance of that class. The class specifies the instance attributes of its objects by defining a `constructor` method for initializing new objects. For example, part of initializing an object of the `Account` class is to assign it a starting balance of `0`.

```javascript
class Account {
  constructor(accountHolder) {
    this.balance = 0;
    this.holder = accountHolder;
  }
}
```

The `constructor` for `Account` has one formal parameter: `accountHolder`, which is bound to the argument passed when creating a new instance. Inside the constructor, `this` refers to the newly created `Account` object. The constructor assigns the instance attribute `balance` to `0` and the attribute `holder` to the value of `accountHolder`.

**Key difference from Python:** In Python, the constructor is called `__init__` and explicitly takes `self` as the first parameter. In JavaScript, the constructor is named `constructor` and `this` is implicit -- you never pass it as a parameter, but you must be careful with arrow functions, which do not bind their own `this`.

Having defined the `Account` class, we can instantiate it.

```javascript
const a = new Account('Kirk');
```

This call creates a new object that is an instance of `Account`, then runs the `constructor` with `this` bound to the new object and `'Kirk'` as the argument. By convention, `this` always refers to the object being operated on inside a method. Note the mandatory `new` keyword -- without it, the class call will throw an error (in strict mode) or produce unexpected behavior.

Now, we can access the object's `balance` and `holder` using dot notation.

```javascript
a.balance
// 0
a.holder
// 'Kirk'
```

**Identity.** Each new account instance has its own `balance` attribute, the value of which is independent of other objects of the same class.

```javascript
const b = new Account('Spock');
b.balance = 200;
[a.balance, b.balance]
// [0, 200]
```

To enforce this separation, every object that is an instance of a user-defined class has a unique identity. Object identity is compared using the `===` and `!==` operators, or more precisely with `Object.is()`.

```javascript
a === a
// true
a !== b
// true
```

Despite being constructed from identical calls, the objects bound to `a` and `b` are not the same. As usual, binding an object to a new name using assignment does not create a new object.

```javascript
const c = a;
c === a
// true
```

New objects that have user-defined classes are only created when a class (such as `Account`) is instantiated with `new`.

**Methods.** Object methods are defined in the class body without the `function` keyword. Below, `deposit` and `withdraw` are both defined as methods on objects of the `Account` class.

```javascript
class Account {
  constructor(accountHolder) {
    this.balance = 0;
    this.holder = accountHolder;
  }
  deposit(amount) {
    this.balance = this.balance + amount;
    return this.balance;
  }
  withdraw(amount) {
    if (amount > this.balance) {
      return 'Insufficient funds';
    }
    this.balance = this.balance - amount;
    return this.balance;
  }
}
```

Each method has access to the object via `this`, which is automatically bound to the object on which the method is invoked. When we call `spockAccount.deposit(100)`, `this` is bound to `spockAccount` and `amount` is bound to `100`. All invoked methods have access to the object via `this`, and so they can all access and manipulate the object's state.

**Warning about `this` and arrow functions:** Arrow functions (`=>`) do not bind their own `this`. If you use an arrow function as a method, `this` will refer to the enclosing scope, not the object. Always use regular method syntax (shorthand method syntax without `function`) in class bodies.

```javascript
// WRONG - arrow function as method loses 'this'
class Bad {
  value = 42;
  getValue = () => this.value;  // This works, but is an instance field, not a method
}

// CORRECT - shorthand method syntax
class Good {
  constructor() { this.value = 42; }
  getValue() { return this.value; }  // 'this' correctly refers to the instance
}
```

To invoke these methods, we use dot notation:

```javascript
const spockAccount = new Account('Spock');
spockAccount.deposit(100)
// 100
spockAccount.withdraw(90)
// 10
spockAccount.withdraw(90)
// 'Insufficient funds'
spockAccount.holder
// 'Spock'
```

When a method is invoked via dot notation, the object itself (bound to `spockAccount`, in this case) plays a dual role. First, it determines what the name `withdraw` means -- `withdraw` is not a name in the global scope, but instead a name defined in the `Account` class. Second, the object is bound to `this` when the `withdraw` method is invoked.

### 2.5.3 Message Passing and Dot Expressions

Methods, which are defined in classes, and instance attributes, which are typically assigned in constructors, are the fundamental elements of object-oriented programming. These two concepts replicate much of the behavior of a dispatch dictionary in a message passing implementation of a data value. Objects take messages using dot notation, but instead of those messages being arbitrary string-valued keys, they are names local to a class. Objects also have named local state values (the instance attributes), but that state can be accessed and manipulated using dot notation directly.

The central idea in message passing was that data values should have behavior by responding to messages that are relevant to the abstract type they represent. Dot notation is a syntactic feature of JavaScript that formalizes the message passing metaphor. The advantage of using a language with a built-in object system is that message passing can interact seamlessly with other language features, such as assignment statements. We do not require different messages to "get" or "set" the value associated with a local attribute name; the language syntax allows us to use the name directly.

**Dot expressions.** The code fragment `spockAccount.deposit` is called a *dot expression*. A dot expression consists of an expression, a dot, and a name:

```
<expression>.<name>
```

The `<expression>` can be any valid JavaScript expression that evaluates to an object, and `<name>` must be a valid identifier. A dot expression evaluates to the value of the attribute with the given name, for the object that is the value of the expression.

JavaScript also provides bracket notation for accessing attributes by string, similar to Python's `getattr`:

```javascript
spockAccount['balance']
// 10
```

We can also test whether an object has a named attribute using the `in` operator or `hasOwnProperty`:

```javascript
'deposit' in spockAccount
// true
spockAccount.hasOwnProperty('balance')
// true
```

The attributes of an object include all of its instance attributes (own properties), along with all of the attributes (including methods) defined in its class and its prototype chain. Methods are attributes of the class prototype that require special handling.

**Methods and functions.** In JavaScript, when you access a method via dot notation, the method's `this` is automatically bound to the object on which it was accessed. However, if you extract a method and call it later, `this` binding can be lost:

```javascript
const depositFn = spockAccount.deposit;
// Calling depositFn(100) would fail because 'this' is undefined (strict mode)
// or the global object (non-strict mode)
```

To preserve `this` binding, use `.bind()`, an arrow function wrapper, or call the method directly:

```javascript
// Option 1: bind
const boundDeposit = spockAccount.deposit.bind(spockAccount);
boundDeposit(100);  // works correctly

// Option 2: arrow function wrapper
const depositViaArrow = (amount) => spockAccount.deposit(amount);
depositViaArrow(100);  // works correctly

// Option 3: call/apply
spockAccount.deposit.call(spockAccount, 100);
```

Unlike Python, which distinguishes between unbound functions and bound methods, JavaScript methods are simply functions stored on the prototype. The `this` binding is determined at call time based on how the function is called (the "call site"). This is one of the most important differences between Python and JavaScript OOP.

You can also call a method by referencing it through the class prototype and explicitly passing the object as `this`:

```javascript
Account.prototype.deposit.call(spockAccount, 1001)
// 1011
```

This is roughly equivalent to calling `Account.deposit(spockAccount, 1001)` in Python, though the mechanism is different.

**Naming conventions.** Class names are conventionally written using PascalCase (also called UpperCamelCase). Method names follow the convention of using camelCase. This differs from Python, which uses `snake_case` for method names.

In some cases, there are instance variables and methods that are related to the maintenance and consistency of an object that we do not want users of the object to see or use. They are not part of the abstraction defined by a class, but instead part of the implementation. JavaScript does not enforce true private members by default, but the convention is to prefix internal attributes with an underscore (`_`). JavaScript also supports truly private class fields and methods with the `#` prefix:

```javascript
class Account {
  #balance;  // truly private field

  constructor(accountHolder) {
    this.#balance = 0;
    this.holder = accountHolder;
  }

  // Private method
  #validateAmount(amount) {
    return amount > 0;
  }

  deposit(amount) {
    if (this.#validateAmount(amount)) {
      this.#balance += amount;
    }
    return this.#balance;
  }

  get balance() {
    return this.#balance;
  }
}
```

### 2.5.4 Class Attributes

Some attribute values are shared across all objects of a given class. Such attributes are associated with the class itself, rather than any individual instance of the class. For instance, let us say that a bank pays interest on the balance of accounts at a fixed interest rate. That interest rate may change, but it is a single value shared across all accounts.

In JavaScript, class attributes are defined using `static` keyword or by assigning properties directly on the class. In the broader developer community, class attributes may also be called *class variables* or *static properties*.

```javascript
class Account {
  static interest = 0.02;  // A class (static) attribute

  constructor(accountHolder) {
    this.balance = 0;
    this.holder = accountHolder;
  }
  // Additional methods would be defined here
}
```

This attribute can be accessed from the class itself, and also from any instance via the prototype chain:

```javascript
const spockAccount = new Account('Spock');
const kirkAccount = new Account('Kirk');
spockAccount.constructor.interest
// 0.02
kirkAccount.constructor.interest
// 0.02

// More commonly, access directly on the class:
Account.interest
// 0.02
```

However, a single assignment statement to the class attribute changes the value for all instances:

```javascript
Account.interest = 0.04;
spockAccount.constructor.interest
// 0.04
kirkAccount.constructor.interest
// 0.04
```

**Note on instance access to static properties:** Unlike Python, where `spockAccount.interest` automatically falls through to the class attribute, in JavaScript, accessing a static property on an instance does *not* work directly with dot notation. You must use `Account.interest` or `this.constructor.interest`. However, static methods are accessible via the prototype chain when called properly.

**Attribute lookup.** We have introduced enough complexity into our object system that we must specify how names are resolved to particular attributes. After all, we could easily have a class attribute and an instance attribute with the same name.

To evaluate a dot expression `<expression>.<name>`:

1. Evaluate the `<expression>` to the left of the dot, which yields the *object* of the dot expression.
2. `<name>` is matched against the instance's own properties; if a property with that name exists, its value is returned.
3. If `<name>` does not appear among the instance's own properties, then `<name>` is looked up in the object's prototype chain (which includes the class), which may yield a class attribute value.
4. That value is returned unless it is a function, in which case a method call is performed with `this` bound to the object.

In this evaluation procedure, instance attributes (own properties) are found before class attributes (prototype properties), just as local names have priority over global in a scope. The procedure for looking up a name in the prototype chain has additional nuances that will arise once we introduce class inheritance.

**Attribute assignment.** All assignment statements that contain a dot expression on their left-hand side affect attributes for the object of that dot expression. If the object is an instance, then assignment sets an instance attribute. If the object is a class, then assignment sets a class attribute. As a consequence of this rule, assignment to an attribute of an object cannot affect the attributes of its class. The examples below illustrate this distinction.

If we assign to the named attribute `interest` of an account instance, we create a new instance attribute that has the same name as the existing class attribute.

```javascript
kirkAccount.interest = 0.08;
```

And that attribute value will be returned from a dot expression on that instance:

```javascript
kirkAccount.interest
// 0.08
```

However, the class attribute `interest` still retains its original value, which is returned for all other accounts:

```javascript
spockAccount.constructor.interest
// 0.04
```

Changes to the class attribute `interest` will affect `spockAccount` (via the prototype chain), but the instance attribute for `kirkAccount` will be unaffected:

```javascript
Account.interest = 0.05;           // changing the class attribute
spockAccount.constructor.interest   // falls through to class attribute
// 0.05
kirkAccount.interest                // uses its own instance attribute
// 0.08
```

### 2.5.5 Inheritance

When working in the object-oriented programming paradigm, we often find that different types are related. In particular, we find that similar classes differ in their amount of specialization. Two classes may have similar attributes, but one represents a special case of the other.

For example, we may want to implement a checking account, which is different from a standard account. A checking account charges an extra $1 for each withdrawal and has a lower interest rate. Here, we demonstrate the desired behavior:

```javascript
const ch = new CheckingAccount('Spock');
ch.interest        // Lower interest rate for checking accounts
// 0.01
ch.deposit(20)     // Deposits are the same
// 20
ch.withdraw(5)     // Withdrawals decrease balance by an extra charge
// 14
```

A `CheckingAccount` is a specialization of an `Account`. In OOP terminology, the generic account will serve as the *base class* (or *superclass* / *parent class*) of `CheckingAccount`, while `CheckingAccount` will be a *subclass* (or *child class*) of `Account`.

A subclass *inherits* the attributes of its base class, but may *override* certain attributes, including certain methods. With inheritance, we only specify what is different between the subclass and the base class. Anything that we leave unspecified in the subclass is automatically assumed to behave just as it would for the base class.

Inheritance also has a role in our object metaphor, in addition to being a useful organizational feature. Inheritance is meant to represent *is-a* relationships between classes, which contrast with *has-a* relationships. A checking account *is-a* specific type of account, so having a `CheckingAccount` inherit from `Account` is an appropriate use of inheritance. On the other hand, a bank *has-a* list of bank accounts that it manages, so neither should inherit from the other. Instead, a list of account objects would be naturally expressed as an instance attribute of a bank object.

### 2.5.6 Using Inheritance

First, we give a full implementation of the `Account` class:

```javascript
class Account {
  /** A bank account that has a non-negative balance. */
  static interest = 0.02;

  constructor(accountHolder) {
    this.balance = 0;
    this.holder = accountHolder;
  }

  /** Increase the account balance by amount and return the new balance. */
  deposit(amount) {
    this.balance = this.balance + amount;
    return this.balance;
  }

  /** Decrease the account balance by amount and return the new balance. */
  withdraw(amount) {
    if (amount > this.balance) {
      return 'Insufficient funds';
    }
    this.balance = this.balance - amount;
    return this.balance;
  }
}
```

A full implementation of `CheckingAccount` appears below. We specify inheritance using the `extends` keyword:

```javascript
class CheckingAccount extends Account {
  /** A bank account that charges for withdrawals. */
  static withdrawCharge = 1;
  static interest = 0.01;

  withdraw(amount) {
    return super.withdraw(amount + CheckingAccount.withdrawCharge);
  }
}
```

Here, we introduce a static property `withdrawCharge` that is specific to the `CheckingAccount` class. We assign a lower value to the `interest` static property. We also define a new `withdraw` method to override the behavior defined in the `Account` class. With no further definitions in the class body, all other behavior is inherited from the base class `Account`.

**Key difference from Python:** Python calls the base class method as `Account.withdraw(self, amount + ...)`, explicitly passing `self`. JavaScript uses `super.withdraw(amount + ...)` which automatically binds `this` correctly.

```javascript
const checking = new CheckingAccount('Sam');
checking.deposit(10)
// 10
checking.withdraw(5)
// 4
checking.constructor.interest
// 0.01
```

The expression `checking.deposit` evaluates to a method for making deposits, which was defined in the `Account` class. When JavaScript resolves a name in a dot expression that is not an own property of the instance, it looks up the name in the prototype chain. We can define this procedure recursively. To look up a name for an object:

1. If it names an own property of the object, return the property value.
2. Otherwise, look up the name in the object's prototype (its class), and then recursively in the prototype's prototype (the base class), if there is one.

In the case of `deposit`, JavaScript would have looked for the name first on the instance, then in the `CheckingAccount` class prototype. Finally, it would look in the `Account` class prototype, where `deposit` is defined. Since `deposit` is a function looked up in the prototype chain for the `checking` instance, calling it binds `this` to the `checking` object.

The class of an object stays constant throughout. Even though the `deposit` method was found in the `Account` class, `deposit` is called with `this` bound to an instance of `CheckingAccount`, not of `Account`.

**Calling ancestors.** Attributes that have been overridden are still accessible via `super`. For instance, we implemented the `withdraw` method of `CheckingAccount` by calling `super.withdraw` with an argument that included the `withdrawCharge`.

Notice that we used `CheckingAccount.withdrawCharge` rather than `this.withdrawCharge`. Since `withdrawCharge` is a static property, we reference it through the class directly. In methods that might be further subclassed, you could also use `this.constructor.withdrawCharge` to allow subclasses to override the charge.

**Interfaces.** It is extremely common in object-oriented programs that different types of objects will share the same attribute names. An *object interface* is a collection of attributes and conditions on those attributes. For example, all accounts must have `deposit` and `withdraw` methods that take numerical arguments, as well as a `balance` attribute. The classes `Account` and `CheckingAccount` both implement this interface. Inheritance specifically promotes name sharing in this way. In some programming languages such as Java and TypeScript, interface implementations must be explicitly declared. In JavaScript, any object with the appropriate names implements an interface (this is called *duck typing*).

The parts of your program that use objects (rather than implementing them) are most robust to future changes if they do not make assumptions about object types, but instead only about their attribute names. That is, they use the object abstraction, rather than assuming anything about its implementation.

For example, let us say that we run a lottery, and we wish to deposit $5 into each of a list of accounts. The following implementation does not assume anything about the types of those accounts, and therefore works equally well with any type of object that has a `deposit` method:

```javascript
function depositAll(winners, amount = 5) {
  for (const account of winners) {
    account.deposit(amount);
  }
}
```

The function `depositAll` above assumes only that each account satisfies the account object abstraction, and so it will work with any other account classes that also implement this interface. Assuming a particular class of account would violate the abstraction barrier:

```javascript
// AVOID THIS - it only works with Account, not subclasses that override deposit
function depositAll(winners, amount = 5) {
  for (const account of winners) {
    Account.prototype.deposit.call(account, amount);
  }
}
```

We will address this topic in more detail later in the chapter.

**Type checking.** Python's `isinstance(x, T)` corresponds to JavaScript's `instanceof` operator. Python's `type(x)` corresponds to JavaScript's `x.constructor` or `typeof x`:

```javascript
checking instanceof CheckingAccount
// true
checking instanceof Account
// true
checking.constructor
// [class CheckingAccount extends Account]
typeof checking
// 'object'
```

### 2.5.7 Multiple Inheritance

Python supports the concept of a subclass inheriting attributes from multiple base classes, a language feature called *multiple inheritance*. **JavaScript does not support multiple inheritance natively** -- a class can only `extend` one base class. However, the same goals can be achieved using the **mixin pattern**.

First, let us look at the Python example. Suppose that we have a `SavingsAccount` that inherits from `Account`, but charges customers a small fee every time they make a deposit:

```python
# Python version (for reference)
class SavingsAccount(Account):
    deposit_charge = 2
    def deposit(self, amount):
        return Account.deposit(self, amount - self.deposit_charge)
```

In JavaScript:

```javascript
class SavingsAccount extends Account {
  static depositCharge = 2;

  deposit(amount) {
    return super.deposit(amount - SavingsAccount.depositCharge);
  }
}
```

Then, a clever executive conceives of an `AsSeenOnTVAccount` with the best features of both `CheckingAccount` and `SavingsAccount`: withdrawal fees, deposit fees, and a low interest rate. In Python, this would use multiple inheritance:

```python
# Python version (for reference) - multiple inheritance
class AsSeenOnTVAccount(CheckingAccount, SavingsAccount):
    def __init__(self, account_holder):
        self.holder = account_holder
        self.balance = 1  # A free dollar!
```

**JavaScript approach: mixins.** Since JavaScript classes can only extend one base class, we use mixins to compose behavior from multiple sources. A mixin is a function that takes a base class and returns a new extended class:

```javascript
// Mixin that adds withdrawal fee behavior
const WithWithdrawFee = (Base) => class extends Base {
  static withdrawCharge = 1;

  withdraw(amount) {
    return super.withdraw(amount + this.constructor.withdrawCharge);
  }
};

// Mixin that adds deposit fee behavior
const WithDepositFee = (Base) => class extends Base {
  static depositCharge = 2;

  deposit(amount) {
    return super.deposit(amount - this.constructor.depositCharge);
  }
};

// Compose the mixins to create AsSeenOnTVAccount
class AsSeenOnTVAccount extends WithDepositFee(WithWithdrawFee(Account)) {
  constructor(accountHolder) {
    super(accountHolder);
    this.balance = 1;  // A free dollar!
  }
}

const suchADeal = new AsSeenOnTVAccount('John');
suchADeal.balance
// 1
suchADeal.deposit(20)    // $2 fee from WithDepositFee
// 19
suchADeal.withdraw(5)    // $1 fee from WithWithdrawFee
// 13
```

Each mixin is a function that takes a class and returns a new class that extends it with additional behavior. By chaining mixins, we can compose behavior from multiple sources. The order of mixin application matters -- mixins applied last are "closest" in the inheritance chain and their `super` calls will reach the next mixin in the chain.

**Another common mixin pattern -- Serializable:**

```javascript
// A mixin that adds serialization capability to any class
const Serializable = (Base) => class extends Base {
  toJSON() {
    const entries = Object.entries(this)
      .filter(([key]) => !key.startsWith('_'));
    return JSON.stringify(Object.fromEntries(entries));
  }

  static fromJSON(json) {
    const data = JSON.parse(json);
    return new this(data);  // 'this' in static context refers to the class
  }
};

class Person extends Serializable(Object) {
  constructor({ name, age }) {
    super();
    this.name = name;
    this.age = age;
  }
}

const alice = new Person({ name: 'Alice', age: 30 });
alice.toJSON()
// '{"name":"Alice","age":30}'
```

**Key takeaway:** JavaScript's single-inheritance model with mixins is simpler than Python's C3 Method Resolution Order (MRO) for multiple inheritance. While it cannot replicate every multiple inheritance scenario, it handles the vast majority of practical cases. The mixin pattern keeps the inheritance chain linear and predictable.

### 2.5.8 The Role of Objects

The JavaScript object system is designed to make data abstraction and message passing both convenient and flexible. The specialized syntax of classes, methods, inheritance, and dot expressions all enable us to formalize the object metaphor in our programs, which improves our ability to organize large programs.

In particular, we would like our object system to promote a *separation of concerns* among the different aspects of the program. Each object in a program encapsulates and manages some part of the program's state, and each class definition defines the functions that implement some part of the program's overall logic. Abstraction barriers enforce the boundaries between different aspects of a large program.

Object-oriented programming is particularly well-suited to programs that model systems that have separate but interacting parts. For instance, different users interact in a social network, different characters interact in a game, and different shapes interact in a physical simulation. When representing such systems, the objects in a program often map naturally onto objects in the system being modeled, and classes represent their types and relationships.

On the other hand, classes may not provide the best mechanism for implementing certain abstractions. Functional abstractions provide a more natural metaphor for representing relationships between inputs and outputs. One should not feel compelled to fit every bit of logic in a program within a class, especially when defining independent functions for manipulating data is more natural. Functions can also enforce a separation of concerns.

Multi-paradigm languages such as JavaScript allow programmers to match organizational paradigms to appropriate problems. Learning to identify when to introduce a new class, as opposed to a new function, in order to simplify or modularize a program, is an important design skill in software engineering that deserves careful attention.

## Python vs JavaScript Notes

| Concept | Python | JavaScript |
|---|---|---|
| Define a class | `class MyClass:` | `class MyClass { }` |
| Constructor | `def __init__(self, args):` | `constructor(args) { }` |
| Reference to instance | `self` (explicit first param) | `this` (implicit, no param needed) |
| Create an instance | `obj = MyClass(args)` | `const obj = new MyClass(args)` |
| Instance attribute | `self.attr = value` | `this.attr = value` |
| Method definition | `def method(self, args):` | `method(args) { }` |
| Class attribute | `class C: attr = val` (in class body) | `static attr = val` |
| Class method | `@classmethod def f(cls):` | `static f() { }` |
| Property getter | `@property def x(self):` | `get x() { }` |
| Property setter | `@x.setter def x(self, v):` | `set x(v) { }` |
| Inheritance | `class Sub(Base):` | `class Sub extends Base { }` |
| Call parent method | `super().method(args)` or `Base.method(self, args)` | `super.method(args)` |
| Call parent constructor | `super().__init__(args)` | `super(args)` |
| Multiple inheritance | `class C(A, B):` | Not supported; use mixins |
| Mixin pattern | N/A (use multiple inheritance) | `const M = (Base) => class extends Base { }; class C extends M(Base) { }` |
| Check type | `isinstance(x, T)` | `x instanceof T` |
| Get class/type | `type(x)` | `x.constructor` or `typeof x` |
| Check attribute exists | `hasattr(obj, 'name')` | `'name' in obj` |
| Get attribute by string | `getattr(obj, 'name')` | `obj['name']` |
| Private convention | `_name` (convention), `__name` (name mangling) | `_name` (convention), `#name` (truly private) |
| Method naming | `snake_case` | `camelCase` |
| Arrow functions and `this` | N/A | Arrow functions (`=>`) do NOT bind `this`; use regular methods in classes |
| Identity comparison | `a is b` | `a === b` or `Object.is(a, b)` |
