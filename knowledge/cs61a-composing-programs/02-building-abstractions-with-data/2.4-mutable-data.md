## Key Concepts

- **Mutable data** allows a single data object to change state over time, enabling modular programs where objects evolve independently of the rest of the program.
- **Sequence mutation** in JavaScript uses `push`, `pop`, `splice`, and index assignment to modify arrays in place, unlike immutable operations that create new arrays.
- **Objects as dictionaries** (plain JS objects or `Map`) store key-value pairs and support dynamic addition, update, and lookup of entries.
- **Local state via closures** uses `let` bindings captured by inner functions to maintain private mutable state across calls -- the JavaScript equivalent of Python's `nonlocal`.
- **Dispatch dictionaries** (plain objects with function values) implement message-passing interfaces, a stepping stone toward full object-oriented programming.
- **Referential transparency** is broken by non-local assignment: expressions with mutable state can return different values when called multiple times with the same arguments.

## Content

### 2.4.1 The Object Metaphor

Objects combine data values with behavior. Objects represent information, but also *behave* like the things that they represent. The logic of how an object interacts with other objects is bundled along with the information that encodes the object's value. When an object is printed, it knows how to spell itself out in text. If an object is composed of parts, it knows how to reveal those parts on demand. Objects are both information and processes, bundled together to represent the properties, interactions, and behaviors of complex things.

JavaScript, more than Python, is fundamentally object-oriented: nearly every value is an object or behaves like one. A `Date` is a kind of object:

```javascript
const tues = new Date(2014, 4, 13);  // Month is 0-indexed: 4 = May
```

While `tues` was constructed from primitive numbers, it behaves like a date. For instance, subtracting it from another date gives a time difference in milliseconds:

```javascript
const diff = new Date(2014, 4, 19) - tues;
// diff is 518400000 (milliseconds)
// To get a human-readable Duration-like result:
const days = diff / (1000 * 60 * 60 * 24);  // 6
```

Objects have **properties**, which are named values that are part of the object. In JavaScript, we use dot notation (or bracket notation) to designate a property of an object:

```
<expression>.<name>
```

Above, the `<expression>` evaluates to an object, and `<name>` is the name of a property for that object.

```javascript
tues.getFullYear();  // 2014
tues.getMonth();     // 4 (May, since months are 0-indexed)
tues.getDate();      // 13
```

Objects also have **methods**, which are function-valued properties. Metaphorically, we say that the object "knows" how to carry out those methods. By implementation, methods are functions that compute their results from both their arguments and their object. For example, the `toLocaleDateString` method of `tues` takes options that specify how to display a date:

```javascript
tues.toLocaleDateString('en-US', { weekday: 'long', year: 'numeric', month: 'long', day: 'numeric' });
// 'Tuesday, May 13, 2014'
```

Computing the return value of `toLocaleDateString` requires two inputs: the options that describe the format of the output and the date information bundled into `tues`. Date-specific logic is applied within this method to yield this result. We never stated that the 13th of May, 2014, was a Tuesday, but knowing the corresponding weekday is part of what it means to be a date. By bundling behavior and information together, this JavaScript object offers us a convincing, self-contained abstraction of a date.

Dates are objects, but numbers, strings, arrays, and functions are all objects as well in JavaScript. They represent values, but also behave in a manner that befits the values they represent. They also have properties and methods. For instance, strings have an array of methods that facilitate text processing:

```javascript
'1234'.match(/^\d+$/) !== null;        // true (is numeric)
'rOBERT dE nIRO'.replace(/./g, c =>    // 'Robert De Niro'
  c === c.toUpperCase() ? c.toLowerCase() : c.toUpperCase()
);
'eyes'.toUpperCase().endsWith('YES');   // true
```

In JavaScript, all values except `null` and `undefined` behave as objects in the sense that they have properties and methods (primitives are auto-boxed when you access properties on them). They act like the values they represent.

### 2.4.2 Sequence Objects

Instances of primitive built-in values such as numbers and strings are **immutable**. The values themselves cannot change over the course of program execution. Arrays, on the other hand, are **mutable**.

Mutable objects are used to represent values that change over time. A person is the same person from one day to the next, despite having aged, received a haircut, or otherwise changed in some way. Similarly, an object may have changing properties due to **mutating** operations. For example, it is possible to change the contents of an array. Most changes are performed by calling methods on array objects.

We can introduce many array modification operations through an example that illustrates the history of playing cards (drastically simplified). Comments in the examples describe the effect of each method invocation.

Playing cards were invented in China, perhaps around the 9th century. An early deck had three suits, which corresponded to denominations of money.

```javascript
const chinese = ['coin', 'string', 'myriad'];  // An array literal
let suits = chinese;                            // Two names refer to the same array
```

As cards migrated to Europe (perhaps through Egypt), only the suit of coins remained in Spanish decks (*oro*).

```javascript
suits.pop();                   // Remove and return the final element: 'myriad'
suits.splice(suits.indexOf('string'), 1);  // Remove 'string' by value
```

Three more suits were added (they evolved in name and design over time):

```javascript
suits.push('cup');                          // Add an element to the end
suits.push('sword', 'club');                // Add multiple elements to the end
// Note: Python's extend adds all elements of a sequence.
// JavaScript's push accepts multiple arguments.
```

And Italians called swords *spades*.

```javascript
suits[2] = 'spade';  // Replace an element
```

Giving the suits of a traditional Italian deck of cards:

```javascript
suits;  // ['coin', 'cup', 'spade', 'club']
```

The French variant used today in the U.S. changes the first two suits:

```javascript
suits.splice(0, 2, 'heart', 'diamond');  // Replace elements at indices 0..1
suits;  // ['heart', 'diamond', 'spade', 'club']
```

Methods also exist for sorting and reversing arrays. All of these mutation operations change the value of the array; they do not create new array objects.

**Sharing and Identity.** Because we have been changing a single array rather than creating new arrays, the object bound to the name `chinese` has also changed, because it is the same array object that was bound to `suits`!

```javascript
chinese;  // ['heart', 'diamond', 'spade', 'club']
// This name co-refers with "suits" to the same changing array
```

This behavior is new. Previously, if a name did not appear in a statement, then its value would not be affected by that statement. With mutable data, methods called on one name can affect another name at the same time.

Arrays can be copied using `slice()` or the spread syntax. Changes to one array do not affect another, unless they share structure.

```javascript
const nest = [...suits];  // Bind "nest" to a new array with the same elements
nest[0] = suits;          // Create a nested array
```

According to this arrangement, changing the array referenced by `suits` will affect the nested array that is the first element of `nest`, but not the other elements.

```javascript
suits.splice(2, 0, 'Joker');  // Insert 'Joker' at index 2, shifting the rest
nest;
// [['heart', 'diamond', 'Joker', 'spade', 'club'], 'diamond', 'spade', 'club']
```

And likewise, undoing this change in the first element of `nest` will change `suits` as well.

```javascript
nest[0].splice(2, 1)[0];  // Remove and return the element at index 2: 'Joker'
suits;  // ['heart', 'diamond', 'spade', 'club']
```

Because two arrays may have the same contents but in fact be different arrays, we require a means to test whether two objects are the same. JavaScript uses `===` to test reference identity (whether two expressions evaluate to the identical object in memory). Two objects are identical if they are equal in their current value, and any change to one will always be reflected in the other. Identity is a stronger condition than equality.

```javascript
suits === nest[0];                          // true  (same object)
suits === ['heart', 'diamond', 'spade', 'club'];  // false (different object, same contents)
// To compare contents:
suits.length === 4 &&
  suits.every((v, i) => v === ['heart', 'diamond', 'spade', 'club'][i]);  // true
```

The final comparison illustrates the difference between `===` and deep equality. The former checks for identity (same reference), while the latter checks for equality of contents.

**Array comprehensions.** `Array.prototype.map` always creates a new array. For example, we can create an array of Unicode suit symbols:

```javascript
// Python: [lookup('WHITE ' + s.upper() + ' SUIT') for s in suits]
// JavaScript:
const suitSymbols = { heart: '♡', diamond: '♢', spade: '♤', club: '♧' };
suits.map(s => suitSymbols[s]);  // ['♡', '♢', '♤', '♧']
// i.e., ['♡', '♢', '♤', '♧']
```

This resulting array does not share any of its contents with `suits`, and evaluating the `map` does not modify the `suits` array.

**Immutable sequences.** JavaScript does not have a built-in tuple type. However, you can create immutable arrays using `Object.freeze`:

```javascript
const code = Object.freeze(['up', 'up', 'down', 'down',
  ...'left right '.repeat(2).trim().split(' ')]);
// ['up', 'up', 'down', 'down', 'left', 'right', 'left', 'right']

code.length;       // 8
code[3];           // 'down'
code.filter(x => x === 'down').length;  // 2 (count occurrences)
code.indexOf('left');  // 4

code.push('up');   // TypeError: Cannot add property... object is not extensible
```

While it is not possible to change which elements are in a frozen array, if an element is itself a mutable object (like a nested array), that element's contents can still be changed. To create a deep freeze, you would need to recursively freeze all nested objects.

### 2.4.3 Dictionaries

JavaScript objects (and the `Map` type) serve as built-in data structures for storing and manipulating correspondence relationships. An object contains key-value pairs, where both the keys and values can be of various types. The purpose of a dictionary is to provide an abstraction for storing and retrieving values that are indexed not by consecutive integers, but by descriptive keys.

Strings commonly serve as keys, because strings are our conventional representation for names of things. This object literal gives the values of various Roman numerals:

```javascript
const numerals = { I: 1, V: 5, X: 10 };
```

Looking up values by their keys uses bracket notation (or dot notation for valid identifiers):

```javascript
numerals['X'];  // 10
numerals.X;     // 10
```

An object can have at most one value for each key. Adding new key-value pairs and changing the existing value for a key can both be achieved with assignment statements:

```javascript
numerals['I'] = 1;
numerals['L'] = 50;
numerals;  // { I: 1, V: 5, X: 10, L: 50 }
// Note: JavaScript preserves insertion order for object keys
```

The object type also supports various methods of iterating over the contents:

```javascript
// Python: sum(numerals.values())
// JavaScript:
Object.values(numerals).reduce((a, b) => a + b, 0);  // 66
```

An array of key-value pairs can be converted into an object using `Object.fromEntries`:

```javascript
// Python: dict([(3, 9), (4, 16), (5, 25)])
// JavaScript:
Object.fromEntries([[3, 9], [4, 16], [5, 25]]);
// { 3: 9, 4: 16, 5: 25 }
```

JavaScript objects do have some restrictions compared to Python dictionaries:

- Keys are automatically converted to strings (or Symbols). Use `Map` if you need non-string keys.
- There can be at most one value for a given key.

A useful pattern implemented by objects is the `||` or `??` operator for default values, analogous to Python's `dict.get`:

```javascript
// Python: numerals.get('A', 0)
// JavaScript:
numerals['A'] ?? 0;  // 0 (nullish coalescing)
numerals['V'] ?? 0;  // 5
```

Objects also support a comprehension-like pattern using `Object.fromEntries`:

```javascript
// Python: {x: x*x for x in range(3,6)}
// JavaScript:
Object.fromEntries([3, 4, 5].map(x => [x, x * x]));
// { 3: 9, 4: 16, 5: 25 }
```

**Using `Map`.** When you need keys that are not strings, or when you need to frequently add and remove entries, JavaScript's `Map` type is more appropriate:

```javascript
const m = new Map();
m.set('I', 1);
m.set('V', 5);
m.set('X', 10);
m.get('X');    // 10
m.has('A');    // false
m.get('A');    // undefined
m.size;        // 3
m.delete('V'); // true
```

### 2.4.4 Local State

Arrays and objects have *local state*: they are changing values that have some particular contents at any point in the execution of a program. The word "state" implies an evolving process in which that state may change.

Functions can also have local state. For instance, let us define a function that models the process of withdrawing money from a bank account. We will create a function called `withdraw`, which takes as its argument an amount to be withdrawn. If there is enough money in the account to accommodate the withdrawal, then `withdraw` will return the balance remaining after the withdrawal. Otherwise, `withdraw` will return the message `'Insufficient funds'`. For example, if we begin with $100 in the account, we would like to obtain the following sequence of return values by calling `withdraw`:

```javascript
withdraw(25);   // 75
withdraw(25);   // 50
withdraw(60);   // 'Insufficient funds'
withdraw(15);   // 35
```

Above, the expression `withdraw(25)`, evaluated twice, yields different values. Thus, this user-defined function is non-pure. Calling the function not only returns a value, but also has the side effect of changing the function in some way, so that the next call with the same argument will return a different result. This side effect is a result of `withdraw` making a change to a name-value binding outside of the current scope.

For `withdraw` to make sense, it must be created with an initial account balance. The function `makeWithdraw` is a higher-order function that takes a starting balance as an argument. The function `withdraw` is its return value.

```javascript
const withdraw = makeWithdraw(100);
```

An implementation of `makeWithdraw` uses `let` to create a mutable binding captured by a closure. When we call `makeWithdraw`, we bind the name `balance` to the initial amount. We then define and return a local function, `withdraw`, which updates and returns the value of `balance` when called.

```javascript
function makeWithdraw(balance) {
  /** Return a withdraw function that draws down balance with each call. */
  return function withdraw(amount) {
    if (amount > balance) {
      return 'Insufficient funds';
    }
    balance = balance - amount;  // Re-bind the existing balance name (let, not const)
    return balance;
  };
}
```

In JavaScript, `let` (and `var`) declarations create mutable bindings in their enclosing scope. When an inner function references a `let` variable from an outer scope, it forms a **closure** that captures a reference to that variable. Reassigning `balance` inside the inner function changes the binding in the `makeWithdraw` scope. This is the default behavior in JavaScript -- no special declaration is needed, unlike Python's `nonlocal` statement.

Contrast this with `const`, which creates an immutable binding. If we used `const balance`, the reassignment `balance = balance - amount` would throw a `TypeError`.

The following example illustrates the effects of multiple calls to a function created by `makeWithdraw`:

```javascript
function makeWithdraw(balance) {
  return function withdraw(amount) {
    if (amount > balance) {
      return 'Insufficient funds';
    }
    balance = balance - amount;
    return balance;
  };
}

const wd = makeWithdraw(20);
wd(5);   // 15
wd(3);   // 12
```

The first call to `makeWithdraw` creates and returns a locally defined function `withdraw`. The name `balance` is bound in the parent scope of this function. Crucially, there will only be this single binding for the name `balance` throughout the rest of this example.

Next, we evaluate an expression that calls this function, bound to the name `wd`, on an amount 5. The body of `withdraw` is executed in a new scope that extends the scope in which `withdraw` was defined. The assignment `balance = balance - amount` finds the `balance` variable in the enclosing `makeWithdraw` scope and updates it.

By virtue of changing the binding for `balance`, we have changed the `withdraw` function as well. The next time it is called, the name `balance` will evaluate to 15 instead of 20. Hence, when we call `withdraw` a second time, we see that its return value is 12 and not 17. The change to `balance` from the first call affects the result of the second call.

**JavaScript Particulars.** This pattern of non-local assignment is a general feature of programming languages with higher-order functions and lexical scope. In JavaScript, `let` variables in an outer scope are automatically accessible and reassignable from inner functions -- no `nonlocal` statement is needed. This is the default behavior for `let` and `var` in JavaScript, unlike Python where the `nonlocal` keyword is required to rebind names in enclosing scopes.

However, `const` variables cannot be reassigned. If you need mutable state in a closure, you must use `let`:

```javascript
function makeWithdrawConst(balance) {
  // This would fail with const:
  // const balance = initialBalance;  // TypeError on reassignment!
  return function(amount) {
    if (amount > balance) return 'Insufficient funds';
    balance = balance - amount;  // Requires let, not const
    return balance;
  };
}
```

Another common pattern in JavaScript is to use a mutable container (like an object or array) with `const`, since `const` prevents reassignment of the binding but not mutation of the value:

```javascript
function makeWithdrawObj(initialBalance) {
  const state = { balance: initialBalance };
  return function(amount) {
    if (amount > state.balance) return 'Insufficient funds';
    state.balance = state.balance - amount;
    return state.balance;
  };
}
```

### 2.4.5 The Benefits of Non-Local Assignment

Non-local assignment is an important step on our path to viewing a program as a collection of independent and autonomous *objects*, which interact with each other but each manage their own internal state.

In particular, non-local assignment has given us the ability to maintain some state that is local to a function, but evolves over successive calls to that function. The balance associated with a particular `withdraw` function is shared among all calls to that function. However, the binding for `balance` associated with an instance of `withdraw` is inaccessible to the rest of the program. Only `wd` is associated with the scope for `makeWithdraw` in which it was defined. If `makeWithdraw` is called again, then it will create a separate scope with a separate binding for `balance`.

We can extend our example to illustrate this point. A second call to `makeWithdraw` returns a second `withdraw` function that has a different parent scope. We bind this second function to the name `wd2` in the global scope.

```javascript
function makeWithdraw(balance) {
  return function withdraw(amount) {
    if (amount > balance) {
      return 'Insufficient funds';
    }
    balance = balance - amount;
    return balance;
  };
}

const wd = makeWithdraw(20);
const wd2 = makeWithdraw(7);
wd2(6);   // 1
wd(8);    // 12
```

Now, we see that there are in fact two bindings for the name `balance` in two different scopes, and each `withdraw` function has a different enclosing scope. The name `wd` is bound to a function with a `balance` of 20, while `wd2` is bound to a different function with a `balance` of 7.

Calling `wd2` changes the binding of its `balance` variable, but does not affect the function bound to the name `wd`. A future call to `wd` is unaffected by the changing balance of `wd2`; its balance is still 20 (minus what was withdrawn).

In this way, each instance of `withdraw` maintains its own `balance` state, but that state is inaccessible to any other function in the program. Viewing this situation at a higher level, we have created an abstraction of a bank account that manages its own internals but behaves in a way that models accounts in the world: it changes over time based on its own history of withdrawal requests.

### 2.4.6 The Cost of Non-Local Assignment

Our scope model of computation cleanly extends to explain the effects of non-local assignment. However, non-local assignment introduces some important nuances in the way we think about names and values.

Previously, our values did not change; only our names and bindings changed. When two names `a` and `b` were both bound to the value 4, it did not matter whether they were bound to the same 4 or different 4's. As far as we could tell, there was only one 4 object that never changed.

However, functions with state do not behave this way. When two names `wd` and `wd2` are both bound to a `withdraw` function, it *does* matter whether they are bound to the same function or different instances of that function. Consider the following example, which contrasts the one we just analyzed. In this case, calling the function named by `wd2` did change the value of the function named by `wd`, because both names refer to the same function.

```javascript
function makeWithdraw(balance) {
  return function withdraw(amount) {
    if (amount > balance) {
      return 'Insufficient funds';
    }
    balance = balance - amount;
    return balance;
  };
}

const wd = makeWithdraw(12);
const wd2 = wd;   // wd2 refers to the SAME function as wd
wd2(1);  // 11
wd(1);   // 10
```

It is not unusual for two names to co-refer to the same value in the world, and so it is in our programs. But, as values change over time, we must be very careful to understand the effect of a change on other names that might refer to those values.

The key to correctly analyzing code with non-local assignment is to remember that only function calls introduce new scopes. Assignment statements always change bindings in existing scopes. In this case, unless `makeWithdraw` is called twice, there can be only one binding for `balance`.

**Sameness and change.** These subtleties arise because, by introducing non-pure functions that change the non-local environment, we have changed the nature of expressions. An expression that contains only pure function calls is *referentially transparent*; its value does not change if we substitute one of its subexpressions with the value of that subexpression.

Re-binding operations violate the conditions of referential transparency because they do more than return a value; they change the environment. When we introduce arbitrary re-binding, we encounter a thorny epistemological issue: what it means for two values to be the same. In our scope model of computation, two separately defined functions are not the same, because changes to one may not be reflected in the other.

In general, so long as we never modify data objects, we can regard a compound data object to be precisely the totality of its pieces. For example, a rational number is determined by giving its numerator and its denominator. But this view is no longer valid in the presence of change, where a compound data object has an "identity" that is something different from the pieces of which it is composed. A bank account is still "the same" bank account even if we change the balance by making a withdrawal; conversely, we could have two bank accounts that happen to have the same balance, but are different objects.

Despite the complications it introduces, non-local assignment is a powerful tool for creating modular programs. Different parts of a program, which correspond to different scope frames, can evolve separately throughout program execution. Moreover, using functions with local state, we are able to implement mutable data types. In fact, we can implement abstract data types that are equivalent to the built-in `Array` and `Object` types introduced above.

### 2.4.7 Implementing Lists and Dictionaries

The JavaScript language does not give us access to the implementation of arrays, only to the sequence abstraction and mutation methods built into the language. To understand how a mutable list could be represented using functions with local state, we will now develop an implementation of a mutable linked list.

We will represent a mutable linked list by a function that has a linked list as its local state. Lists need to have an identity, like any mutable value. In particular, we cannot use `null` to represent an empty mutable list, because two empty lists are not identical values (e.g., appending to one does not append to the other), but `null === null`. On the other hand, two different functions that each have `EMPTY` as their local state will suffice to distinguish two empty lists.

If a mutable linked list is a function, what arguments does it take? The answer exhibits a general pattern in programming: the function is a **dispatch function** and its arguments are first a message, followed by additional arguments to parameterize that method. This message is a string naming what the function should do. Dispatch functions are effectively many functions in one: the message determines the behavior of the function, and the additional arguments are used in that behavior.

Our mutable list will respond to five different messages: `len`, `getitem`, `pushFirst`, `popFirst`, and `str`. The first two implement the behaviors of the sequence abstraction. The next two add or remove the first element of the list. The final message returns a string representation of the whole linked list.

```javascript
function mutableLink() {
  /** Return a functional implementation of a mutable linked list. */
  let contents = null;  // EMPTY

  function dispatch(message, value) {
    if (message === 'len') {
      return lenLink(contents);
    } else if (message === 'getitem') {
      return getitemLink(contents, value);
    } else if (message === 'pushFirst') {
      contents = link(value, contents);
    } else if (message === 'popFirst') {
      const f = first(contents);
      contents = rest(contents);
      return f;
    } else if (message === 'str') {
      return joinLink(contents, ', ');
    }
  }
  return dispatch;
}
```

We can also add a convenience function to construct a functionally implemented linked list from any built-in sequence, simply by adding each element in reverse order.

```javascript
function toMutableLink(source) {
  /** Return a functional list with the same contents as source. */
  const s = mutableLink();
  for (let i = source.length - 1; i >= 0; i--) {
    s('pushFirst', source[i]);
  }
  return s;
}
```

At this point, we can construct functionally implemented mutable linked lists. Note that the linked list itself is a function.

```javascript
const suits = ['heart', 'diamond', 'spade', 'club'];
const s = toMutableLink(suits);
typeof s;           // 'function'
s('str');           // 'heart, diamond, spade, club'
```

In addition, we can pass messages to the list `s` that change its contents, for instance removing the first element.

```javascript
s('popFirst');      // 'heart'
s('str');           // 'diamond, spade, club'
```

In principle, the operations `pushFirst` and `popFirst` suffice to make arbitrary changes to a list. We can always empty out the list entirely and then replace its old contents with the desired result.

**Message passing.** Given some time, we could implement the many useful mutation operations of JavaScript arrays, such as `splice` and `concat`. We would have a choice: we could implement them all as functions, which use the existing messages `popFirst` and `pushFirst` to make all changes. Alternatively, we could add additional `else if` clauses to the body of `dispatch`, each checking for a message (e.g., `'extend'`) and applying the appropriate change to `contents` directly.

This second approach, which encapsulates the logic for all operations on a data value within one function that responds to different messages, is a discipline called **message passing**. A program that uses message passing defines dispatch functions, each of which may have local state, and organizes computation by passing "messages" as the first argument to those functions. The messages are strings that correspond to particular behaviors.

**Implementing Dictionaries.** We can also implement a value with similar behavior to a dictionary. In this case, we use an array of key-value pairs to store the contents of the dictionary. Each pair is a two-element array.

```javascript
function dictionary() {
  /** Return a functional implementation of a dictionary. */
  let records = [];

  function getitem(key) {
    const matches = records.filter(r => r[0] === key);
    if (matches.length === 1) {
      return matches[0][1];
    }
  }

  function setitem(key, value) {
    const nonMatches = records.filter(r => r[0] !== key);
    records = [...nonMatches, [key, value]];
  }

  function dispatch(message, key, value) {
    if (message === 'getitem') {
      return getitem(key);
    } else if (message === 'setitem') {
      setitem(key, value);
    }
  }
  return dispatch;
}
```

Again, we use the message passing method to organize our implementation. We have supported two messages: `getitem` and `setitem`. To insert a value for a key, we filter out any existing records with the given key, then add one. In this way, we are assured that each key appears only once in `records`. To look up a value for a key, we filter for the record that matches the given key. We can now use our implementation to store and retrieve values.

```javascript
const d = dictionary();
d('setitem', 3, 9);
d('setitem', 4, 16);
d('getitem', 3);   // 9
d('getitem', 4);   // 16
```

This implementation of a dictionary is *not* optimized for fast record lookup, because each call must filter through all records. The built-in `Object` and `Map` types are considerably more efficient. The way in which they are implemented (using hash tables) is beyond the scope of this text.

### 2.4.8 Dispatch Dictionaries

The dispatch function is a general method for implementing a message passing interface for abstract data. To implement message dispatch, we have thus far used conditional statements to compare the message string to a fixed set of known messages.

The built-in object type provides a general method for looking up a value for a key. Instead of using conditionals to implement dispatching, we can use objects with string keys.

The mutable account data type below is implemented as an object. It has a constructor `account` and selector `checkBalance`, as well as functions to deposit or withdraw funds. Moreover, the local state of the account is stored in the object alongside the functions that implement its behavior.

```javascript
function account(initialBalance) {
  function deposit(amount) {
    dispatch.balance += amount;
    return dispatch.balance;
  }

  function withdraw(amount) {
    if (amount > dispatch.balance) {
      return 'Insufficient funds';
    }
    dispatch.balance -= amount;
    return dispatch.balance;
  }

  const dispatch = {
    deposit: deposit,
    withdraw: withdraw,
    balance: initialBalance
  };

  return dispatch;
}

function withdrawFrom(acct, amount) {
  return acct.withdraw(amount);
}

function depositTo(acct, amount) {
  return acct.deposit(amount);
}

function checkBalance(acct) {
  return acct.balance;
}

const a = account(20);
depositTo(a, 5);       // 25
withdrawFrom(a, 17);   // 8
checkBalance(a);       // 8
```

The name `dispatch` within the body of the `account` constructor is bound to an object that contains the messages accepted by an account as keys. The *balance* is a number, while the messages *deposit* and *withdraw* are bound to functions. These functions have access to the `dispatch` object, and so they can read and change the balance. By storing the balance in the `dispatch` object rather than in a `let` variable in the `account` scope, we avoid the need for mutable `let` bindings in `deposit` and `withdraw` -- the object itself is mutated instead.

The operators `+=` and `-=` are shorthand in JavaScript (as in Python and many other languages) for combined lookup and re-assignment. The last two lines below are equivalent:

```javascript
let a = 2;
a = a + 1;  // 3
a += 1;     // 4
```

### 2.4.9 Propagating Constraints

Mutable data allows us to simulate systems with change, but also allows us to build new kinds of abstractions. In this extended example, we combine closures with mutable state, arrays, and objects to build a **constraint-based system** that supports computation in multiple directions. Expressing programs as constraints is a type of *declarative programming*, in which a programmer declares the structure of a problem to be solved, but abstracts away the details of exactly how the solution to the problem is computed.

Computer programs are traditionally organized as one-directional computations, which perform operations on pre-specified arguments to produce desired outputs. On the other hand, we often want to model systems in terms of relations among quantities. For example, the ideal gas law relates the pressure (p), volume (v), quantity (n), and temperature (t) of an ideal gas via Boltzmann's constant (k):

```
p * v = n * k * t
```

Such an equation is not one-directional. Given any four of the quantities, we can use this equation to compute the fifth. Yet translating the equation into a traditional computer language would force us to choose one of the quantities to be computed in terms of the other four.

In this section, we sketch a general model of linear relationships. We define primitive constraints that hold between quantities, such as an `adder(a, b, c)` constraint that enforces the mathematical relationship `a + b = c`.

We also define a means of combination, so that primitive constraints can be combined to express more complex relations. In this way, our program resembles a programming language. We combine constraints by constructing a network in which constraints are joined by **connectors**. A connector is an object that "holds" a value and may participate in one or more constraints.

For example, the relationship between Fahrenheit and Celsius temperatures is:

```
9 * c = 5 * (f - 32)
```

This equation is a complex constraint between `c` and `f`. Such a constraint can be thought of as a network consisting of primitive `adder`, `multiplier`, and `constant` constraints.

**Using the Constraint System.** To use the constraint system to carry out temperature computation, we first create two named connectors:

```javascript
const celsius = connector('Celsius');
const fahrenheit = connector('Fahrenheit');
```

Then, we link these connectors into a network:

```javascript
function converter(c, f) {
  /** Connect c to f with constraints to convert from Celsius to Fahrenheit. */
  const u = connector(), v = connector(), w = connector();
  const x = connector(), y = connector();
  multiplier(c, w, u);
  multiplier(v, x, u);
  adder(v, y, f);
  constant(w, 9);
  constant(x, 5);
  constant(y, 32);
}

converter(celsius, fahrenheit);
```

One message we can send to a connector is to set its value. Here, we (the "user") set the value of `celsius` to 25:

```javascript
celsius.setVal('user', 25);
// Celsius = 25
// Fahrenheit = 77
```

Not only does the value of `celsius` change to 25, but its value propagates through the network, and so the value of `fahrenheit` is changed as well.

Now we can try to set `fahrenheit` to a new value, say 212:

```javascript
fahrenheit.setVal('user', 212);
// Contradiction detected: 77 vs 212
```

The connector complains that it has sensed a contradiction: its value is 77, and someone is trying to set it to 212. If we really want to reuse the network with new values, we can tell `celsius` to forget its old value:

```javascript
celsius.forget('user');
// Celsius is forgotten
// Fahrenheit is forgotten
```

Now that `fahrenheit` has no value, we are free to set it to 212:

```javascript
fahrenheit.setVal('user', 212);
// Fahrenheit = 212
// Celsius = 100
```

This new value, when propagated through the network, forces `celsius` to have a value of 100. We have used the very same network to compute `celsius` given `fahrenheit` and to compute `fahrenheit` given `celsius`. This non-directionality of computation is the distinguishing feature of constraint-based systems.

**Implementing the Constraint System (Conceptual Overview).** Connectors are objects that map message names to function and data values. They respond to messages like `setVal`, `hasVal`, `forget`, and `connect`. Constraints are also objects, which receive information from connectors by means of messages like `newVal` and `forget`.

The `adder` function constructs an adder constraint over three connectors, where the first two must add to the third: `a + b = c`. To support multidirectional constraint propagation, the adder must also specify that it subtracts `a` from `c` to get `b`, and likewise subtracts `b` from `c` to get `a`.

Here is a simplified implementation sketch of the key pieces:

```javascript
// A ternary constraint factory
function makeTernaryConstraint(a, b, c, ab, ca, cb) {
  /** The constraint that ab(a,b)=c and ca(c,a)=b and cb(c,b)=a. */
  function newValue() {
    const av = a.hasVal(), bv = b.hasVal(), cv = c.hasVal();
    if (av && bv) {
      c.setVal(constraint, ab(a.val, b.val));
    } else if (av && cv) {
      b.setVal(constraint, ca(c.val, a.val));
    } else if (bv && cv) {
      a.setVal(constraint, cb(c.val, b.val));
    }
  }

  function forgetValue() {
    for (const conn of [a, b, c]) {
      conn.forget(constraint);
    }
  }

  const constraint = { newVal: newValue, forget: forgetValue };
  for (const conn of [a, b, c]) {
    conn.connect(constraint);
  }
  return constraint;
}

function adder(a, b, c) {
  /** The constraint that a + b = c. */
  return makeTernaryConstraint(a, b, c, (x, y) => x + y, (x, y) => x - y, (x, y) => x - y);
}

function multiplier(a, b, c) {
  /** The constraint that a * b = c. */
  return makeTernaryConstraint(a, b, c, (x, y) => x * y, (x, y) => x / y, (x, y) => x / y);
}

function constant(conn, value) {
  /** The constraint that conn = value. */
  const constraint = {};
  conn.setVal(constraint, value);
  return constraint;
}
```

A connector is represented as an object that contains a value, an informant, and an array of constraints:

```javascript
function connector(name) {
  /** A connector between constraints. */
  let informant = null;
  const constraints = [];

  function setValue(source, value) {
    if (conn.val === null) {
      informant = source;
      conn.val = value;
      if (name) console.log(`${name} = ${value}`);
      informAllExcept(source, 'newVal', constraints);
    } else if (conn.val !== value) {
      console.log(`Contradiction detected: ${conn.val} vs ${value}`);
    }
  }

  function forgetValue(source) {
    if (informant === source) {
      informant = null;
      conn.val = null;
      if (name) console.log(`${name} is forgotten`);
      informAllExcept(source, 'forget', constraints);
    }
  }

  const conn = {
    val: null,
    setVal: setValue,
    forget: forgetValue,
    hasVal: () => conn.val !== null,
    connect: (source) => constraints.push(source)
  };
  return conn;
}

function informAllExcept(source, message, constraints) {
  /** Inform all constraints of the message, except source. */
  for (const c of constraints) {
    if (c !== source) {
      c[message]();
    }
  }
}
```

The constraint system we have designed introduces many ideas that will appear again in object-oriented programming. Constraints and connectors are both abstractions that are manipulated through messages. When the value of a connector is changed, it is changed via a message that not only changes the value, but validates it (checking the source) and propagates its effects (informing other constraints). In fact, we will use a similar architecture of objects with string-valued keys and function values to implement an object-oriented system later in this chapter.
