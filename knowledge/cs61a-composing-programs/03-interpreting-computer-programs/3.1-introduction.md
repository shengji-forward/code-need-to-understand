## Key Concepts

- **Programming languages** define both *syntax* (the structural rules of valid text) and *semantics* (the meaning assigned to syntactically valid constructs), and an interpreter is the program that bridges the two.
- **The language processing pipeline** transforms source text through discrete stages: source code, tokenization, parsing into an abstract syntax tree (AST), and evaluation to produce a value.
- **Tokenization (lexical analysis)** splits raw source text into a sequence of categorized tokens such as numbers, operators, identifiers, and punctuation.
- **Parsing** consumes the token stream and builds a tree-structured abstract syntax tree (AST) that captures the hierarchical relationships between expressions.
- **Evaluation** walks the AST recursively, dispatching on node type, to compute the value each expression represents.
- **The eval/apply cycle** is the elegant mutual recursion at the heart of every interpreter: `eval` dispatches on expression type, and `apply` evaluates function bodies in extended environments.
- **Environments** chain frames together so that variable lookup follows a parent-pointer chain from local to global scope.

## Content

### Chapter 3: Interpreting Computer Programs

Chapters 1 and 2 explored the relationship between two fundamental elements of programming: functions and data. We saw how functions can be manipulated as data using higher-order functions, and how data can be endowed with behavior through objects and message passing. We studied functional abstraction, data abstraction, class inheritance, and generic functions. These concepts form a strong foundation for building modular, maintainable, and extensible programs.

This chapter focuses on the third fundamental element: **programs themselves**. A JavaScript program is just a collection of text. Only through the process of interpretation do we perform any meaningful computation based on that text. A programming language like JavaScript is useful because we can define an **interpreter** -- a program that carries out evaluation and execution procedures. It is no exaggeration to regard this as the most fundamental idea in programming: an interpreter, which determines the meaning of expressions in a programming language, is just another program.

To appreciate this point is to change our image of ourselves as programmers. We come to see ourselves as designers of languages, rather than only users of languages designed by others.

### 3.1.1 Programming Languages

Programming languages vary widely in their syntactic structures, features, and domains of application. Among general-purpose programming languages, the constructs of function definition and function application are pervasive. On the other hand, powerful languages exist that do not include an object system, higher-order functions, assignment, or even control constructs such as `while` and `for` statements. Scheme, a dialect of Lisp, is an example of a powerful language with a minimal set of features -- the subset we reference in this chapter does not allow mutable values at all.

In this chapter, we study the design of interpreters and the computational processes they create when executing programs. The prospect of designing an interpreter for a general programming language may seem daunting. After all, interpreters are programs that can carry out any possible computation, depending on their input. However, many interpreters have an elegant common structure: two mutually recursive functions. The first evaluates expressions in environments; the second applies functions to arguments.

These functions are recursive in that they are defined in terms of each other: applying a function requires evaluating the expressions in its body, while evaluating an expression may involve applying one or more functions.

### 3.1.2 The Language Processing Pipeline

Before we build an interpreter, it helps to understand the pipeline that all interpreters -- and compilers -- follow. Starting from raw source text, the text is transformed through a series of stages until it produces a result:

```
Source Text  -->  Tokens  -->  AST  -->  Value
  (string)     (array)     (tree)    (JS value)
```

Each stage has a distinct responsibility:

1. **Lexical analysis (tokenization)**: Split the raw string of source code into a flat sequence of tokens, each annotated with a type (number, operator, identifier, punctuation).
2. **Parsing**: Consume the token stream and build a tree structure -- the abstract syntax tree (AST) -- that captures the hierarchical nesting of expressions.
3. **Evaluation**: Walk the AST recursively, computing the value each subtree represents.

The rest of this section walks through each stage in detail, building a tiny interpreter for arithmetic expressions in JavaScript.

### 3.1.3 Tokenization

Tokenization is the first stage: converting a raw string into a flat array of tokens. Each token has a `type` that classifies it and a `value` that carries the original text (or a converted value like a number).

Consider the expression `3 + 4 * 2`. A tokenizer splits this into:

```
[
  { type: "number", value: 3 },
  { type: "operator", value: "+" },
  { type: "number", value: 4 },
  { type: "operator", value: "*" },
  { type: "number", value: 2 },
]
```

Here is a simple tokenizer for arithmetic expressions involving non-negative integers and the operators `+` and `*`, with parentheses for grouping:

```javascript
function tokenize(source) {
  const tokens = [];
  let i = 0;
  while (i < source.length) {
    const ch = source[i];
    // Skip whitespace
    if (ch === " " || ch === "\t" || ch === "\n") {
      i++;
      continue;
    }
    // Single-character tokens
    if (ch === "+" || ch === "*") {
      tokens.push({ type: "operator", value: ch });
      i++;
      continue;
    }
    if (ch === "(" || ch === ")") {
      tokens.push({ type: "punctuation", value: ch });
      i++;
      continue;
    }
    // Multi-character number literals
    if (ch >= "0" && ch <= "9") {
      let numStr = "";
      while (i < source.length && source[i] >= "0" && source[i] <= "9") {
        numStr += source[i];
        i++;
      }
      tokens.push({ type: "number", value: Number(numStr) });
      continue;
    }
    throw new Error(`Unexpected character: '${ch}'`);
  }
  return tokens;
}

tokenize("3 + 4 * 2");
// [ { type: 'number', value: 3 },
//   { type: 'operator', value: '+' },
//   { type: 'number', value: 4 },
//   { type: 'operator', value: '*' },
//   { type: 'number', value: 2 } ]

tokenize("(1 + 2) * 3");
// [ { type: 'punctuation', value: '(' },
//   { type: 'number', value: 1 },
//   { type: 'operator', value: '+' },
//   { type: 'number', value: 2 },
//   { type: 'punctuation', value: ')' },
//   { type: 'operator', value: '*' },
//   { type: 'number', value: 3 } ]
```

The tokenizer is intentionally simple. A production tokenizer would also handle floating-point numbers, strings, keywords, identifiers, comments, and more. But the principle is the same: scan the source text left to right, grouping characters into classified tokens.

### 3.1.4 Parsing

Parsing consumes the flat token stream and builds a tree -- the **abstract syntax tree** (AST) -- that captures the nested structure of the expression. In an AST, each node represents a language construct, and its children represent its sub-expressions.

For arithmetic, we need two node types:

- **Number literal**: `{ type: "NumberLiteral", value: 3 }`
- **Binary expression**: `{ type: "BinaryExpression", operator: "+", left: <node>, right: <node> }`

For example, the expression `3 + 4 * 2` should parse into:

```
        (+)
       /   \
      3    (*)
          /   \
         4     2
```

Expressed as a JavaScript object:

```javascript
{
  type: "BinaryExpression",
  operator: "+",
  left: { type: "NumberLiteral", value: 3 },
  right: {
    type: "BinaryExpression",
    operator: "*",
    left: { type: "NumberLiteral", value: 4 },
    right: { type: "NumberLiteral", value: 2 },
  },
}
```

The tree structure encodes that `*` binds tighter than `+`: the `4 * 2` sub-expression is a subtree under the `+` node, so it is evaluated first.

A standard technique for building such trees is **recursive descent parsing**, where each grammar rule corresponds to a function. Here is a parser that handles `+` and `*` with correct precedence (`*` binds tighter) and parentheses:

```javascript
function parse(tokens) {
  let pos = 0;

  function peek() {
    return tokens[pos];
  }

  function consume(expectedType, expectedValue) {
    const token = tokens[pos];
    if (!token) {
      throw new Error("Unexpected end of input");
    }
    if (expectedType && token.type !== expectedType) {
      throw new Error(`Expected type ${expectedType}, got ${token.type}`);
    }
    if (expectedValue !== undefined && token.value !== expectedValue) {
      throw new Error(`Expected '${expectedValue}', got '${token.value}'`);
    }
    pos++;
    return token;
  }

  // expression := term (('+') term)*
  function parseExpression() {
    let left = parseTerm();
    while (peek() && peek().type === "operator" && peek().value === "+") {
      const op = consume("operator", "+").value;
      const right = parseTerm();
      left = { type: "BinaryExpression", operator: op, left, right };
    }
    return left;
  }

  // term := factor (('*') factor)*
  function parseTerm() {
    let left = parseFactor();
    while (peek() && peek().type === "operator" && peek().value === "*") {
      const op = consume("operator", "*").value;
      const right = parseFactor();
      left = { type: "BinaryExpression", operator: op, left, right };
    }
    return left;
  }

  // factor := number | '(' expression ')'
  function parseFactor() {
    if (peek() && peek().type === "punctuation" && peek().value === "(") {
      consume("punctuation", "(");
      const expr = parseExpression();
      consume("punctuation", ")");
      return expr;
    }
    const num = consume("number");
    return { type: "NumberLiteral", value: num.value };
  }

  const ast = parseExpression();
  if (pos < tokens.length) {
    throw new Error(`Unexpected token after expression: ${JSON.stringify(tokens[pos])}`);
  }
  return ast;
}
```

Let us parse a few expressions to see the resulting ASTs:

```javascript
const ast1 = parse(tokenize("3 + 4 * 2"));
// { type: 'BinaryExpression', operator: '+',
//   left: { type: 'NumberLiteral', value: 3 },
//   right:
//     { type: 'BinaryExpression', operator: '*',
//       left: { type: 'NumberLiteral', value: 4 },
//       right: { type: 'NumberLiteral', value: 2 } } }

const ast2 = parse(tokenize("(3 + 4) * 2"));
// { type: 'BinaryExpression', operator: '*',
//   left:
//     { type: 'BinaryExpression', operator: '+',
//       left: { type: 'NumberLiteral', value: 3 },
//       right: { type: 'NumberLiteral', value: 4 } },
//   right: { type: 'NumberLiteral', value: 2 } }
```

Notice how parentheses change the tree structure. In `3 + 4 * 2`, the `*` node is nested under `+` (multiplication binds tighter). In `(3 + 4) * 2`, the `+` node is nested under `*` (parentheses force addition first).

### 3.1.5 Evaluation

Evaluation is the final stage: walk the AST recursively and compute the value it represents. The evaluator dispatches on the `type` field of each node.

```javascript
function evaluate(node) {
  if (node.type === "NumberLiteral") {
    return node.value;
  }
  if (node.type === "BinaryExpression") {
    const leftVal = evaluate(node.left);
    const rightVal = evaluate(node.right);
    if (node.operator === "+") {
      return leftVal + rightVal;
    }
    if (node.operator === "*") {
      return leftVal * rightVal;
    }
    throw new Error(`Unknown operator: ${node.operator}`);
  }
  throw new Error(`Unknown node type: ${node.type}`);
}
```

Putting the full pipeline together:

```javascript
function interpret(source) {
  const tokens = tokenize(source);
  const ast = parse(tokens);
  return evaluate(ast);
}

interpret("3 + 4 * 2");    // 11  (3 + (4 * 2))
interpret("(3 + 4) * 2");  // 14  ((3 + 4) * 2)
interpret("1 + 2 + 3");    // 6
interpret("2 * 3 + 4");    // 10  ((2 * 3) + 4)
```

The evaluator is small because the parser has already done the hard work of encoding precedence and grouping into the tree structure. The evaluator simply walks the tree, computing values bottom-up: leaves first, then their parents.

This three-stage pipeline -- tokenize, parse, evaluate -- is the architecture of every interpreter, from our tiny arithmetic language up to JavaScript engines like V8. Real engines add more stages (optimization, bytecode compilation, JIT compilation), but the core data flow is the same: text becomes tokens, tokens become trees, trees become values.

### 3.1.6 The Eval/Apply Cycle

The original Composing Programs text identifies an elegant structure shared by many interpreters: two mutually recursive functions, traditionally called `eval` and `apply`. We have already seen the dispatch-on-type pattern in our `evaluate` function. Now we extend it to handle function definition and application.

**`eval` (evaluate)** dispatches on the type of expression:

- A literal? Return its value directly.
- A name? Look it up in the current environment.
- A function definition? Create a closure (function value) and bind it.
- A function call? Evaluate the operator and operands, then call `apply`.

**`apply` (apply a function)** executes a function body:

- Create a new frame binding parameters to argument values.
- Extend the closure's captured environment with this new frame.
- Call `eval` on the body expression in the extended environment.

This mutual recursion -- `eval` calls `apply`, `apply` calls `eval` -- is the computational engine at the heart of every interpreter. Let us build a minimal version that supports numbers, names, `lambda` (anonymous functions), and function calls.

First, we define AST node types for these constructs:

```javascript
// Number literal: { type: "NumberLiteral", value: 5 }
// Name lookup:    { type: "Name", name: "x" }
// Lambda:         { type: "Lambda", params: ["x", "y"], body: <expr> }
// Function call:  { type: "Call", operator: <expr>, args: [<expr>, ...] }
```

The evaluator with `eval` and `apply`:

```javascript
function evalExpr(expr, env) {
  switch (expr.type) {
    case "NumberLiteral":
      return expr.value;

    case "Name":
      if (expr.name in env) {
        return env[expr.name];
      }
      throw new Error(`Unbound name: ${expr.name}`);

    case "Lambda":
      // Return a closure: the function body + the defining environment
      return { type: "closure", params: expr.params, body: expr.body, env };

    case "Call": {
      // Evaluate operator and operands
      const func = evalExpr(expr.operator, env);
      const argVals = expr.args.map((arg) => evalExpr(arg, env));
      return applyFunc(func, argVals);
    }

    default:
      throw new Error(`Unknown expression type: ${expr.type}`);
  }
}

function applyFunc(func, args) {
  if (func.type !== "closure") {
    throw new Error(`Not a function: ${JSON.stringify(func)}`);
  }
  if (args.length !== func.params.length) {
    throw new Error(
      `Expected ${func.params.length} args, got ${args.length}`
    );
  }
  // Extend the closure's environment with parameter bindings
  const childEnv = Object.create(func.env);
  for (let i = 0; i < func.params.length; i++) {
    childEnv[func.params[i]] = args[i];
  }
  return evalExpr(func.body, childEnv);
}

// A global environment with no inherited properties
const evalEnv = Object.create(null);
evalEnv["+"] = (a, b) => a + b;
```

Notice the mutual recursion: `evalExpr` calls `applyFunc` when it encounters a `Call` node, and `applyFunc` calls `evalExpr` to evaluate the function body.

Let us use this to evaluate `((x, y) => x + y)(3, 4)`, expressed as an AST:

```javascript
// The AST for: ((x, y) => x + y)(3, 4)
const callExpr = {
  type: "Call",
  operator: {
    type: "Lambda",
    params: ["x", "y"],
    body: {
      type: "Call",
      operator: { type: "Name", name: "+" },
      args: [
        { type: "Name", name: "x" },
        { type: "Name", name: "y" },
      ],
    },
  },
  args: [
    { type: "NumberLiteral", value: 3 },
    { type: "NumberLiteral", value: 4 },
  ],
};

// We need "+" in the environment
// Using Object.create(null) avoids inherited properties like toString
const globalEnv = Object.create(null);
globalEnv["+"] = function builtinAdd(a, b) {
  return a + b;
};

// Patch applyFunc to handle built-in functions
function applyFuncPatched(func, args) {
  if (typeof func === "function") {
    return func(...args);
  }
  if (func.type !== "closure") {
    throw new Error(`Not a function: ${JSON.stringify(func)}`);
  }
  if (args.length !== func.params.length) {
    throw new Error(
      `Expected ${func.params.length} args, got ${args.length}`
    );
  }
  const childEnv = Object.create(func.env);
  for (let i = 0; i < func.params.length; i++) {
    childEnv[func.params[i]] = args[i];
  }
  return evalExprPatched(func.body, childEnv);
}

function evalExprPatched(expr, env) {
  switch (expr.type) {
    case "NumberLiteral":
      return expr.value;
    case "Name":
      if (expr.name in env) {
        return env[expr.name];
      }
      throw new Error(`Unbound name: ${expr.name}`);
    case "Lambda":
      return { type: "closure", params: expr.params, body: expr.body, env };
    case "Call": {
      const func = evalExprPatched(expr.operator, env);
      const argVals = expr.args.map((arg) => evalExprPatched(arg, env));
      return applyFuncPatched(func, argVals);
    }
    default:
      throw new Error(`Unknown expression type: ${expr.type}`);
  }
}

evalExprPatched(callExpr, globalEnv);  // 7
```

The result is `7` -- the sum of `3` and `4`, computed entirely by our own evaluator walking the AST. The eval/apply cycle handled the function call: `eval` recognized a `Call` node, evaluated the lambda to produce a closure, evaluated the arguments to get `[3, 4]`, then handed control to `apply`, which created a new environment binding `x` to `3` and `y` to `4`, and called `eval` again on the body.

### 3.1.7 Environments and Name Lookup

An **environment** is a chain of frames, where each frame is a mapping from names to values. When we look up a name, we search the chain from the innermost (local) frame outward to the global frame, returning the first binding found.

We can model this using `Object.create(null)`, which creates a plain dictionary with no inherited properties. Child frames use `Object.create(parentFrame)` so that the `in` operator walks our frame chain, not `Object.prototype`:

```javascript
// Global frame (no prototype, so "toString" etc. are absent)
const globalFrame = Object.create(null);
globalFrame["+"] = (a, b) => a + b;
globalFrame["-"] = (a, b) => a - b;
globalFrame["*"] = (a, b) => a * b;
globalFrame.pi = 3.141592653589793;

// A function call creates a local frame that extends the global frame
const localFrame = Object.create(globalFrame);
localFrame.x = 10;
localFrame.y = 20;

// Name lookup walks the chain
localFrame.x;           // 10   (found in local frame)
localFrame.pi;          // 3.14... (found in global frame, via prototype)
"pi" in localFrame;     // true  (prototype chain is searched)
"toString" in localFrame;  // false (no Object.prototype leakage)
```

When we call a closure, we create a new frame whose parent is the closure's saved environment (not the caller's environment). This is **lexical scoping**: names are resolved based on where a function is *defined*, not where it is *called*.

Consider an environment diagram for evaluating `((x) => ((y) => x + y)(3))(2)`:

```
Global Frame (f1)
  "+" -> builtin +

Evaluating the outer call: lambda applied to 2
  f2 [parent: f1]
    x -> 2

  Evaluating the inner call: lambda applied to 3
    f3 [parent: f2]    <-- parent is f2 (where the inner lambda was defined)
      y -> 3

    Evaluating x + y:
      x found in f2 -> 2
      y found in f3 -> 3
      Result: 5
```

Here is the same evaluation using our environment model:

```javascript
// Build AST for: ((x) => ((y) => x + y)(3))(2)
const expr = {
  type: "Call",
  operator: {
    type: "Lambda",
    params: ["x"],
    body: {
      type: "Call",
      operator: {
        type: "Lambda",
        params: ["y"],
        body: {
          type: "Call",
          operator: { type: "Name", name: "+" },
          args: [
            { type: "Name", name: "x" },
            { type: "Name", name: "y" },
          ],
        },
      },
      args: [{ type: "NumberLiteral", value: 3 }],
    },
  },
  args: [{ type: "NumberLiteral", value: 2 }],
};

evalExprPatched(expr, globalFrame);  // 5
```

The inner lambda `{ params: ["y"], body: ... }` is defined inside the outer lambda. When the outer lambda is called with argument `2`, a frame `f2` is created with `x: 2`. The inner lambda becomes a closure that saves `f2` as its environment. When the inner lambda is called with argument `3`, a frame `f3` is created with parent `f2` and binding `y: 3`. Looking up `x` in `f3` falls through to `f2`, finding `2`. Looking up `y` finds `3` directly. The sum is `5`.

This environment-chain model is not just an academic exercise. It is how JavaScript engines actually implement scope. Every function object internally stores a reference to its **lexical environment** (the environment in which it was defined). When the function is called, a new lexical environment is created with the stored one as its outer reference.

```javascript
function makeCounter() {
  let count = 0;
  return function increment() {
    count = count + 1;
    return count;
  };
}

const counter = makeCounter();
counter();  // 1
counter();  // 2
counter();  // 3
```

The environment diagram for this example:

```
Global Frame
  makeCounter -> func makeCounter()
  counter     -> closure increment() [parent: makeCounter() frame]

makeCounter() call frame (f1)  [parent: Global]
  count -> 0  (then 1, then 2, then 3 as increment is called)

increment() closure captures f1 as its parent.
Each call to increment() looks up 'count' in f1,
modifies it, and returns the new value.
```

The `increment` function is a closure: it carries a reference to the `makeCounter()` call frame where `count` lives. Each invocation of `increment` finds `count` through this reference, modifies it, and returns. No matter how many times `makeCounter` is called, each returned counter has its own independent `count` because each call creates a separate frame.

### 3.1.8 Bringing It All Together

We have now traced the full pipeline from source text to computed value:

```
"(1 + 2) * 3"
      |
      v  tokenize
[ '(', 1, '+', 2, ')', '*', 3 ]   (tokens)
      |
      v  parse
     (*)
    /   \
  (+)     3
  / \
 1    2                            (AST)
      |
      v  evaluate
     9                               (value)
```

Each stage is a self-contained transformation with a clear input and output contract. This separation of concerns is what makes interpreters tractable to build and reason about. You can test the tokenizer independently of the parser, and the parser independently of the evaluator.

The eval/apply cycle within the evaluator gives it the power to handle arbitrary computation. Any program, no matter how complex, is ultimately evaluated by these two mutually recursive functions dispatching on expression type and extending environments. This is the fundamental insight of this chapter: the meaning of a programming language is itself a program -- one that can be understood, modified, and extended by programmers like us.

## Python/Scheme vs JavaScript Notes

| Topic | Python / Scheme | JavaScript |
|---|---|---|
| **Scheme as teaching language** | CS61A uses Scheme to illustrate minimal interpreters | We build interpreters in JavaScript; the eval/apply structure is identical regardless of host language |
| **`lambda` syntax** | Python: `lambda x: x + 1`; Scheme: `(lambda (x) (+ x 1))` | `(x) => x + 1` (arrow function) |
| **`def` / `define`** | Python: `def foo(x):`; Scheme: `(define (foo x) ...)` | `function foo(x) { ... }` or `const foo = (x) => ...` |
| **Environment model** | Python uses dict-like frames with parent pointers; Scheme uses linked environment frames | JavaScript uses prototype chain (`Object.create`) to model parent pointers; real engines use internal lexical environment slots |
| **`nonlocal` / mutation** | Python requires `nonlocal x` to rebind in enclosing scope | JavaScript allows mutation of `let`/`var` in enclosing scope without declaration; `const` prevents reassignment |
| **Recursive descent parsing** | Python's `yield` and generators sometimes used for parser combinators | Same recursive descent technique works; we use plain functions returning objects |
| **`Object.create` for scope** | Not a Python idiom (Python classes serve this role) | `Object.create(parent)` creates an object whose prototype is `parent`, giving free name lookup through the chain via JS's built-in property resolution |
