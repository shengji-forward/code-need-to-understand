## Key Concepts

- **Exception objects** are instances of `Error` and its subclasses (`TypeError`, `ReferenceError`, `SyntaxError`, etc.) that carry a `message`, `name`, and `stack` trace describing what went wrong and where.
- **Throwing exceptions** with `throw` interrupts normal control flow immediately, signaling that an exceptional circumstance has arisen and no further statements in the current block will execute.
- **Handling exceptions** with `try/catch` lets a program recover from errors at a designated point, rather than crashing. JavaScript catches all error types in a single `catch` clause and uses `instanceof` to distinguish them.
- **Propagation** means that if a function does not catch an exception, the exception bubbles up through the call stack until it reaches a handler or terminates the program.
- **Finally** blocks always execute after `try`/`catch`, regardless of whether an exception was thrown or caught, making them ideal for resource cleanup.
- **Custom error classes** extend `Error` to create domain-specific error types that can carry extra context and be distinguished from built-in errors.
- **Assertions** enforce invariants and preconditions. JavaScript has no built-in `assert`, but the pattern `if (!condition) throw new Error(message)` is equivalent.

## Content

### 3.3.1 Exception Objects

In JavaScript, errors are objects. Every error is an instance of the built-in `Error` constructor or one of its subclasses. The most important built-in error types are:

- **`Error`** -- the base class for all user-thrown errors.
- **`TypeError`** -- thrown when a value is not of the expected type (e.g., calling a non-function).
- **`ReferenceError`** -- thrown when accessing an undeclared variable.
- **`SyntaxError`** -- thrown when code cannot be parsed.
- **`RangeError`** -- thrown when a value is outside the allowable range.

Creating an error object is separate from throwing it. You construct one with `new Error("message")`:

```javascript
const err = new Error("something went wrong");

err.message;  // "something went wrong"
err.name;     // "Error"
typeof err.stack;  // "string" — a multi-line stack trace
```

Every `Error` instance has three key properties:

- **`message`** -- the human-readable description passed to the constructor.
- **`name`** -- the error's class name (e.g., `"TypeError"`, `"RangeError"`).
- **`stack`** -- a string representing the call stack at the point the error was created, useful for debugging.

The built-in subclasses work the same way:

```javascript
const typeErr = new TypeError("x is not a function");
typeErr.message;  // "x is not a function"
typeErr.name;     // "TypeError"

const refErr = new ReferenceError("foo is not defined");
refErr.name;  // "ReferenceError"
```

The JavaScript engine itself creates these error objects when something goes wrong at runtime:

```javascript
null.x;
// TypeError: Cannot read properties of null (reading 'x')

notDeclaredAnywhere;
// ReferenceError: notDeclaredAnywhere is not defined
```

These automatic errors behave identically to errors you create manually -- they are all instances of `Error` and can be caught and inspected with `try/catch`.

### 3.3.2 Raising Exceptions

The `throw` statement interrupts normal execution immediately. Any expression can be thrown, but by convention (and for compatibility with `catch` blocks) you should always throw an `Error` instance:

```javascript
function divide(a, b) {
  if (b === 0) {
    throw new Error("division by zero");
  }
  return a / b;
}

divide(10, 2);   // 5
divide(10, 0);   // Error: division by zero
```

When `throw` executes, no further statements in the current block run. The exception propagates outward to the nearest enclosing `try/catch`, or to the top level if there is none. This makes `throw` a powerful control-flow mechanism: it unwinds the call stack until a handler is found.

Functions should throw when they encounter conditions they cannot fulfill:

```javascript
function elementAt(arr, index) {
  if (index < 0 || index >= arr.length) {
    throw new RangeError(`index ${index} out of bounds for length ${arr.length}`);
  }
  return arr[index];
}

elementAt([10, 20, 30], 1);   // 20
elementAt([10, 20, 30], 5);   // RangeError: index 5 out of bounds for length 3
```

```javascript
function sqrt(x) {
  if (x < 0) {
    throw new Error(`cannot take square root of negative number: ${x}`);
  }
  return Math.sqrt(x);
}

sqrt(9);    // 3
sqrt(-1);   // Error: cannot take square root of negative number: -1
```

In both cases, the function checks a precondition and throws when it is violated. This is a **contract** between the function and its caller: the function promises to work correctly if the inputs are valid, and the caller promises to provide valid inputs.

### 3.3.3 Handling Exceptions

A `try/catch` statement lets you respond to exceptions at a designated point in your program. The `try` block runs first. If any exception is thrown during its execution, control jumps to the `catch` block:

```javascript
function invert(x) {
  if (x === 0) {
    throw new Error("division by zero");
  }
  return 1 / x;
}

function invertSafe(x) {
  try {
    return invert(x);
  } catch (e) {
    return 0;
  }
}

invertSafe(2);   // 0.5
invertSafe(0);   // 0  (exception caught, fallback returned)
```

When `invert(0)` throws, the `return invert(x)` in the `try` block is abandoned. Execution jumps directly to the `catch` block, which returns `0`. No code after the throw runs:

```javascript
function invert(x) {
  if (x === 0) {
    throw new Error("division by zero");
  }
  console.log("computed inverse");  // not reached when x is 0
  return 1 / x;
}

function invertSafe(x) {
  try {
    return invert(x);
  } catch (e) {
    return `caught: ${e.message}`;
  }
}

invertSafe(2);   // 0.5  (logs "computed inverse")
invertSafe(0);   // "caught: division by zero"  (nothing logged)
```

Note that in JavaScript, `1 / 0` returns `Infinity` rather than throwing. To demonstrate exception handling, our `invert` function must explicitly check for zero and throw. This is a meaningful difference from Python, where `1 / 0` raises `ZeroDivisionError`.

**Catching specific error types.** Unlike Python, which has separate `except` clauses for each type, JavaScript has a single `catch` clause that receives the thrown value. You use `instanceof` inside the `catch` to distinguish error types:

```javascript
function safeOperation(value) {
  try {
    return riskyOperation(value);
  } catch (e) {
    if (e instanceof TypeError) {
      return "type error handled: " + e.message;
    } else if (e instanceof RangeError) {
      return "range error handled: " + e.message;
    } else {
      throw e;  // re-throw anything we don't handle
    }
  }
}
```

Re-throwing errors you do not handle is an important pattern. It lets you catch the specific errors you can recover from while letting unexpected errors propagate to a higher-level handler:

```javascript
function parseJSON(text) {
  try {
    return JSON.parse(text);
  } catch (e) {
    if (e instanceof SyntaxError) {
      return { error: "invalid JSON", raw: text };
    }
    throw e;  // re-throw unexpected errors
  }
}

parseJSON('{"a": 1}');       // { a: 1 }
parseJSON('not json at all'); // { error: "invalid JSON", raw: "not json at all" }
```

### 3.3.4 Propagating Exceptions

When a function does not catch an exception, the exception **propagates** up the call stack. It bubbles through each caller until it finds a `try/catch` that handles it, or until it reaches the top level and terminates the program with an uncaught error.

Consider a chain of function calls:

```javascript
function deepest() {
  throw new Error("originated in deepest");
}

function middle() {
  return deepest();  // no try/catch, so exception propagates
}

function outermost() {
  try {
    return middle();
  } catch (e) {
    return `caught at outermost: ${e.message}`;
  }
}

outermost();  // "caught at outermost: originated in deepest"
```

The call stack at the point of the throw looks like: `outermost -> middle -> deepest`. The exception is thrown in `deepest`, passes through `middle` (which has no handler), and is caught in `outermost`.

This propagation is what makes exceptions so useful for error handling: you can place a single `try/catch` at a high level and it will catch errors from any function call in the subtree below it. You do not need to check return codes at every level.

A more realistic example shows how exceptions separate the logic of computing a result from the logic of handling failure:

```javascript
function safeSqrt(x) {
  if (x < 0) {
    throw new Error(`square root of negative number: ${x}`);
  }
  return Math.sqrt(x);
}

function computeResult(value) {
  const root = safeSqrt(value);  // throws if value < 0
  return root * 2;
}

function tryCompute(value) {
  try {
    return computeResult(value);
  } catch (e) {
    return `failed: ${e.message}`;
  }
}

tryCompute(9);    // 6   (safeSqrt(9) = 3, then 3 * 2 = 6)
tryCompute(-4);   // "failed: square root of negative number: -4"
```

When `safeSqrt(-4)` throws, the exception propagates through `computeResult` (which has no handler) and is caught in `tryCompute`. These concerns are cleanly separated -- `safeSqrt` validates its input, `computeResult` focuses on its computation, and `tryCompute` handles failure.

### 3.3.5 Finally

The `finally` block always executes after the `try` (and `catch`, if one ran), regardless of whether an exception was thrown, caught, or re-thrown. This makes `finally` the right place for cleanup actions that must happen no matter what:

```javascript
function readFile(path) {
  const handle = openHandle(path);  // hypothetical resource
  try {
    return handle.read();
  } catch (e) {
    return `error: ${e.message}`;
  } finally {
    handle.close();  // always runs
  }
}
```

The execution order is:

1. The `try` block runs.
2. If an exception is thrown and a `catch` is present, the `catch` block runs.
3. The `finally` block always runs, whether or not an exception was thrown or caught.

```javascript
function demonstrateFinally(shouldThrow) {
  try {
    console.log("try block");
    if (shouldThrow) {
      throw new Error("boom");
    }
    return "try result";
  } catch (e) {
    console.log("catch block:", e.message);
    return "catch result";
  } finally {
    console.log("finally block (always runs)");
  }
}

demonstrateFinally(false);
// try block
// finally block (always runs)
// => "try result"

demonstrateFinally(true);
// try block
// catch block: boom
// finally block (always runs)
// => "catch result"
```

A `finally` block without a `catch` is also valid. It ensures cleanup happens while letting the exception continue propagating:

```javascript
function withCleanup() {
  console.log("acquiring resource");
  try {
    throw new Error("something went wrong");
  } finally {
    console.log("cleaning up");  // runs before the error propagates
  }
  // This line is never reached
}

try {
  withCleanup();
} catch (e) {
  console.log("caught:", e.message);
}
// acquiring resource
// cleaning up
// caught: something went wrong
```

The `finally` block runs even if the `try` or `catch` contains a `return` statement. In fact, a `return` inside `finally` will override the return value from `try` or `catch` -- this is almost always a mistake and should be avoided.

### 3.3.6 Custom Error Classes

JavaScript lets you define your own error classes by extending `Error`. Custom error types serve two purposes: they carry domain-specific information, and they let you distinguish your errors from built-in ones using `instanceof`.

```javascript
class InterpreterError extends Error {
  constructor(message) {
    super(message);
    this.name = "InterpreterError";
  }
}

const err = new InterpreterError("unbound variable: x");
err.message;                // "unbound variable: x"
err.name;                   // "InterpreterError"
err instanceof Error;       // true
err instanceof InterpreterError;  // true
```

Custom error classes can carry additional context beyond the message string. For example, an interpreter might want to report the expression that caused an error:

```javascript
class UnboundNameError extends Error {
  constructor(name, expression) {
    super(`name '${name}' is not bound in the current environment`);
    this.name = "UnboundNameError";
    this.unboundName = name;
    this.expression = expression;
  }
}

const err = new UnboundNameError("y", { type: "name", value: "y" });
err.unboundName;   // "y"
err.expression;    // { type: "name", value: "y" }
err.message;       // "name 'y' is not bound in the current environment"
```

This extra context is valuable for error reporting. The interpreter can inspect the error object to produce a helpful message, rather than trying to encode everything into a single string.

Another example -- an arity mismatch error that records how many arguments were expected versus how many were provided:

```javascript
class ArityMismatchError extends Error {
  constructor(name, expected, received) {
    super(`${name} expects ${expected} arguments but received ${received}`);
    this.name = "ArityMismatchError";
    this.expected = expected;
    this.received = received;
  }
}

const err = new ArityMismatchError("add", 2, 1);
err.message;   // "add expects 2 arguments but received 1"
err.expected;  // 2
err.received;  // 1
```

Using `instanceof` to distinguish between custom error types:

```javascript
function handleInterpreterError(e) {
  if (e instanceof UnboundNameError) {
    return `Variable not found: ${e.unboundName}`;
  } else if (e instanceof ArityMismatchError) {
    return `Wrong number of arguments: need ${e.expected}, got ${e.received}`;
  } else {
    return `Internal error: ${e.message}`;
  }
}
```

### 3.3.7 Error Handling in Interpreters

The interpreter we build in sections 3.4 and 3.5 uses exceptions to report three kinds of problems: syntax errors, runtime errors, and unsupported constructs. Exceptions are the right mechanism here because parsing and evaluation are deeply recursive -- an error might be discovered many levels deep, and the exception propagation mechanism cleanly unwinds the call stack to the handler.

**Syntax errors** are detected during parsing, when the input tokens do not form a valid expression. A helper function like `expectToken` throws a `SyntaxError` when the next token does not match what the grammar requires:

```javascript
function expectToken(tokens, index, expected) {
  if (index >= tokens.length) {
    throw new SyntaxError(`unexpected end of input, expected '${expected}'`);
  }
  if (tokens[index] !== expected) {
    throw new SyntaxError(`expected '${expected}', got '${tokens[index]}'`);
  }
  return index + 1;
}

// Parsing a parenthesized expression like "(+ 1 2)"
function parseCall(tokens, index) {
  index = expectToken(tokens, index, "(");
  const operator = tokens[index];
  index = index + 1;
  // ... parse operands ...
  index = expectToken(tokens, index, ")");
  return { type: "call", operator, index };
}

parseCall(["(", "+", "1", "2", ")"], 0);  // ok
parseCall(["(", "+", "1", "2"], 0);       // SyntaxError: unexpected end of input, expected ')'
parseCall(["+", "1", ")"], 0);            // SyntaxError: expected '(', got '+'
```

**Runtime errors** occur during evaluation, when a syntactically valid expression cannot be computed. The most common cases in an interpreter are:

- Looking up a name that is not bound in any enclosing environment.
- Applying a non-function value.
- Passing the wrong number of arguments.

```javascript
class Environment {
  constructor(parent = null) {
    this.bindings = {};
    this.parent = parent;
  }

  lookup(name) {
    if (name in this.bindings) {
      return this.bindings[name];
    }
    if (this.parent) {
      return this.parent.lookup(name);
    }
    throw new UnboundNameError(name);
  }
}

const global = new Environment();
global.bindings.x = 10;

global.lookup("x");   // 10
global.lookup("y");   // UnboundNameError: name 'y' is not bound in the current environment
```

**The top-level evaluation loop** wraps the entire process in a single `try/catch` that reports the error to the user and then prompts for the next input:

```javascript
function readEvalPrintLoop() {
  while (true) {
    const input = prompt("表达式> ");  // e.g., read from stdin
    if (input === null) break;
    try {
      const tokens = tokenize(input);
      const expression = parse(tokens);
      const result = evaluate(expression, globalEnv);
      console.log(result);
    } catch (e) {
      if (e instanceof SyntaxError) {
        console.log(`Syntax error: ${e.message}`);
      } else if (e instanceof InterpreterError) {
        console.log(`Runtime error: ${e.message}`);
      } else {
        console.log(`Internal error: ${e.message}`);
      }
    }
  }
}
```

This structure separates the concerns cleanly: the parser focuses on grammar, the evaluator focuses on computation, and the top-level loop focuses on error reporting. Each part throws exceptions when it encounters a problem, and the loop catches and presents them to the user. The deep recursion of parsing and evaluation is handled naturally by exception propagation -- there is no need to pass error codes back through every level.

### 3.3.8 Assertions

Python has a built-in `assert` statement. JavaScript does not, but the equivalent pattern is straightforward:

```javascript
function assert(condition, message) {
  if (!condition) {
    throw new Error(`Assertion failed: ${message}`);
  }
}
```

This helper enforces invariants and preconditions:

```javascript
function factorial(n) {
  assert(n >= 0, `n must be non-negative, got ${n}`);
  assert(Number.isInteger(n), `n must be an integer, got ${n}`);
  if (n === 0) return 1;
  return n * factorial(n - 1);
}

factorial(5);    // 120
factorial(-1);   // Error: Assertion failed: n must be non-negative, got -1
```

Assertions are used in testing helpers like `assertEqual` and `assertThrows`:

```javascript
function assertEqual(actual, expected, label = "") {
  if (actual !== expected) {
    throw new Error(
      `assertEqual failed${label ? " (" + label + ")" : ""}: ` +
      `expected ${JSON.stringify(expected)}, got ${JSON.stringify(actual)}`
    );
  }
}

assertEqual(1 + 1, 2);            // passes silently
assertEqual(1 + 1, 3);            // Error: assertEqual failed: expected 3, got 2
```

`assertThrows` verifies that a function does indeed throw, and optionally checks the error message:

```javascript
function assertThrows(fn, expectedMessage) {
  let threw = false;
  try {
    fn();
  } catch (e) {
    threw = true;
    if (expectedMessage !== undefined && !e.message.includes(expectedMessage)) {
      throw new Error(
        `assertThrows: expected message containing "${expectedMessage}", ` +
        `got "${e.message}"`
      );
    }
  }
  if (!threw) {
    throw new Error("assertThrows: expected function to throw, but it did not");
  }
}

assertThrows(() => { throw new Error("oops"); }, "oops");  // passes
assertThrows(() => 42);  // Error: assertThrows: expected function to throw, but it did not
```

Assertions serve a different purpose from error handling. `try/catch` is for errors you expect and can recover from. Assertions are for conditions that should *never* be false -- if one fails, it means there is a bug in the program. In practice, assertions are most heavily used in tests and during development to catch mistakes early.

## Python vs JavaScript Notes

| Topic | Python | JavaScript |
|---|---|---|
| **Throwing** | `raise Exception("msg")` or `raise` (re-raise) | `throw new Error("msg")` or `throw` (re-throw) |
| **Base error class** | `BaseException` (with `Exception` as the common base) | `Error` |
| **Catching all errors** | `except Exception as e:` | `catch (e) { ... }` (catches everything thrown) |
| **Catching specific types** | Multiple `except` clauses: `except TypeError as e:` | Single `catch` clause, then `if (e instanceof TypeError)` |
| **Re-throwing** | `raise` (bare) re-raises the current exception | `throw e;` or `throw;` re-throws the caught exception |
| **Finally** | `try: ... except: ... finally: ...` | `try { ... } catch (e) { ... } finally { ... }` |
| **Built-in assert** | `assert condition, "message"` raises `AssertionError` | No built-in `assert`; use `if (!cond) throw new Error(msg)` |
| **Error properties** | `str(e)` for message, `type(e)` for class, `traceback` module for stack | `e.message`, `e.name`, `e.stack` (string) |
| **Custom error classes** | `class MyError(Exception): def __init__(self, ...):` | `class MyError extends Error { constructor(...) { super(...); this.name = "MyError"; } }` |
| **Type checking caught errors** | `isinstance(e, TypeError)` | `e instanceof TypeError` |
| **Error in `catch` binding** | `except TypeError as e:` binds `e` only in the suite | `catch (e) { ... }` binds `e` in the catch block |
| **Throwing non-Error values** | Allowed but discouraged | Allowed but strongly discouraged (breaks `instanceof`, `.message`, `.stack`) |
