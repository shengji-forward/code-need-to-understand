## Key Concepts

- **Metalinguistic abstraction** is the act of establishing new languages by constructing interpreters -- functions that, when applied to an expression of the language, perform the actions required to evaluate that expression.
- **The Calculator language** is a simple S-expression language for arithmetic. It uses prefix notation and supports `+`, `-`, `*`, `/` with variable arity, mirroring a subset of Scheme.
- **Tokenization** (lexical analysis) splits raw source text into a flat sequence of tokens -- parentheses, operators, and numbers -- the minimal syntactic units of the language.
- **Parsing** (syntactic analysis) converts a token sequence into an abstract syntax tree (AST) via recursive descent, producing nested node objects that represent the hierarchical structure of the expression.
- **Tree-walking evaluation** dispatches on AST node type: number literals evaluate to themselves (self-evaluating), while call expressions recursively evaluate operands and then apply the operator.
- **The interpreter pipeline** composes three stages -- tokenize, parse, evaluate -- into a single function that goes from source string to numeric result.

## Content

### 3.4.1 The Calculator Language

The Calculator language is a minimal expression language for arithmetic. It uses S-expression syntax (parenthesized prefix notation), the same syntax used by Scheme and Lisp. Every expression is either a number literal or a call expression of the form `(operator operand ...)`.

The four arithmetic operators each accept a variable number of arguments:

```javascript
// Addition: sums all arguments, identity is 0
// (+ 1 2 3 4) => 10
// (+)         => 0

// Multiplication: multiplies all arguments, identity is 1
// (* 1 2 3 4) => 24
// (*)         => 1
```

Subtraction and division have two modes. With multiple arguments, they combine all arguments left-to-right. With a single argument, they negate or invert:

```javascript
// Subtraction: subtracts subsequent arguments from the first
// (- 10 1 2 3) => 4
// (- 3)        => -3   (negation)

// Division: divides the first argument by the rest
// (/ 15 12)    => 1.25
// (/ 30 5 2)   => 3
// (/ 10)       => 0.1  (inverse)
```

Call expressions can be nested. A call expression is evaluated by first evaluating its operand sub-expressions, then applying the operator to the resulting arguments:

```javascript
// (- 100 (* 7 (+ 8 (/ -12 -3))))
// Step 1: (/ -12 -3)  => 4
// Step 2: (+ 8 4)     => 12
// Step 3: (* 7 12)    => 84
// Step 4: (- 100 84)  => 16
```

This nested evaluation is the same process used by any interpreter: evaluate sub-expressions recursively, then combine the results. The Calculator language is intentionally small so that we can focus on the structure of an interpreter -- the pipeline from source text to computed result -- without the complexity of a full programming language.

### 3.4.2 Expression Trees and AST Nodes

Before we can evaluate an expression, we need a way to represent it as data. The original Composing Programs text uses Scheme pairs (linked lists) for this purpose. In our JavaScript adaptation, we use plain objects as **abstract syntax tree (AST) nodes**.

The Calculator language has exactly two kinds of expressions, so we need two AST node shapes:

1. **NumberLiteral** -- represents a numeric value:

```javascript
{ type: "NumberLiteral", value: 42 }
```

2. **CallExpression** -- represents an operator applied to zero or more operand expressions:

```javascript
{
  type: "CallExpression",
  operator: "+",
  operands: [
    { type: "NumberLiteral", value: 1 },
    { type: "NumberLiteral", value: 2 }
  ]
}
```

The operands of a CallExpression are themselves AST nodes, which may be NumberLiterals or nested CallExpressions. This nesting is what makes the tree a tree. For example, the expression `(+ (* 3 4) 5)` is represented as:

```javascript
const exampleAst = {
  type: "CallExpression",
  operator: "+",
  operands: [
    {
      type: "CallExpression",
      operator: "*",
      operands: [
        { type: "NumberLiteral", value: 3 },
        { type: "NumberLiteral", value: 4 }
      ]
    },
    { type: "NumberLiteral", value: 5 }
  ]
};
```

This tree structure mirrors the nested parentheses of the source text. The `operator` field is always a string (`"+"`, `"-"`, `"*"`, `"/"`). The `operands` field is always an array of AST nodes. A NumberLiteral has no children -- it is a leaf node.

This representation is simpler than the Scheme pair lists used in the original text, but it serves the same purpose: it gives our interpreter a structured representation of the expression that it can traverse and evaluate.

### 3.4.3 Tokenization

The first stage of the interpreter pipeline is **lexical analysis** (tokenization). A tokenizer splits a source string into a flat array of tokens. For the Calculator language, the token types are:

- **Open parenthesis** `(` -- marks the beginning of a call expression
- **Close parenthesis** `)` -- marks the end of a call expression
- **Operator** `+`, `-`, `*`, `/` -- arithmetic operators
- **Number** -- integer or floating-point numerals like `42`, `3.14`, `-7`

The tokenizer works character by character. Whitespace separates tokens but is not itself a token. Parentheses always form their own token, even when not separated by whitespace.

```javascript
function tokenizeCalculator(source) {
  const tokens = [];
  let i = 0;

  while (i < source.length) {
    const ch = source[i];

    // Skip whitespace
    if (ch === " " || ch === "\t" || ch === "\n" || ch === "\r") {
      i = i + 1;
      continue;
    }

    // Parentheses are single-character tokens
    if (ch === "(" || ch === ")") {
      tokens.push(ch);
      i = i + 1;
      continue;
    }

    // Operators are single-character tokens
    if (ch === "+" || ch === "-" || ch === "*" || ch === "/") {
      // Distinguish unary minus on a number vs. operator.
      // In Calculator, '-' is always an operator because operators
      // appear right after '(' or after operands. Negative numbers
      // are written as (- 3), not as a literal -3.
      tokens.push(ch);
      i = i + 1;
      continue;
    }

    // Number: digit or digit sequence with optional decimal point
    if (isDigit(ch) || (ch === "." && i + 1 < source.length && isDigit(source[i + 1]))) {
      let numStr = "";
      while (i < source.length && (isDigit(source[i]) || source[i] === ".")) {
        numStr = numStr + source[i];
        i = i + 1;
      }
      const value = parseFloat(numStr);
      if (isNaN(value)) {
        throw new SyntaxError(`invalid numeral: ${numStr}`);
      }
      tokens.push(value);
      continue;
    }

    throw new SyntaxError(`unexpected character: '${ch}'`);
  }

  return tokens;
}

function isDigit(ch) {
  return ch >= "0" && ch <= "9";
}
```

Let us see it in action:

```javascript
tokenizeCalculator("(+ 1 2)");
// ["(", "+", 1, 2, ")"]

tokenizeCalculator("(* (+ 1 2) 4)");
// ["(", "*", "(", "+", 1, 2, ")", 4, ")"]

tokenizeCalculator("(- 10 3 2)");
// ["(", "-", 10, 3, 2, ")"]

tokenizeCalculator("(/ 20 2 2)");
// ["(", "/", 20, 2, 2, ")"]

tokenizeCalculator("3.14");
// [3.14]
```

Notice that numbers are parsed into JavaScript `number` values (not left as strings). Operators and parentheses remain as strings. The tokenizer does not understand the structure of expressions -- it merely produces a flat list of atoms. Structural understanding is the job of the parser.

### 3.4.4 Parsing

The second stage is **syntactic analysis** (parsing). The parser consumes the flat token array produced by the tokenizer and builds a nested AST. Parsing is a recursive process because expressions can contain sub-expressions to arbitrary depth.

Our parser uses **recursive descent**: a function that reads tokens one at a time, calling itself recursively when it encounters a sub-expression. We use a mutable index into the token array to track our position.

```javascript
function parseCalculator(tokens) {
  const state = { tokens, pos: 0 };
  const ast = parseExpr(state);

  // After parsing, all tokens should be consumed
  if (state.pos < tokens.length) {
    throw new SyntaxError(
      `unexpected token after expression: '${tokens[state.pos]}'`
    );
  }

  return ast;
}

function parseExpr(state) {
  const { tokens, pos } = state;

  if (pos >= tokens.length) {
    throw new SyntaxError("unexpected end of input");
  }

  const token = tokens[pos];

  // Case 1: A number literal
  if (typeof token === "number") {
    state.pos = pos + 1;
    return { type: "NumberLiteral", value: token };
  }

  // Case 2: A call expression begins with '('
  if (token === "(") {
    state.pos = pos + 1; // consume '('

    // Read the operator
    if (state.pos >= tokens.length) {
      throw new SyntaxError("unexpected end of input after '('");
    }

    const operator = tokens[state.pos];
    if (typeof operator !== "string" || !isOperator(operator)) {
      throw new SyntaxError(
        `expected operator after '(', got '${operator}'`
      );
    }
    state.pos = state.pos + 1; // consume operator

    // Read operands until ')'
    const operands = [];
    while (
      state.pos < state.tokens.length &&
      state.tokens[state.pos] !== ")"
    ) {
      operands.push(parseExpr(state)); // recursive call for each operand
    }

    // Expect closing ')'
    if (state.pos >= state.tokens.length) {
      throw new SyntaxError("missing closing ')'");
    }
    state.pos = state.pos + 1; // consume ')'

    return { type: "CallExpression", operator, operands };
  }

  throw new SyntaxError(`unexpected token: '${token}'`);
}

function isOperator(token) {
  return token === "+" || token === "-" || token === "*" || token === "/";
}
```

The recursive structure is the key to understanding this parser. `parseExpr` handles two cases:

1. **Base case**: the current token is a number. Return a NumberLiteral node and advance.
2. **Recursive case**: the current token is `(`. Consume `(`, read the operator, then repeatedly call `parseExpr` to read operands until `)` is found. Each recursive call may itself encounter a `(` and recurse further.

This produces a tree that mirrors the nesting of parentheses in the source:

```javascript
parseCalculator(tokenizeCalculator("(+ 1 2)"));
// { type: "CallExpression",
//   operator: "+",
//   operands: [
//     { type: "NumberLiteral", value: 1 },
//     { type: "NumberLiteral", value: 2 } ] }

parseCalculator(tokenizeCalculator("(* (+ 1 2) 4)"));
// { type: "CallExpression",
//   operator: "*",
//   operands: [
//     { type: "CallExpression",
//       operator: "+",
//       operands: [
//         { type: "NumberLiteral", value: 1 },
//         { type: "NumberLiteral", value: 2 } ] },
//     { type: "NumberLiteral", value: 4 } ] }

parseCalculator(tokenizeCalculator("42"));
// { type: "NumberLiteral", value: 42 }
```

### 3.4.5 Evaluation

The third stage is **evaluation**. The evaluator walks the AST and computes a numeric result. Like the parser, evaluation is recursive: evaluating a CallExpression requires first evaluating all of its operand sub-expressions.

The evaluator dispatches on the `type` field of the AST node:

```javascript
function evaluateCalculator(ast) {
  if (ast.type === "NumberLiteral") {
    // Numbers are self-evaluating: they evaluate to their own value
    return ast.value;
  }

  if (ast.type === "CallExpression") {
    // Step 1: recursively evaluate all operand sub-expressions
    const args = ast.operands.map(evaluateCalculator);

    // Step 2: apply the operator to the evaluated arguments
    return applyCalculatorOperator(ast.operator, args);
  }

  throw new Error(`unknown AST node type: '${ast.type}'`);
}
```

The `evaluateCalculator` function embodies a fundamental pattern in interpreters: **dispatch on the type of expression**. There are two cases:

- **Self-evaluating** expressions (NumberLiteral) return their value directly, with no further evaluation step.
- **Compound** expressions (CallExpression) are evaluated by first evaluating their children (the operands), then combining the results (applying the operator).

This two-step process -- evaluate the operands, then apply the operator -- is called **applicative-order evaluation** and is the evaluation strategy used by most mainstream languages.

Now we define `applyCalculatorOperator`, which handles each of the four operators:

```javascript
function applyCalculatorOperator(operator, args) {
  switch (operator) {
    case "+": {
      // Sum all arguments; identity is 0
      let result = 0;
      for (const arg of args) {
        result = result + arg;
      }
      return result;
    }

    case "-": {
      // Zero arguments: error
      // One argument: negate
      // Two or more: subtract all from the first
      if (args.length === 0) {
        throw new TypeError("- requires at least 1 argument");
      }
      if (args.length === 1) {
        return -args[0];
      }
      let result = args[0];
      for (let i = 1; i < args.length; i++) {
        result = result - args[i];
      }
      return result;
    }

    case "*": {
      // Multiply all arguments; identity is 1
      let result = 1;
      for (const arg of args) {
        result = result * arg;
      }
      return result;
    }

    case "/": {
      // Zero arguments: error
      // One argument: multiplicative inverse
      // Two or more: divide the first by all subsequent
      if (args.length === 0) {
        throw new TypeError("/ requires at least 1 argument");
      }
      if (args.length === 1) {
        return 1 / args[0];
      }
      let result = args[0];
      for (let i = 1; i < args.length; i++) {
        if (args[i] === 0) {
          throw new Error("division by zero");
        }
        result = result / args[i];
      }
      return result;
    }

    default:
      throw new TypeError(`unknown operator: '${operator}'`);
  }
}
```

Each operator has a distinct behavior:

- `+` sums all arguments. With no arguments, it returns `0` (the additive identity).
- `*` multiplies all arguments. With no arguments, it returns `1` (the multiplicative identity).
- `-` with one argument negates; with multiple arguments, it subtracts all but the first from the first.
- `/` with one argument returns the inverse; with multiple arguments, it divides the first by the rest sequentially.

Let us verify the evaluator on the examples from section 3.4.1:

```javascript
evaluateCalculator(
  parseCalculator(tokenizeCalculator("(+ 1 2)"))
);  // 3

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(* (+ 1 2) 4)"))
);  // 12

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(- 10 3 2)"))
);  // 5

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(/ 20 2 2)"))
);  // 5

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(- 3)"))
);  // -3

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(/ 10)"))
);  // 0.1

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(+)"))
);  // 0

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(*)"))
);  // 1

evaluateCalculator(
  parseCalculator(tokenizeCalculator("(- 100 (* 7 (+ 8 (/ -12 -3))))"))
);  // 16
```

### 3.4.6 The Complete Pipeline

The full interpreter composes three stages into a single function:

```javascript
function runCalculator(source) {
  const tokens = tokenizeCalculator(source);
  const ast = parseCalculator(tokens);
  return evaluateCalculator(ast);
}
```

Each stage has a clear responsibility:

1. **`tokenizeCalculator(source)`** -- splits the source string into an array of tokens.
2. **`parseCalculator(tokens)`** -- converts the token array into an AST.
3. **`evaluateCalculator(ast)`** -- walks the AST and computes a numeric result.

The pipeline is linear and composable. Each function takes the output of the previous one and produces the input for the next:

```
"(+ 1 (* 2 3))"  -->  tokenize  -->  ["(", "+", 1, "(", "*", 2, 3, ")", ")"]
                                              |
                                              v
                                     parse  -->  { type: "CallExpression",
                                                    operator: "+",
                                                    operands: [
                                                      { type: "NumberLiteral", value: 1 },
                                                      { type: "CallExpression",
                                                        operator: "*",
                                                        operands: [ ... ] } ] }
                                              |
                                              v
                                   evaluate  -->  7
```

The `runCalculator` function brings it all together:

```javascript
runCalculator("(+ 1 2)");              // 3
runCalculator("(* (+ 1 2) 4)");        // 12
runCalculator("(- 10 3 2)");           // 5
runCalculator("(/ 20 2 2)");           // 5
runCalculator("(- 100 (* 7 (+ 8 (/ -12 -3))))");  // 16
runCalculator("42");                    // 42
runCalculator("(+)");                   // 0
runCalculator("(*)");                   // 1
runCalculator("(- 3)");                // -3
runCalculator("(/ 10)");               // 0.1
```

This three-stage architecture -- tokenize, parse, evaluate -- is the standard structure of interpreters and compilers. The Calculator language is small enough that each stage is a single function, but the same architecture scales to real languages. The tokenizer grows to handle more token types, the parser grows to handle more syntactic forms, and the evaluator grows to handle more expression types. But the pipeline remains the same.

### 3.4.7 Error Handling

A good interpreter provides informative error messages. Our Calculator interpreter can encounter errors at each stage of the pipeline.

**Tokenizer errors** occur when the source contains characters that are not part of the language:

```javascript
tokenizeCalculator("(+ 1 & 2)");
// SyntaxError: unexpected character: '&'

tokenizeCalculator("2.3.4");
// SyntaxError: invalid numeral: 2.3.4
```

**Parser errors** occur when the tokens do not form a valid expression structure:

```javascript
runCalculator(")");
// SyntaxError: unexpected token: ')'

runCalculator("(+ 1 2");
// SyntaxError: missing closing ')'

runCalculator("+");
// SyntaxError: unexpected token: '+'

runCalculator("(1 2 3)");
// SyntaxError: expected operator after '(', got '1'
```

**Evaluation errors** occur when a syntactically valid expression cannot be computed:

```javascript
runCalculator("(-)");
// TypeError: - requires at least 1 argument

runCalculator("(/)");
// TypeError: / requires at least 1 argument

runCalculator("(/ 10 0)");
// Error: division by zero

runCalculator("(% 1 2)");
// TypeError: unknown operator: '%'
```

**A REPL with error recovery.** The read-eval-print loop wraps the entire pipeline in a `try/catch` so that errors are reported to the user without terminating the session:

```javascript
function calculatorRepl(source) {
  try {
    const result = runCalculator(source);
    return result;
  } catch (e) {
    if (e instanceof SyntaxError) {
      return `Syntax error: ${e.message}`;
    } else if (e instanceof TypeError) {
      return `Type error: ${e.message}`;
    } else {
      return `Error: ${e.message}`;
    }
  }
}

calculatorRepl("(+ 1 2)");       // 3
calculatorRepl(")");              // "Syntax error: unexpected token: ')'"
calculatorRepl("(+ 1 2");        // "Syntax error: missing closing ')'"
calculatorRepl("(-)");           // "Type error: - requires at least 1 argument"
calculatorRepl("(/ 10 0)");      // "Error: division by zero"
```

This error-handling structure is a direct application of exception propagation (covered in section 3.3). Errors thrown deep inside the recursive parser or evaluator propagate up through the call stack to the top-level handler. The handler does not need to know how many levels deep the error occurred -- it simply catches the exception and reports it.

### 3.4.8 Extending the Interpreter

The Calculator interpreter is designed for extension. Adding a new operator requires changes in only two places: the `isOperator` function (so the parser accepts it) and the `applyCalculatorOperator` function (so the evaluator computes it).

For example, to add a `min` operator that returns the minimum of its arguments:

```javascript
// Step 1: Update isOperator to recognize "min"
// (In our design, operator tokens are single characters, so we would
// need to extend the tokenizer to recognize multi-character operators.
// For now, we show the evaluator change.)

// Step 2: Add a case to applyCalculatorOperator
function applyCalculatorOperatorExtended(operator, args) {
  switch (operator) {
    case "+":
    case "-":
    case "*":
    case "/":
      return applyCalculatorOperator(operator, args);
    case "min": {
      if (args.length === 0) {
        throw new TypeError("min requires at least 1 argument");
      }
      let result = args[0];
      for (let i = 1; i < args.length; i++) {
        if (args[i] < result) {
          result = args[i];
        }
      }
      return result;
    }
    default:
      throw new TypeError(`unknown operator: '${operator}'`);
  }
}
```

To support multi-character operators like `min`, the tokenizer needs a small modification. Rather than treating every non-parenthesis, non-number token as a single character, we collect sequences of letters into operator names:

```javascript
// Extended tokenizer that recognizes multi-character names
function tokenizeCalculatorExtended(source) {
  const tokens = [];
  let i = 0;

  while (i < source.length) {
    const ch = source[i];

    if (ch === " " || ch === "\t" || ch === "\n" || ch === "\r") {
      i = i + 1;
      continue;
    }

    if (ch === "(" || ch === ")") {
      tokens.push(ch);
      i = i + 1;
      continue;
    }

    // Arithmetic operator symbols
    if (ch === "+" || ch === "-" || ch === "*" || ch === "/") {
      tokens.push(ch);
      i = i + 1;
      continue;
    }

    // Multi-character names (like "min", "max")
    if (isLetter(ch)) {
      let name = "";
      while (i < source.length && isLetter(source[i])) {
        name = name + source[i];
        i = i + 1;
      }
      tokens.push(name);
      continue;
    }

    // Numbers
    if (isDigit(ch) || (ch === "." && i + 1 < source.length && isDigit(source[i + 1]))) {
      let numStr = "";
      while (i < source.length && (isDigit(source[i]) || source[i] === ".")) {
        numStr = numStr + source[i];
        i = i + 1;
      }
      const value = parseFloat(numStr);
      if (isNaN(value)) {
        throw new SyntaxError(`invalid numeral: ${numStr}`);
      }
      tokens.push(value);
      continue;
    }

    throw new SyntaxError(`unexpected character: '${ch}'`);
  }

  return tokens;
}

function isLetter(ch) {
  return (ch >= "a" && ch <= "z") || (ch >= "A" && ch <= "Z");
}
```

The parser's `isOperator` check would then be expanded to include named operators:

```javascript
function isOperator(token) {
  return (
    token === "+" || token === "-" || token === "*" || token === "/" ||
    token === "min" || token === "max"
  );
}
```

This extensibility is a direct benefit of the three-stage pipeline architecture. Each stage has a narrow, well-defined responsibility, so changes to one stage (adding a new operator) require minimal changes to the others.

### 3.4.9 Read-Eval-Print Loop

The original Composing Programs text presents a read-eval-print loop (REPL) as the standard interface for an interpreter. In JavaScript, we can build a simple REPL using the standard input:

```javascript
const readline = require("readline");

function startCalculatorRepl() {
  const rl = readline.createInterface({
    input: process.stdin,
    output: process.stdout,
    prompt: "calc> "
  });

  rl.prompt();

  rl.on("line", (line) => {
    const trimmed = line.trim();
    if (trimmed === "") {
      rl.prompt();
      return;
    }
    try {
      const result = runCalculator(trimmed);
      console.log(result);
    } catch (e) {
      if (e instanceof SyntaxError) {
        console.log(`SyntaxError: ${e.message}`);
      } else if (e instanceof TypeError) {
        console.log(`TypeError: ${e.message}`);
      } else {
        console.log(`Error: ${e.message}`);
      }
    }
    rl.prompt();
  });

  rl.on("close", () => {
    console.log("Calculation completed.");
  });
}

// startCalculatorRepl();  // Uncomment to run interactively
```

An interactive session would look like:

```
calc> (+ 1 2 3)
6
calc> (* 2 (+ 3 4))
14
calc> (- 10 1 2 3)
4
calc> (/ 1 0)
Error: division by zero
calc> )
SyntaxError: unexpected token: ')'
calc> (+ 2 (/ 4 8))
2.5
```

The REPL catches errors and reports them, then prompts for the next input. This lets users revise their expressions without restarting the interpreter. The structure -- read input, evaluate, print result, handle errors, loop -- is the same structure used by the Node.js REPL, the Python REPL, and the browser console.

### 3.4.10 Dispatching on Type

A key design pattern in the Calculator interpreter (and in interpreters generally) is **dispatching on type**: the evaluator examines the kind of expression it has received and handles each kind differently.

In our Calculator, there are only two types of expressions, so the dispatch is simple:

```javascript
function evaluateCalculator(ast) {
  if (ast.type === "NumberLiteral") {
    return ast.value;
  }
  if (ast.type === "CallExpression") {
    const args = ast.operands.map(evaluateCalculator);
    return applyCalculatorOperator(ast.operator, args);
  }
  throw new Error(`unknown AST node type: '${ast.type}'`);
}
```

This pattern scales. When we add new expression types -- variable names, function definitions, conditionals -- we add new `if` branches (or a `switch` statement). Each branch handles one syntactic form:

- **Self-evaluating** expressions (numbers, strings, booleans) return their own value.
- **Names** are looked up in an environment.
- **Call expressions** recursively evaluate operands, then apply the operator.
- **Special forms** (like `if` or `define`) have their own evaluation rules.

The general `calc_eval` function from the original text has exactly this structure. Our `evaluateCalculator` is a minimal version with only two cases. Section 3.5 will expand this pattern to handle variables, environments, and function definition -- the ingredients needed for a Turing-complete language.

## Python/Scheme vs JavaScript Notes

| Topic | Python / Scheme (Original) | JavaScript (This Adaptation) |
|---|---|---|
| **Expression representation** | Scheme `Pair` linked lists (e.g., `Pair('+', Pair(1, Pair(2, nil)))`) | Plain objects with `type` field (e.g., `{ type: "CallExpression", operator: "+", operands: [...] }`) |
| **Tokenizer output** | Returns Python list of mixed types: strings for parens/operators, `int`/`float` for numbers | Returns JavaScript array of mixed types: strings for parens/operators, `number` for numerals |
| **Parser input model** | Uses a `Buffer` abstraction that spans multiple lines; `scheme_read` and `read_tail` are mutually recursive | Takes a flat token array with a mutable position index; single `parseExpr` function handles both atoms and lists |
| **Pair / list class** | `Pair` class with `first`, `second`, `map`, and Python sequence protocol | No Pair class needed; operands stored as a JavaScript `Array` |
| **Operator application** | `reduce` with `operator.add`, `operator.mul`, etc. from Python's standard library | `for...of` loops accumulating into a result variable (JavaScript has no built-in `reduce` for this use case outside of `Array.reduce`) |
| **Variable-arity operators** | `+` and `*` use `reduce` with identity values `0` and `1`; `-` and `/` check `len(args)` | Same logic using `args.length` and `switch` statement |
| **Self-evaluating check** | `type(exp) in (int, float)` | `ast.type === "NumberLiteral"` (dispatch on AST node type, not on JavaScript runtime type) |
| **REPL implementation** | `while True` loop with `buffer_input()`, `scheme_read`, `calc_eval` | `readline` module with event-based `rl.on("line", ...)` callback, or synchronous `calculatorRepl(source)` function |
| **Error types** | `SyntaxError`, `TypeError`, `ValueError`, `ZeroDivisionError` (Python built-ins) | `SyntaxError`, `TypeError`, `Error` (JavaScript built-ins; no `ValueError` or `ZeroDivisionError`) |
| **Division by zero** | Python raises `ZeroDivisionError` automatically for `1 / 0` | JavaScript returns `Infinity` for `1 / 0`; our interpreter must explicitly check and throw |
| **Tokenizer architecture** | `tokenize_line` processes one line; `Buffer` collects tokens across lines | `tokenizeCalculator` processes the entire source string at once (no multi-line buffer needed for Calculator) |
| **Metalinguistic abstraction** | "We now embark on a tour of the technology by which languages are established in terms of other languages" | Same concept; we build a language interpreter *in* JavaScript rather than *in* Python |
