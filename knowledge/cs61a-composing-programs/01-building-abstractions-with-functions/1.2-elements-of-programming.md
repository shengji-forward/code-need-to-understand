## Key Concepts

- Every powerful language provides three mechanisms: **primitive expressions**, **means of combination**, and **means of abstraction**.
- **Expressions** (arithmetic, comparison, logical) are the simplest building blocks and evaluate to values.
- **Call expressions** apply functions to arguments; JavaScript uses a call-expression model identical to most languages — `fn(arg1, arg2)`.
- **Names and environments** bind identifiers to values using `const` and `let`; the environment is the memory that tracks these bindings.
- **Nested expression evaluation** is recursive: evaluate operator and operands first, then apply — producing an expression tree.
- **Pure functions** return values with no side effects; **non-pure functions** (like `console.log`) produce side effects and may return `undefined`.

## Content

### The Three Mechanisms of a Language

A programming language is more than a way to instruct a computer. It is a framework for organizing ideas about computation, and programs must be written for people to read first and machines second.

Every powerful language provides three mechanisms for combining simple ideas into complex ones:

1. **Primitive expressions and statements** — the simplest building blocks the language provides.
2. **Means of combination** — how compound elements are built from simpler ones.
3. **Means of abstraction** — how compound elements can be named and manipulated as units.

In programming we deal with two kinds of elements: **functions** and **data**. (Soon we will discover they are not so distinct.) Any powerful language should describe primitive data, primitive functions, and methods for combining and abstracting both.

---

### 1.2.1 Expressions

We begin with primitive expressions. A number is one kind of primitive expression:

```javascript
42;
// 42
```

Expressions representing numbers may be combined with mathematical operators to form compound expressions:

```javascript
-1 - -1;
// 0

1 / 2 + 1 / 4 + 1 / 8 + 1 / 16 + 1 / 32 + 1 / 64 + 1 / 128;
// 0.9921875
```

These mathematical expressions use **infix notation**, where the operator (`+`, `-`, `*`, `/`, `%`) appears between the operands. JavaScript also supports comparison and logical expressions:

```javascript
// Comparison expressions
3 > 2;
// true

5 === 5;
// true

4 !== 3;
// true

// Logical expressions
true && false;
// false

true || false;
// true

!true;
// false
```

Rather than enumerate every expression form at once, we will introduce new forms as we go, alongside the language features they support.

---

### 1.2.2 Call Expressions

The most important kind of compound expression is a **call expression**, which applies a function to some arguments. Recall from algebra that a function maps input arguments to an output value.

```javascript
Math.max(7.5, 9.5);
// 9.5
```

This call expression has subexpressions: the **operator** is the expression preceding the parentheses, which enclose a comma-delimited list of **operand** expressions.

The operator specifies a **function**. When this call expression is evaluated, we say that `Math.max` is **called** with **arguments** 7.5 and 9.5, and **returns** a **value** of 9.5.

The order of arguments matters. For instance, `Math.pow` raises its first argument to the power of its second:

```javascript
Math.pow(100, 2);
// 10000

Math.pow(2, 100);
// 1.2676506002282294e+30
```

Function notation has three principal advantages over infix notation:

**First**, functions may take an arbitrary number of arguments:

```javascript
Math.max(1, -2, 3, -4);
// 3
```

No ambiguity can arise, because the function name always precedes its arguments.

**Second**, function notation extends straightforwardly to **nested expressions**, where the elements are themselves compound expressions. The structure of the nesting is entirely explicit in the parentheses:

```javascript
Math.max(Math.min(1, -2), Math.min(Math.pow(3, 5), -4));
// -2
```

There is no limit (in principle) to the depth of such nesting. However, humans quickly get confused by multi-level nesting. An important role for you as a programmer is to structure expressions so that they remain interpretable.

**Third**, all mathematical complexity — multiplication between terms, exponents as superscripts, division as horizontal bars — can be unified via call expression notation. While JavaScript supports common mathematical operators using infix notation (like `+` and `-`), any operator can be expressed as a function:

```javascript
// Using infix operators
3 + 4;
// 7

// Using the functional equivalent (less common in JS, but available)
const add = (a, b) => a + b;
add(3, 4);
// 7
```

### 1.2.3 Importing Library Functions

JavaScript defines a very large number of functions but does not make all of them available by default. Instead, it organizes them into modules. The built-in `Math` object provides a variety of familiar mathematical functions:

```javascript
Math.sqrt(256);
// 16

Math.abs(-5);
// 5

Math.round(3.7);
// 4

Math.floor(3.7);
// 3
```

In Node.js, additional modules are loaded using ES module `import` syntax. For example, the `path` module provides utilities for working with file paths:

```javascript
import path from 'path';

path.join('/users', 'docs', 'file.txt');
// '/users/docs/file.txt'
```

Or named imports from a module:

```javascript
import { readFile, writeFile } from 'fs/promises';

// readFile and writeFile are now available as names
```

The `Math` object is always available globally — no import needed. It acts as a namespace that groups related functions, similar to how Python uses modules. Once a function is available (either globally or via import), it can be called multiple times.

There is no practical difference between using operator symbols (`+`, `-`) and their functional equivalents. Conventionally, most programmers use symbols and infix notation for simple arithmetic.

### 1.2.4 Names and the Environment

A critical aspect of a programming language is the means it provides for using **names** to refer to computational objects. If a value has been given a name, we say the name **binds** to the value.

In JavaScript, we establish new bindings using `const` (for values that won't change) or `let` (for values that may change):

```javascript
const radius = 10;
radius;
// 10

2 * radius;
// 20
```

```javascript
const pi = Math.PI;
pi * 71 / 223;
// 1.0002380197528042
```

Assignment is our simplest means of **abstraction**, for it allows us to use simple names to refer to the results of compound operations. In this way, complex programs are constructed by building, step by step, computational objects of increasing complexity.

The possibility of binding names to values and later retrieving those values means the interpreter must maintain some sort of memory that keeps track of names, values, and bindings. This memory is called an **environment**.

Names can also be bound to functions:

```javascript
const f = Math.max;
f(2, 3, 4);
// 4
```

With `let`, a name can be rebound to a new value:

```javascript
let x = 2;
x = x + 1;
x;
// 3
```

When executing an assignment, JavaScript evaluates the expression to the right of `=` before changing the binding to the name on the left. Therefore, you can refer to a name in the right-side expression, even if it is the name being reassigned.

```javascript
let y = 5;
y = y * 2;
y;
// 10
```

JavaScript supports destructuring assignment, which binds multiple names at once from an array or object:

```javascript
const [area, circumference] = [
  Math.PI * radius * radius,
  2 * Math.PI * radius,
];
// area: 314.1592653589793
// circumference: 62.83185307179586
```

With destructuring, all expressions on the right are evaluated before any names on the left are bound. This makes it possible to swap two values in a single statement:

```javascript
let a = 3;
let b = 4.5;
[a, b] = [b, a];
a;
// 4.5
b;
// 3
```

Changing the value of one name does not affect other names. Below, even though `area` was defined in terms of `radius`, the value of `area` has not changed when `radius` changes:

```javascript
let currentRadius = 10;
let currentArea = Math.PI * currentRadius * currentRadius;
currentRadius = 11;
currentArea;
// 314.1592653589793  (unchanged!)

// Updating area requires another assignment
currentArea = Math.PI * currentRadius * currentRadius;
currentArea;
// 380.132711084365
```

**`const` vs `let`.** Prefer `const` by default — it signals that a binding will not change. Use `let` only when you genuinely need to reassign. This convention makes your intent clear to readers.

### 1.2.5 Evaluating Nested Expressions

One of our goals is to isolate issues about thinking procedurally. In evaluating nested call expressions, the interpreter itself follows a procedure.

To evaluate a call expression, JavaScript follows this procedure:

1. **Evaluate the operator (callee)** — determine the function to call.
2. **Evaluate the operands (arguments) left-to-right** — each argument subexpression is evaluated in order.
3. **Apply** the function to the resulting argument values.

This procedure is **recursive** in nature — it includes, as one of its steps, the need to invoke the rule itself.

For example, evaluating:

```javascript
Math.pow(2, 1 + 10) - Math.pow(2, 5);
// 2016
```

requires that this evaluation procedure be applied multiple times. We can visualize the hierarchical structure of this process as an **expression tree**:

```
       (-)
      /   \
   pow    pow
   / \    / \
  2  (+)  2   5
    /  \
   1   10
```

In computer science, trees conventionally grow from the top down. The objects at each point are called **nodes**. Evaluating the root requires first evaluating the branches (subexpressions). The **leaf** nodes represent primitive values or functions. The interior nodes contain the call expression and its result. Values percolate upward from terminal nodes, combining at higher and higher levels.

The repeated application of step 1 brings us to the point where we evaluate primitive expressions — numerals and names:

- A **numeral** evaluates to the number it names.
- A **name** evaluates to the value associated with that name in the current environment.

Notice the important role of **environment** in determining the meaning of symbols. It is meaningless to speak of the value of an expression like:

```javascript
add(x, 1);
```

without specifying any information about the environment that would provide meaning for the name `x` (or even `add`). Environments provide the context in which evaluation takes place.

This evaluation procedure handles call expressions, numerals, and names — but not assignment statements. Executing:

```javascript
const x = 3;
```

does not return a value; its purpose is to bind a name to a value. In general, **statements** are not evaluated but **executed**; they do not produce a value but instead make some change. Each type of expression or statement has its own evaluation or execution procedure.

### 1.2.6 The Non-Pure Print Function

Throughout this text, we distinguish between two types of functions.

**Pure functions.** Functions have some input (their arguments) and return some output (the result of applying them).

```javascript
Math.abs(-2);
// 2
```

`Math.abs` is **pure**. Pure functions have the property that applying them has no effects beyond returning a value. Moreover, a pure function must always return the same value when called twice with the same arguments.

**Non-pure functions.** In addition to returning a value, applying a non-pure function can generate **side effects** — changes to the state of the interpreter or computer. A common side effect is producing output via `console.log`:

```javascript
console.log(1, 2, 3);
// 1 2 3
```

While `console.log` and `Math.abs` may appear similar in these examples, they work in fundamentally different ways. The value that `console.log` returns is always `undefined`. The Node.js REPL *does* display `undefined` for expression results, which makes the return value visible:

```javascript
> console.log(1, 2, 3)
1 2 3
undefined
```

The `undefined` on the last line is the REPL showing the return value of `console.log`. In the case of `console.log`, the function itself is printing output as a **side effect** of being called.

A nested expression of calls to `console.log` highlights the non-pure character of the function:

```javascript
console.log(console.log(1), console.log(2));
// 1
// 2
// undefined undefined
```

If you find this output unexpected, draw an expression tree to clarify why evaluating this expression produces this peculiar output. Each inner `console.log` call prints its argument as a side effect and returns `undefined`. The outer `console.log` then receives two `undefined` values as arguments and prints them.

Be careful with `console.log`! The fact that it returns `undefined` means it **should not** be used as the expression in an assignment:

```javascript
const two = console.log(2);
// 2

console.log(two);
// undefined
```

Pure functions are restricted in that they cannot have side effects or change behavior over time. Imposing these restrictions yields substantial benefits:

1. **Reliable composition.** Pure functions can be composed into compound call expressions reliably. As shown above, `console.log` does not return a useful result when used in an operand expression. By contrast, functions like `Math.max`, `Math.pow`, and `Math.sqrt` work effectively in nested expressions.

2. **Easier testing.** A list of arguments will always lead to the same return value, which can be compared to an expected result.

3. **Concurrency.** Pure functions are essential for writing concurrent programs, where multiple call expressions may be evaluated simultaneously.

For these reasons, we concentrate heavily on creating and using pure functions. `console.log` is used only so that we can see intermediate results of computations.

## Python vs JavaScript Notes

| Topic | Python | JavaScript |
|---|---|---|
| **Division** | `/` always returns a float (`1/2` is `0.5`) | `/` returns a float too (`1/2` is `0.5`); integer division requires `Math.floor(a/b)` |
| **Exponentiation** | `pow(2, 10)` or `2 ** 10` | `Math.pow(2, 10)` or `2 ** 10` |
| **Modulo** | `a % b` | `a % b` (same syntax, but JS `%` preserves sign of dividend; Python preserves sign of divisor) |
| **Integer type** | Separate `int` type; arbitrary precision | Single `Number` type (IEEE 754 double); `BigInt` for arbitrary precision (`10n`) |
| **Variable declaration** | Simple assignment: `x = 5` | Requires keyword: `const x = 5` or `let x = 5` |
| **Rebinding** | Always allowed: `x = x + 1` | `let` allows reassignment; `const` does not |
| **Print / output** | `print()` returns `None` | `console.log()` returns `undefined` |
| **Nothing value** | `None` | `undefined` (also `null`, but `undefined` is the default "no value") |
| **Equality** | `==` for value, `is` for identity | `===` for strict equality (value + type), `==` for loose (with coercion) |
| **Math library** | `import math; math.sqrt(4)` | `Math.sqrt(4)` (built-in global, no import needed) |
| **Library imports** | `from math import sqrt` or `import math` | `import { sqrt } from 'module'` or `import * as math from 'module'` |
| **Swapping** | `a, b = b, a` | `[a, b] = [b, a]` (destructuring assignment) |
| **Multiple assignment** | `x, y = 1, 2` | `const [x, y] = [1, 2]` (destructuring) |
| **Truthiness** | `False`, `None`, `0`, `""`, `[]`, `{}` are falsy | `false`, `undefined`, `null`, `0`, `""`, `NaN` are falsy; `[]` and `{}` are **truthy** |
| **Logical operators** | `and`, `or`, `not` (keywords) | `&&`, `||`, `!` (symbols) |
| **REPL output** | REPL prints the repr of every expression's value | Node REPL prints the result of expressions; `undefined` is shown with `undefined` marker |
| **Statement vs expression** | Assignment is a statement (no value) | Assignment is an expression (returns the assigned value with `let`/`var`, but not `const` in strict mode) |
