## Key Concepts

- **Function definitions** bind a name to a compound operation, enabling reuse and abstraction beyond what simple name-value bindings provide.
- **Environments** are sequences of frames (global and local) that determine how names resolve to values during evaluation.
- **Local frames** are created each time a function is called, binding formal parameters to arguments and keeping those names isolated from other frames.
- **Scope** limits the accessibility of parameter names to the body of the function that defines them, preventing name collisions across function calls.
- **Functions as abstractions** mean callers depend only on a function's domain, range, and intent -- not its implementation details.
- **Operators** are shorthand for function calls; understanding this equivalence clarifies evaluation order and nesting.

## Content

### Function Definitions

Every powerful programming language provides three foundational mechanisms: primitive expressions and operations, a means of combining operations, and a means of abstracting operations by naming them. Function definitions go further than simple assignment -- they let us bind a name to a *compound operation* so it can be used as a unit.

Consider the idea of "squaring": to square something, multiply it by itself. In JavaScript:

```javascript
function square(x) {
  return x * x;
}
```

This is a **function declaration**. It creates a user-defined function and binds the name `square` to it. The identifier `x` is a **formal parameter** -- a placeholder name for the value that will be supplied when the function is called. The body `return x * x` specifies what the function computes; it is not evaluated until the function is actually invoked.

Having defined `square`, we can call it:

```javascript
square(21);           // 441
square(2 + 5);        // 49
square(square(3));     // 81
```

We can also use `square` as a building block inside other functions:

```javascript
function sumSquares(x, y) {
  return square(x) + square(y);
}

sumSquares(3, 4);     // 25
```

User-defined functions are used identically to built-in functions. Looking at `sumSquares`, there is no way to tell whether `square` is built into the language, imported from a module, or defined by the user.

**Rebinding names.** Both function declarations and variable assignments bind names. An existing binding can be overwritten:

```javascript
function g() {
  return 1;
}
g();          // 1
g = 2;
console.log(g);  // 2
g = function(h, i) {
  return h + i;
};
g(1, 2);      // 3
```

Note: reassigning a name that was originally declared with `function` is allowed, but overwriting functions with non-function values will cause errors if you later try to call the name.

### Environments

As programs grow, the meaning of names becomes non-trivial. What happens if a parameter has the same name as a global variable? Can two functions share parameter names without interference? To answer these questions precisely, we need the concept of an **environment**.

An environment is a sequence of **frames**, each of which contains **bindings** that associate names with values. There is a single **global frame** that holds top-level declarations. When a function is called, a new **local frame** is created for that invocation.

```
Global Frame
  square  -> func square(x)
  sumSquares -> func sumSquares(x, y)
```

Each function is represented by its intrinsic name and formal parameters. The name bound in a frame is the one used during lookup; the intrinsic name is informational and does not drive evaluation.

**Name Evaluation.** A name evaluates to the value bound to that name in the *earliest* (innermost) frame of the current environment in which that name is found. Local frames are checked before the global frame.

### Calling User-Defined Functions

When the interpreter evaluates a call expression whose operator names a user-defined function, it follows these steps:

1. Evaluate the operator and operand subexpressions.
2. Create a new **local frame** in which the formal parameters are bound to the corresponding argument values.
3. Evaluate the function body in the environment that starts with this new local frame.

This means the body's environment has two frames: the local frame (containing parameter bindings) followed by the global frame (containing everything else). Each function call gets its own independent local frame.

Let's trace `square(-2)` step by step:

```
1. square is defined:
   Global Frame
     square -> func square(x)

2. square(-2) is called; a new local frame is created:
   Global Frame
     square -> func square(x)
   square() Frame
     x -> -2

3. The body `return x * x` is evaluated.
   x is looked up: found in the local frame as -2.
   Result: (-2) * (-2) = 4
   Return value: 4
```

### Example: Calling a User-Defined Function

Let us trace the evaluation of `sumSquares(5, 12)` with both `square` and `sumSquares` defined in the global frame.

```javascript
function square(x) {
  return x * x;
}

function sumSquares(x, y) {
  return square(x) + square(y);
}

const result = sumSquares(5, 12);  // 169
```

Step-by-step:

1. `sumSquares` is looked up in the global frame and found to be a user-defined function.
2. A local frame for `sumSquares` is created, binding `x` to `5` and `y` to `12`.
3. The body `square(x) + square(y)` is evaluated:
   - **Operand 1:** `square(x)` where `x` is `5`. A new local frame for `square` binds `x` to `5`. The body evaluates to `25`.
   - **Operand 2:** `square(y)` where `y` is `12`. A *separate* new local frame for `square` binds `x` to `12`. The body evaluates to `144`.
4. Addition is applied: `25 + 144 = 169`.

Key insight: three local frames exist during this computation, and two of them bind the name `x` to different values. Each function call creates its own isolated local frame, so the `x` in `sumSquares` and the `x` in each `square` call do not interfere.

### Local Names

The choice of parameter names inside a function should not affect the function's behavior. These two definitions are equivalent:

```javascript
function square(x) {
  return x * x;
}

function square(y) {
  return y * y;
}
```

This principle has a direct consequence: parameter names are **local** to the function body. The `x` inside `square` is completely independent of the `x` inside `sumSquares`. Each function call creates its own local frame, and bindings in different frames are unrelated.

The **scope** of a local name is limited to the body of the function that defines it. When a name is no longer accessible, it is *out of scope*. In JavaScript, `let` and `const` declarations are block-scoped (to the nearest enclosing `{}`), while `var` is function-scoped. For function parameters, the scope is the function body.

```javascript
function sumSquares(x, y) {
  // x and y are in scope here
  return square(x) + square(y);
  // x and y go out of scope when the function returns
}
// x and y are not accessible here
```

### Choosing Names

Well-chosen function and parameter names are essential for readability. While names are interchangeable to the interpreter, they are critical for human understanding. Here are conventions adapted for JavaScript:

1. **Function names** use `camelCase` (e.g., `sumSquares`, `computeArea`). This follows standard JavaScript style.
2. **Function names** should evoke either the operation performed (e.g., `print`, `add`, `square`) or the quantity produced (e.g., `max`, `abs`, `sum`).
3. **Parameter names** use `camelCase` and are typically short, descriptive words (e.g., `radius`, `width`, `message`).
4. **Parameter names** should describe the *role* of the parameter in the function, not just its type.
5. **Single-letter names** (e.g., `x`, `y`, `i`) are acceptable when their role is obvious from context. Avoid `l` (lowercase L), `O` (uppercase O), or `I` (uppercase I) to prevent confusion with numerals.

Consistent naming conventions make code easier to read and maintain across a team.

### Functions as Abstractions

The `sumSquares` function is defined in terms of `square`, but it relies only on the *relationship* that `square` establishes between its input and its output. The caller does not need to know *how* squaring is implemented.

This means `sumSquares` treats `square` as a **functional abstraction**. Any function that takes a number and returns its square would work equally well:

```javascript
function square(x) {
  return x * x;
}

// This alternative implementation is indistinguishable to callers:
function square(x) {
  return x * (x - 1) + x;
}
```

Both versions produce the same output for every input. A well-designed function hides its implementation details behind its interface.

**Aspects of a Functional Abstraction.** Every function can be described by three attributes:

- **Domain:** the set of arguments it can accept (e.g., any single number).
- **Range:** the set of values it can return (e.g., any non-negative number).
- **Intent:** the relationship it computes between inputs and output (e.g., the output is the square of the input).

These attributes say *what* the function does, not *how*. Understanding a function through its domain, range, and intent is the key to using it correctly without needing to inspect its body.

### Operators

Arithmetic operators (`+`, `-`, `*`, `/`, `%`) are shorthand for function calls. When you write:

```javascript
2 + 3   // 5
```

you can think of it as:

```javascript
add(2, 3)   // 5
```

where `add` is a function that performs addition. Operators follow standard mathematical precedence rules:

```javascript
2 + 3 * 4 + 5;          // 19  (multiplication before addition)
// Equivalent to: add(add(2, mul(3, 4)), 5)
```

Parentheses override precedence or make grouping explicit:

```javascript
(2 + 3) * (4 + 5);      // 45
// Equivalent to: mul(add(2, 3), add(4, 5))
```

**Division in JavaScript.** Unlike Python, JavaScript has only one division operator `/`, which always produces a floating-point result:

```javascript
5 / 4;     // 1.25
8 / 4;     // 2
```

To achieve Python-style floor division (`//`), use `Math.floor`:

```javascript
Math.floor(5 / 4);     // 1
Math.floor(-5 / 4);    // -1  (differs from Python's -2!)
```

For integer division that matches Python's behavior (floor toward negative infinity), use `Math.trunc` for positive numbers and be aware of the difference for negative numbers, or use this helper:

```javascript
function floorDiv(a, b) {
  return Math.floor(a / b);
}

floorDiv(5, 4);    // 1
floorDiv(-5, 4);   // -2  (matches Python's //)
```

JavaScript also provides the remainder operator `%` (which behaves like `Math.trunc`-based remainder) and the newer `Math.trunc` for truncation toward zero.

**Using operators idiomatically.** In JavaScript, prefer infix operators for simple arithmetic. Reserve function-style calls for when you need to pass arithmetic operations as values:

```javascript
const operations = {
  add: (a, b) => a + b,
  mul: (a, b) => a * b,
};

operations.add(2, 3);   // 5
operations.mul(3, 4);   // 12
```

## Python vs JavaScript Notes

| Topic | Python | JavaScript |
|---|---|---|
| **Function definition** | `def square(x):` with indented body | `function square(x) { ... }` with braces; also `const square = (x) => x * x;` for arrow functions |
| **Return statement** | `return expr` | `return expr;` (semicolon required) |
| **Naming convention** | `snake_case` for functions and variables (`sum_squares`) | `camelCase` for functions and variables (`sumSquares`) |
| **Division operators** | Two operators: `/` (true division, returns float) and `//` (floor division) | One operator: `/` (always float division); use `Math.floor(a / b)` for floor division |
| **Floor division direction** | `//` floors toward negative infinity (`-5 // 4` is `-2`) | `Math.floor(-5 / 4)` is `-2` (matches Python); `Math.trunc(-5 / 4)` is `-1` (truncates toward zero) |
| **Variable scoping** | Function-scoped; no block scoping for plain assignments | `let` and `const` are block-scoped; `var` is function-scoped |
| **Name rebinding** | Can freely rebind names that held functions to other types | Same, but may cause `TypeError: g is not a function` at call time |
| **Exponentiation** | `x ** 2` or `pow(x, 2)` | `x ** 2` (ES2016+) or `Math.pow(x, 2)` |
| **Modulo/remainder** | `%` is true modulo (result has sign of divisor): `-5 % 4` is `3` | `%` is remainder (result has sign of dividend): `-5 % 4` is `-1` |
| **Statement separator** | Newlines; semicolons optional | Semicolons or automatic semicolon insertion (ASI); best practice is to include them |
| **Function as value** | Functions are first-class objects; `square` references the function without calling it | Same; `square` is the function, `square(3)` calls it |
| **Built-in arithmetic functions** | `from operator import add, mul` to get function versions of operators | No standard `add`/`mul` functions; use operators directly or define your own |
| **Multiple return values** | `return a, b` returns a tuple | No tuple return; use arrays (`return [a, b]`) or destructuring (`const [x, y] = fn()`) |
