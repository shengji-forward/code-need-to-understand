## Key Concepts

- **Single responsibility** -- each function should have exactly one job, identifiable by a short name and describable in a single line of text.
- **DRY principle** (Don't Repeat Yourself) -- redundant logic should be extracted into a named function and reused, not copied and pasted.
- **Generality** -- functions should be defined broadly enough to cover related cases; special-case functions are often better expressed as general functions with default parameters.
- **Domain, range, and intent** describe *what* a function does (its inputs, outputs, and purpose) independent of *how* it is implemented; preconditions constrain valid inputs and side effects describe observable interactions beyond the return value.
- **JSDoc documentation** (`/** ... */`) serves as the JavaScript equivalent of Python docstrings, describing a function's purpose, parameters, and return value.
- **Default parameter values** let callers omit optional arguments, making general functions convenient for the common case.
- **Comments** (`//`) annotate code for human readers and are ignored by the JavaScript engine.

## Content

### Designing Functions

Functions are the primary medium for expressing computational processes. After understanding the formal properties of functions -- how they are defined, called, and evaluated -- the next question is: what makes a *good* function?

Fundamentally, the qualities of good functions all reinforce the idea that **functions are abstractions**. Three guiding principles apply:

1. **Each function should have exactly one job.** That job should be identifiable with a short name and characterizable in a single line of text. Functions that perform multiple jobs in sequence should be divided into multiple functions.

2. **Don't repeat yourself (DRY).** This central tenet of software engineering states that multiple fragments of code should not describe redundant logic. Instead, that logic should be implemented once, given a name, and applied multiple times. If you find yourself copying and pasting a block of code, you have probably found an opportunity for functional abstraction.

3. **Functions should be defined generally.** A `square` function is less general than a `pow` function that raises a number to an arbitrary exponent. When practical, prefer the more general form and supply specifics through arguments or default values.

These guidelines improve readability, reduce the number of errors, and often minimize the total amount of code written. Decomposing a complex task into concise functions is a skill that takes experience to master. JavaScript provides several features to support this effort.

### Documentation

A function definition should include documentation that describes what the function does. In Python this is called a *docstring* (a triple-quoted string inside the function body). In JavaScript, the equivalent is a **JSDoc comment** -- a block comment that begins with `/**` placed directly above the function declaration.

```javascript
/**
 * Compute the pressure in pascals of an ideal gas.
 * Applies the ideal gas law: https://en.wikipedia.org/wiki/Ideal_gas_law
 *
 * @param {number} v - Volume of gas, in cubic meters
 * @param {number} t - Absolute temperature in degrees kelvin
 * @param {number} n - Particles of gas
 * @returns {number} Pressure in pascals
 */
function pressure(v, t, n) {
  const k = 1.38e-23;  // Boltzmann's constant
  return (n * k * t) / v;
}
```

JSDoc has several advantages:

- The first sentence describes the job of the function in one line. The following lines describe arguments and clarify behavior.
- The `@param` tags document each parameter's name and meaning.
- The `@returns` tag describes the return value.
- Many editors (VS Code, WebStorm) display JSDoc inline as hover information, serving a similar role to Python's `help()`.

When writing JavaScript programs, include JSDoc for all but the simplest functions. Remember: code is written once but read many times.

**Comments.** Single-line comments in JavaScript begin with `//`. Everything from `//` to the end of the line is ignored by the engine and exists solely for human readers. In the example above, `// Boltzmann's constant` explains the meaning of `k`. Use comments to clarify *why* something is done, not just *what* is done -- the code itself should express the "what."

```javascript
const SPEED_OF_LIGHT = 299792458;  // meters per second
```

### Default Argument Values

A consequence of defining general functions is the introduction of additional arguments. Functions with many arguments can be awkward to call and difficult to read.

JavaScript lets you provide **default values** for parameters directly in the function header. When the caller omits an argument, the default value is used instead:

```javascript
/**
 * Compute the pressure in pascals of an ideal gas.
 *
 * @param {number} v - Volume of gas, in cubic meters
 * @param {number} t - Absolute temperature in degrees kelvin
 * @param {number} [n=6.022e23] - Particles of gas (default: one mole)
 * @returns {number} Pressure in pascals
 */
function pressure(v, t, n = 6.022e23) {
  const k = 1.38e-23;  // Boltzmann's constant
  return (n * k * t) / v;
}
```

The `=` symbol means two different things in this example. In the function header, `n = 6.022e23` does *not* perform assignment -- it declares a default value that is used when `pressure` is called without a third argument. By contrast, the `const k = 1.38e-23` inside the body is a normal binding.

```javascript
pressure(1, 273.15);                // 2269.974834  (uses default n)
pressure(1, 273.15, 3 * 6.022e23);  // 6809.924502  (overrides default n)
```

The function is defined to accept three arguments, but only two are provided in the first call. In that case, `n` receives the default value `6.022e23` from the header. When a third argument is explicitly provided, the default is ignored.

**Guidelines for defaults.** When a value might reasonably vary between calls, it is a good candidate for a default parameter. Values that are truly constant (like Boltzmann's constant `k`) are best bound inside the function body with `const`.

**Default values and `undefined`.** A default parameter is used only when the argument is `undefined` -- that is, when it is not provided at all. Passing `null` does *not* trigger the default:

```javascript
function greet(name = "World") {
  return `Hello, ${name}!`;
}

greet();          // "Hello, World!"   -- default used
greet("Alice");   // "Hello, Alice!"   -- default ignored
greet(undefined); // "Hello, World!"   -- default used
greet(null);      // "Hello, null!"    -- default NOT used
```

### Locally Defined Functions

Function definitions can appear inside other function bodies. A **locally defined function** (also called a nested function) is only accessible within the enclosing function:

```javascript
function hypotenuse(a, b) {
  function square(x) {
    return x * x;
  }
  return Math.sqrt(square(a) + square(b));
}

hypotenuse(3, 4);  // 5
// square(3);       // ReferenceError: square is not defined
```

The inner `square` is bound in the local frame of `hypotenuse`, not in the global frame. It is invisible outside `hypotenuse` but can be used freely within its body.

Local functions also have access to the parameters of their enclosing function through lexical scope. This lets us build helper functions that "know about" the enclosing arguments without passing them explicitly:

```javascript
function areaBetweenCircles(outerR, innerR) {
  function circleArea(r) {
    return Math.PI * r * r;
  }
  return circleArea(outerR) - circleArea(innerR);
}

areaBetweenCircles(5, 3);  // ~50.265
```

The local function `circleArea` is defined once but called twice. This avoids duplicating the area formula and keeps the helper close to where it is used.

### Functions as Abstractions

The design principles above -- single responsibility, DRY, generality -- all reinforce the idea that a well-designed function is an **abstraction barrier**. Callers of a function depend only on *what* it does (its domain, range, and intent), not on *how* it is implemented.

Consider the `pressure` function. A caller needs to know only three things:

- **Domain:** it accepts a volume `v`, a temperature `t`, and (optionally) a particle count `n`.
- **Range:** it returns a number representing pressure in pascals.
- **Intent:** it computes pressure via the ideal gas law.

The caller does not need to know that the implementation uses Boltzmann's constant or that the formula is `n * k * t / v`. If the implementation changes (say, switching to a van der Waals correction), every caller continues to work as long as the domain, range, and intent remain the same.

This separation of "what" from "how" is the defining feature of a function as an abstraction. It allows programs to be developed, understood, and modified in pieces -- each function can be reasoned about independently.

### Putting It All Together

Here is a complete example that demonstrates all of the concepts in this section: single responsibility, JSDoc documentation, default parameters, and the abstraction barrier.

```javascript
/**
 * Raise a base number to a given exponent.
 *
 * @param {number} base     - The base value
 * @param {number} [exp=2]  - The exponent (default: 2, for squaring)
 * @returns {number} base raised to the power exp
 */
function pow(base, exp = 2) {
  return base ** exp;
}

/**
 * Compute the length of the hypotenuse of a right triangle,
 * given the lengths of the two other sides.
 *
 * @param {number} a - Length of the first side
 * @param {number} b - Length of the second side
 * @returns {number} Length of the hypotenuse
 */
function hypotenuse(a, b) {
  return Math.sqrt(pow(a) + pow(b));
}

hypotenuse(3, 4);   // 5
hypotenuse(5, 12);  // 13
```

Notice how `hypotenuse` depends only on the *interface* of `pow` -- it needs a function that squares a number. It does not know or care whether `pow` uses `**`, `Math.pow`, or repeated multiplication. This is the abstraction barrier at work.

Also notice that `pow` is defined generally (any exponent) but has a sensible default (2), making `pow(5)` a convenient shorthand for squaring while still supporting `pow(2, 10)` for other exponents.

## Python vs JavaScript Notes

| Topic | Python | JavaScript |
|---|---|---|
| **Documentation strings** | Triple-quoted docstrings inside the function body: `"""..."""` | JSDoc comments above the function: `/** ... */` with `@param` and `@returns` tags |
| **Viewing documentation** | `help(pressure)` in the REPL | Hover in editor, or use TypeScript/JS language service; no built-in `help()` |
| **Comments** | `# single-line comments` | `// single-line comments`; `/* block comments */` |
| **Default parameters** | `def f(x, n=6.022e23):` | `function f(x, n = 6.022e23) { ... }` |
| **Default trigger** | Argument omitted; default used for any missing trailing argument | Argument is `undefined` (omitted or explicitly `undefined`); `null` does NOT trigger default |
| **Mutable default pitfall** | `def f(x=[])` shares one list across calls | `function f(x = [])` creates a fresh array each call (no shared-mutable pitfall) |
| **Naming convention** | `snake_case` for functions and variables | `camelCase` for functions and variables |
| **Exponentiation** | `x ** 2` or `pow(x, 2)` (built-in) | `x ** 2` (ES2016+) or `Math.pow(x, 2)` |
| **String interpolation** | f-strings: `f"Hello, {name}!"` | Template literals: `` `Hello, ${name}!` `` |
