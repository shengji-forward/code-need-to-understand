## Key Concepts

- **Statements vs. expressions** -- statements are executed for their side effects and produce no value, while expressions are evaluated and yield a value.
- **Compound statements** use `{ }` blocks to group suites of statements under controlling headers like `if` and `while`.
- **Conditional statements** (`if / else if / else`) direct program flow based on boolean contexts, choosing which suite to execute.
- **Iteration** with `while` repeats a block of statements as long as a condition remains true, enabling repetitive computation.
- **Testing** with `console.assert()` verifies that functions behave as expected, forming the foundation of reliable program design.
- **Boolean context and truthiness** -- JavaScript evaluates conditions using a broader set of falsy and truthy values than Python, with important differences for empty collections.

## Content

### Statements

So far we have primarily considered how to evaluate expressions. However, we have already seen several kinds of **statements**: variable declarations (`let`, `const`), function declarations (`function`), `return` statements, and expression statements. These lines of code are not themselves expressions, although they all *contain* expressions as components.

Rather than being evaluated, statements are **executed**. Each statement describes some change to the interpreter state, and executing the statement applies that change. As we have seen for `return` and assignment statements, executing statements can involve evaluating subexpressions contained within them.

Expressions can also be executed as statements, in which case they are evaluated but their value is discarded. Executing a pure function call as a statement has no useful effect, but executing a non-pure function can cause effects as a consequence:

```javascript
function square(x) {
  x * x;          // Watch out! This expression's value is discarded.
}
square(4);        // Returns undefined -- the multiplication result is lost.
```

This example is valid JavaScript, but probably not what was intended. The body of the function consists of an expression statement. The expression `x * x` is evaluated, but the result is discarded. If you want to do something with the result, you must say so explicitly -- store it in a variable or return it:

```javascript
function square(x) {
  return x * x;   // Now the result is returned to the caller.
}
square(4);        // 16
```

Sometimes it does make sense to have a function whose body is an expression statement, when a non-pure function like `console.log` is called:

```javascript
function printSquare(x) {
  console.log(square(x));
}
printSquare(4);   // Prints: 16 (the return value of console.log is undefined)
```

At its highest level, the JavaScript interpreter's job is to execute programs composed of statements. However, much of the interesting work of computation comes from evaluating expressions. Statements govern the relationship among different expressions in a program and what happens to their results.

### Compound Statements

In general, JavaScript code is a sequence of statements. A **simple statement** is a single operation that does not introduce a block. A **compound statement** is composed of other statements (simple and compound). Compound statements typically span multiple lines and start with a header that identifies the type of statement, followed by a block enclosed in `{ }` (braces). Together, a header and its block is called a **clause**. A compound statement consists of one or more clauses:

```
<header> {
  <statement>
  <statement>
  ...
}
```

We can understand the statements we have already introduced in these terms:

- Expression statements, `return` statements, and variable declarations are simple statements.
- A `function` declaration is a compound statement. The block that follows the `function` header defines the function body.
- `if / else if / else` and `while` are compound statements whose headers control whether (and how many times) their blocks execute.

Specialized evaluation rules for each kind of header dictate when and if the statements in its block are executed. We say that the header **controls** its block. For example, in the case of `function` declarations, the body is not evaluated immediately, but instead stored for later use when the function is eventually called.

We can also understand multi-line programs now:

- To execute a sequence of statements, execute the first statement. If that statement does not redirect control, then proceed to execute the rest of the sequence of statements, if any remain.

This definition exposes the essential structure of a recursively defined *sequence*: a sequence can be decomposed into its first element and the rest of its elements. The "rest" of a sequence of statements is itself a sequence of statements. Thus, we can recursively apply this execution rule. This view of sequences as recursive data structures will appear again in later chapters.

The important consequence of this rule is that statements are executed in order, but later statements may never be reached, because of redirected control.

### Defining Functions II: Local Assignment

Originally, we stated that the body of a user-defined function consisted only of a `return` statement with a single return expression. In fact, functions can define a sequence of operations that extends beyond a single expression.

Whenever a user-defined function is called, the sequence of statements in its body is executed in a **local environment** -- an environment starting with a local frame created by that function call. A `return` statement redirects control: the process of function application terminates whenever the first `return` statement is executed, and the value of the return expression is the returned value of the function.

Variable declarations (`let` or `const`) can appear within a function body. For instance, this function returns the absolute difference between two quantities as a percentage of the first, using a two-step calculation:

```javascript
function percentDifference(x, y) {
  const difference = Math.abs(x - y);
  return 100 * difference / x;
}

percentDifference(40, 50);   // 25
```

The effect of a `const` (or `let`) declaration is to bind a name to a value in the *first* frame of the current environment. As a consequence, variable declarations within a function body cannot affect the global frame. The fact that `const` and `let` declarations within a function body create bindings in the *local* frame -- not the global frame -- is critical to creating **modular** programs. Pure functions interact only via the values they take and return, and their local names do not interfere with the rest of the program. (Functions *can* access and mutate outer bindings via closures or object references; this power should be used judiciously.)

Of course, `percentDifference` could be written as a single expression:

```javascript
function percentDifference(x, y) {
  return 100 * Math.abs(x - y) / x;
}

percentDifference(40, 50);   // 25
```

So far, local assignment has not increased the expressive power of our function definitions. It will do so when combined with other control statements. In addition, local assignment plays a critical role in clarifying the meaning of complex expressions by assigning names to intermediate quantities.

### Conditional Statements

JavaScript has a built-in `Math.abs` function for computing absolute values:

```javascript
Math.abs(-2);   // 2
```

We would like to be able to implement such a function ourselves, but we have no obvious way to define a function that involves a comparison and a choice. We would like to express that if `x` is positive, `abs(x)` returns `x`; if `x` is 0, `abs(x)` returns 0; otherwise, `abs(x)` returns `-x`. In JavaScript, we can express this choice with a **conditional statement**:

```javascript
function absoluteValue(x) {
  if (x > 0) {
    return x;
  } else if (x === 0) {
    return 0;
  } else {
    return -x;
  }
}

absoluteValue(-2);   // 2
```

This implementation raises several important issues.

**Conditional statements.** A conditional statement in JavaScript consists of a series of headers and blocks: a required `if` clause, an optional sequence of `else if` clauses, and finally an optional `else` clause:

```javascript
if (<expression>) {
  <suite>
} else if (<expression>) {
  <suite>
} else {
  <suite>
}
```

When executing a conditional statement, each clause is considered in order:

1. Evaluate the header's expression.
2. If it is a truthy value, execute the block. Then, skip over all subsequent clauses in the conditional statement.

If the `else` clause is reached (which only happens if all `if` and `else if` expressions evaluate to falsy values), its block is executed.

**Boolean contexts.** The expressions inside the header statements of conditional blocks are said to be in **boolean contexts**: their truth values matter to control flow, but otherwise their values are not assigned or returned. JavaScript includes several falsy values, including `false`, `0`, `""`, `null`, `undefined`, and `NaN`. All other values are truthy. See the "Boolean Context and Truthiness" section below for full details.

**Boolean values.** JavaScript has two boolean values, called `true` and `false`. Boolean values represent truth values in logical expressions. The built-in comparison operators `>`, `<`, `>=`, `<=`, `===`, `!==` return these values:

```javascript
4 < 2;       // false
5 >= 5;      // true
0 === -0;    // true
```

The third example reads "0 equals -0." Notice that JavaScript distinguishes assignment (`=`) from equality comparison (`===`), a convention shared across many programming languages. Always use `===` (strict equality) rather than `==` (loose equality with type coercion) to avoid surprising behavior.

**Boolean operators.** Three basic logical operators are built into JavaScript:

```javascript
true && false;    // false
true || false;    // true
!false;           // true
```

Logical expressions have corresponding evaluation procedures. These procedures exploit the fact that the truth value of a logical expression can sometimes be determined without evaluating all of its subexpressions, a feature called **short-circuiting**.

To evaluate the expression `<left> && <right>`:

1. Evaluate `<left>`.
2. If the result is a falsy value, the expression evaluates to that falsy value.
3. Otherwise, the expression evaluates to the value of `<right>`.

To evaluate the expression `<left> || <right>`:

1. Evaluate `<left>`.
2. If the result is a truthy value, the expression evaluates to that truthy value.
3. Otherwise, the expression evaluates to the value of `<right>`.

To evaluate the expression `!<expr>`:

1. Evaluate `<expr>`. The result is `true` if the value is falsy, and `false` otherwise.

These values, rules, and operators provide us with a way to combine the results of comparisons. Functions that perform comparisons and return boolean values typically have names beginning with `is` (e.g., `Number.isFinite`, `Number.isInteger`, `Array.isArray`).

### Iteration

In addition to selecting which statements to execute, control statements are used to express repetition. If each line of code we wrote were only executed once, programming would be a very unproductive exercise. Only through repeated execution of statements do we unlock the full potential of computers. We have already seen one form of repetition: a function can be applied many times, although it is only defined once. **Iterative control structures** are another mechanism for executing the same statements many times.

Consider the sequence of Fibonacci numbers, in which each number is the sum of the preceding two:

```
0, 1, 1, 2, 3, 5, 8, 13, 21, ...
```

Each value is constructed by repeatedly applying the sum-previous-two rule. The first and second are fixed to 0 and 1. For instance, the eighth Fibonacci number is 13.

We can use a `while` statement to enumerate n Fibonacci numbers. We need to track how many values we have created (`k`), along with the kth value (`curr`) and its predecessor (`pred`):

```javascript
function fib(n) {
  let pred = 0;       // Fibonacci number 1
  let curr = 1;       // Fibonacci number 2
  let k = 2;          // Which Fib number is curr?
  while (k < n) {
    let next = pred + curr;
    pred = curr;
    curr = next;
    k = k + 1;
  }
  return curr;
}

fib(8);    // 13
```

To execute a `while` clause:

1. Evaluate the header's expression.
2. If it is a truthy value, execute the block, then return to step 1.

In step 2, the *entire* block of the `while` clause is executed before the header expression is evaluated again.

In order to prevent the block of a `while` clause from being executed indefinitely, the block should always change some binding in each pass. A `while` statement that does not terminate is called an **infinite loop**. Press Ctrl-C to force Node.js to stop looping.

We can simplify the Fibonacci function using **destructuring assignment** to swap two variables in a single line:

```javascript
function fib(n) {
  let pred = 0;
  let curr = 1;
  let k = 2;
  while (k < n) {
    [pred, curr] = [curr, pred + curr];
    k = k + 1;
  }
  return curr;
}

fib(8);    // 13
```

The expression `[pred, curr] = [curr, pred + curr]` simultaneously assigns the old `curr` to `pred` and the sum `pred + curr` to `curr`. This is the JavaScript equivalent of Python's `pred, curr = curr, pred + curr`.

### Testing

**Testing** a function is the act of verifying that the function's behavior matches expectations. Our language of functions is now sufficiently complex that we need to start testing our implementations.

A **test** is a mechanism for systematically performing this verification. Tests typically take the form of another function that contains one or more sample calls to the function being tested. The returned value is then verified against an expected result. Unlike most functions, which are meant to be general, tests involve selecting and validating calls with specific argument values. Tests also serve as documentation: they demonstrate how to call a function and what argument values are appropriate.

**Assertions.** Programmers use assert statements to verify expectations, such as the output of a function being tested. In JavaScript, `console.assert()` serves this role. It takes an expression in a boolean context, followed by a message that will be displayed if the expression evaluates to a falsy value:

```javascript
console.assert(fib(8) === 13, 'The 8th Fibonacci number should be 13');
```

When the expression being asserted evaluates to a truthy value, executing `console.assert` has no effect (it prints nothing). When it is a falsy value, `console.assert` prints the error message. Note: unlike Python's `assert` statement, `console.assert` does **not** throw an error or halt execution by default. It merely logs the failure.

A test function for `fib` should test several arguments, including extreme values of `n`:

```javascript
function fibTest() {
  console.assert(fib(2) === 1, 'The 2nd Fibonacci number should be 1');
  console.assert(fib(3) === 1, 'The 3rd Fibonacci number should be 1');
  console.assert(fib(8) === 13, 'The 8th Fibonacci number should be 13');
  console.assert(fib(50) === 7778742049, 'Error at the 50th Fibonacci number');
}

fibTest();
```

**A simple test helper.** Since `console.assert` does not halt on failure, it is useful to define a helper that provides stricter behavior:

```javascript
function assertEqual(actual, expected, message) {
  if (actual !== expected) {
    throw new Error(`${message}: expected ${expected}, got ${actual}`);
  }
}

assertEqual(fib(8), 13, 'fib(8)');
assertEqual(fib(2), 1, 'fib(2)');
```

This helper throws an exception on failure, immediately stopping execution -- mirroring the behavior of Python's `assert` statement.

**Doc-comment examples.** In Python, doctests embed example calls directly in docstrings. JavaScript has no equivalent built-in test runner, but you can achieve a similar effect by including example calls in JSDoc comments and verifying them manually or with a test helper:

```javascript
/**
 * Return the sum of integers from 1 to n.
 *
 * @param {number} n - A positive integer
 * @returns {number} The sum 1 + 2 + ... + n
 *
 * @example
 * sumNaturals(5);  // 15
 * sumNaturals(1);  // 1
 */
function sumNaturals(n) {
  let total = 0;
  let k = 1;
  while (k <= n) {
    total = total + k;
    k = k + 1;
  }
  return total;
}

// Verify the examples:
assertEqual(sumNaturals(5), 15, 'sumNaturals(5)');
assertEqual(sumNaturals(1), 1, 'sumNaturals(1)');
```

The JSDoc `@example` tag serves as both documentation and a specification for tests, mirroring the role of Python doctests.

**Testing in files.** When writing JavaScript in files rather than in an interactive REPL, tests are typically placed in the same file or a neighboring file with a `.test.js` suffix. With Node.js, you can run test files directly:

```
node fib.test.js
```

The key to effective testing is to write (and run) tests immediately after implementing new functions. It is even good practice to write some tests *before* you implement, so that you have example inputs and expected outputs in mind. A test that applies a single function is called a **unit test**. Exhaustive unit testing is a hallmark of good program design.

### Boolean Context and Truthiness

When JavaScript evaluates a condition (in `if`, `while`, `&&`, `||`, or `!`), it must decide whether a value is "true-like" or "false-like." This decision happens in a **boolean context**. Unlike Python, where many types participate in truthiness, JavaScript's rules are specific and important to understand precisely.

**Falsy values.** The common falsy values in Node.js -- values that evaluate to `false` in a boolean context -- are:

```javascript
if (false)        { /* not reached */ }
if (0)            { /* not reached */ }
if (-0)           { /* not reached */ }
if (0n)           { /* not reached */ }  // BigInt zero
if ("")           { /* not reached */ }
if (null)         { /* not reached */ }
if (undefined)    { /* not reached */ }
if (NaN)          { /* not reached */ }
```

**Truthy values.** All other ordinary Node.js values are truthy. This leads to a crucial difference from Python:

```javascript
// These are TRUTHY in JavaScript (but falsy in Python!):
if ([])            { /* reached! */ }   // empty array is truthy
if ({})            { /* reached! */ }   // empty object is truthy
if ("false")       { /* reached! */ }   // non-empty string is truthy
if (new Boolean(false)) { /* reached! */ }  // Boolean object wrapper is truthy
```

This is one of the most important Python vs. JavaScript differences. In Python, empty collections (`[]`, `{}`, `""`) are falsy. In JavaScript, empty arrays and empty objects are truthy. Only `null`, `undefined`, `false`, `0`, `0n`, `NaN`, and `""` are falsy.

**Practical implication.** To test whether an array is non-empty in JavaScript, you must check `.length` explicitly:

```javascript
const items = [];

// WRONG in JavaScript -- [] is truthy!
if (items) {
  console.log('This runs even for empty arrays!');
}

// CORRECT -- check length explicitly:
if (items.length > 0) {
  console.log('Non-empty');
}
```

**Short-circuiting in practice.** Because `&&` and `||` use truthiness (not strict booleans), they are commonly used for providing defaults:

```javascript
const name = "";           // falsy
const displayName = name || "Anonymous";   // "Anonymous"

const count = 0;           // falsy
const displayCount = count || "none";      // "none" -- careful! 0 is a valid count.
```

The second example demonstrates a common pitfall: using `||` for defaults treats `0` as missing. For this reason, the nullish coalescing operator `??` (ES2020) is preferred when only `null` and `undefined` should trigger the default:

```javascript
const count = 0;
const displayCount = count ?? "none";      // 0 -- only null/undefined trigger the default
```

## Python vs JavaScript Notes

| Topic | Python | JavaScript |
|---|---|---|
| **Conditional statement** | `if x > 0:` with indented suites; `elif` for additional branches | `if (x > 0) { }` with braces; `else if` for additional branches |
| **Equality comparison** | `==` for equality (value-based) | `===` for strict equality (no type coercion); avoid `==` |
| **Boolean operators** | `and`, `or`, `not` (keywords) | `&&`, `||`, `!` (punctuation operators) |
| **Boolean values** | `True` and `False` (capitalized) | `true` and `false` (lowercase) |
| **Falsy values** | `False`, `0`, `0.0`, `""`, `None`, `[]`, `{}`, `()`, `set()` | `false`, `0`, `-0`, `0n`, `""`, `null`, `undefined`, `NaN` |
| **Empty collections truthiness** | `[]`, `{}`, `""` are **falsy** | `[]`, `{}` are **truthy** (only `""` is falsy) |
| **Checking empty array** | `if items:` works (falsy when empty) | `if (items.length > 0)` required |
| **While loop** | `while k < n:` with indented body | `while (k < n) { }` with braces |
| **Assertion** | `assert expr, "message"` -- raises `AssertionError`, halts execution | `console.assert(expr, "message")` -- logs only, does not halt; use a custom helper or `throw` for strict behavior |
| **Destructuring swap** | `pred, curr = curr, pred + curr` (tuple packing/unpacking) | `[pred, curr] = [curr, pred + curr]` (array destructuring assignment) |
| **No `nonlocal` needed** | `nonlocal x` required to rebind enclosing scope variables | `let` declarations in enclosing scope are accessible and mutable from nested functions without special keyword |
| **Truthiness of `NaN`** | No `NaN` concept for integers; `float('nan')` is truthy | `NaN` is falsy; `NaN !== NaN` is `true` (use `Number.isNaN()` to test) |
| **Short-circuit return value** | `and`/`or` return the last evaluated operand | `&&`/`||` return the last evaluated operand (same behavior) |
| **Nullish coalescing** | `x if x is not None else default` or `x or default` (with caveats) | `x ?? default` -- only triggers on `null`/`undefined`, not `0` or `""` |
