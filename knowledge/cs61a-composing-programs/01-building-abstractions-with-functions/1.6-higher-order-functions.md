## Key Concepts

- **Higher-order functions** accept functions as arguments or return functions as values, enabling powerful abstraction over common computation patterns.
- **Functions as arguments** let us generalize recurring patterns (like summation) into a single function that takes the varying part as a parameter.
- **Functions as return values** enable composition, currying, and factory patterns where one function creates specialized functions.
- **Lexical scope** means that inner functions have access to names in the environment where they were defined, not where they are called.
- **Iterative improvement** is a general method expressed naturally by higher-order functions: pass in an update rule and a convergence test.
- **First-class functions** can be bound to names, passed as arguments, returned from functions, and stored in data structures -- giving them the same status as any other value.

### 1.6.1 Functions as Arguments

Consider three functions that each compute a different kind of summation. The first sums natural numbers:

```javascript
function sumNaturals(n) {
  let total = 0;
  let k = 1;
  while (k <= n) {
    total = total + k;
    k = k + 1;
  }
  return total;
}

sumNaturals(100);  // 5050
```

The second sums cubes:

```javascript
function sumCubes(n) {
  let total = 0;
  let k = 1;
  while (k <= n) {
    total = total + k * k * k;
    k = k + 1;
  }
  return total;
}

sumCubes(100);  // 25502500
```

The third sums a series that converges to pi:

```javascript
function piSum(n) {
  let total = 0;
  let k = 1;
  while (k <= n) {
    total = total + 8 / ((4 * k - 3) * (4 * k - 1));
    k = k + 1;
  }
  return total;
}

piSum(100);  // 3.1365926848388144
```

These three functions share a common underlying pattern. They differ only in the function applied to `k` at each step. We can abstract this shared pattern into a single **higher-order function** that takes the varying part -- the term function -- as an argument:

```javascript
function summation(n, term) {
  let total = 0;
  let k = 1;
  while (k <= n) {
    total = total + term(k);
    k = k + 1;
  }
  return total;
}

function cube(x) {
  return x * x * x;
}

function identity(x) {
  return x;
}

function piTerm(x) {
  return 8 / ((4 * x - 3) * (4 * x - 1));
}
```

Now we can express each sum concisely by passing a different term function:

```javascript
function sumCubes(n) {
  return summation(n, cube);
}

function sumNaturals(n) {
  return summation(n, identity);
}

function piSum(n) {
  return summation(n, piTerm);
}

sumCubes(3);            // 36  (1 + 8 + 27)
sumNaturals(10);        // 55
piSum(1e6);             // 3.141592153589902
```

The key insight: `summation` expresses the *concept* of summation itself. The specific term to add is supplied as a function argument, not hard-coded into the loop. This is the power of functions as arguments -- they let us name and reuse general computational patterns.

### 1.6.2 Functions as General Methods

Higher-order functions also let us express **general methods** of computation that are independent of the particular functions they call. Consider an iterative improvement algorithm: start with a guess, repeatedly apply an update function, and stop when a test says the guess is close enough.

```javascript
function approxEq(x, y, tolerance = 1e-15) {
  return Math.abs(x - y) < tolerance;
}

function improve(update, close, guess = 1) {
  while (!close(guess)) {
    guess = update(guess);
  }
  return guess;
}
```

The `improve` function knows nothing about *what* problem is being solved. Those details are left to `update` and `close`, which are passed in as function arguments.

We can use `improve` to compute the **golden ratio** (approximately 1.618). The golden ratio has two properties: it equals 1 plus its own reciprocal, and it is one less than its square.

```javascript
function goldenUpdate(guess) {
  return 1 / guess + 1;
}

function squareCloseToSuccessor(guess) {
  return approxEq(guess * guess, guess + 1);
}

improve(goldenUpdate, squareCloseToSuccessor);  // 1.6180339887498951
```

We can verify this against the closed-form expression:

```javascript
const phi = 0.5 + Math.sqrt(5) / 2;

function improveTest() {
  const approxPhi = improve(goldenUpdate, squareCloseToSuccessor);
  if (!approxEq(phi, approxPhi)) {
    throw new Error('phi differs from its approximation');
  }
}

improveTest();  // No error means success
```

Notice that `improve` expresses a general iterative method. It works for the golden ratio here, but the same pattern works for any problem that can be phrased as "refine a guess until it satisfies a condition."

We could compute a square root by writing a two-argument update function that takes both the guess and the number whose root we seek:

```javascript
function sqrtUpdate(guess, a) {
  return average(guess, a / guess);
}
```

But this forces every helper to carry the extra argument `a`. As we will see in the next section, nested function definitions offer a cleaner approach.

### 1.6.3 Definitions and Names in Local Frames

Passing functions as arguments enhances expressive power, but it has a downside: the global frame becomes cluttered with small helper functions like `cube`, `identity`, and `goldenUpdate`, which must all have unique names. Nested function definitions solve this problem.

Consider computing a square root. Repeatedly averaging a guess `x` with `a / x` converges to the square root of `a`:

```javascript
function average(x, y) {
  return (x + y) / 2;
}

function approxEq(x, y, tolerance = 1e-15) {
  return Math.abs(x - y) < tolerance;
}

function improve(update, close, guess = 1) {
  while (!close(guess)) {
    guess = update(guess);
  }
  return guess;
}

function sqrt(a) {
  function sqrtUpdate(x) {
    return average(x, a / x);
  }
  function sqrtClose(x) {
    return approxEq(x * x, a);
  }
  return improve(sqrtUpdate, sqrtClose);
}

sqrt(256);  // 16.0
```

The functions `sqrtUpdate` and `sqrtClose` are defined inside `sqrt`. They are **local** to `sqrt` and invisible outside it. More importantly, they reference the parameter `a` from their enclosing function. This is **lexical scope**: inner functions have access to names in the environment where they are defined (not where they are called).

Our environment model requires two extensions to support lexical scope:

1. Each user-defined function has a **parent environment**: the environment in which it was defined.
2. When a user-defined function is called, its local frame **extends** its parent environment.

Before `sqrt`, all functions were defined in the global environment, so they all shared the same parent. But `sqrtUpdate` and `sqrtClose` are defined inside a call to `sqrt`, so their parent environment is the local frame of that call -- which is where `a` is bound.

```
Global Frame
  average   -> func average(x, y)
  approxEq  -> func approxEq(x, y, tolerance)
  improve   -> func improve(update, close, guess)
  sqrt      -> func sqrt(a)

sqrt(256) call creates:
  sqrt() Frame  [parent: Global]
    a          -> 256
    sqrtUpdate -> func sqrtUpdate(x)  [parent: sqrt() Frame]
    sqrtClose  -> func sqrtClose(x)   [parent: sqrt() Frame]
```

When `sqrtUpdate` is called, its local frame extends the `sqrt()` frame, so it can look up `a` through the parent chain. This is how the inner functions access the binding of `a` in their parent environment -- the value is not copied or "remembered" in isolation, but found through the environment chain at call time.

### 1.6.4 Functions as Return Values

Functions can also be **returned** from other functions. A powerful example is function composition -- creating a new function that applies two functions in sequence:

```javascript
function compose1(f, g) {
  function h(x) {
    return f(g(x));
  }
  return h;
}

function square(x) {
  return x * x;
}

function successor(x) {
  return x + 1;
}

const squareSuccessor = compose1(square, successor);
squareSuccessor(12);  // 169  (square(successor(12)) = square(13) = 169)
```

The returned function `h` captures `f` and `g` from its enclosing environment. When `h` is later called with argument `12`, it looks up `g` (finding `successor`) and applies it first, then looks up `f` (finding `square`) and applies it to the result.

Another classic pattern is a **function factory** -- a function that creates specialized functions:

```javascript
function makeAdder(n) {
  return (x) => x + n;
}

const addFive = makeAdder(5);
const addTen = makeAdder(10);

addFive(3);   // 8
addTen(3);    // 13
```

Each call to `makeAdder` creates a new function that closes over the `n` parameter of that specific call. The returned arrow function carries a reference to its parent environment, where `n` is bound.

No modification to our environment model is needed to explain returning functions. The returned function carries its parent environment with it, and when it is eventually called, its local frame extends that parent.

### 1.6.5 Newton's Method

Newton's method is a classic iterative algorithm for finding the **zeros** of a function -- the input values that produce an output of zero. It is widely used in scientific computing, machine learning, and optimization.

The idea: given a function `f` and its derivative `df`, follow the tangent line at the current guess to find a better guess. The update rule is:

```
next_guess = current_guess - f(current_guess) / df(current_guess)
```

Expressed as a higher-order function:

```javascript
function newtonUpdate(f, df) {
  return function update(x) {
    return x - f(x) / df(x);
  };
}

function findZero(f, df) {
  function nearZero(x) {
    return approxEq(f(x), 0);
  }
  return improve(newtonUpdate(f, df), nearZero);
}
```

**Computing square roots.** The square root of `a` is the value `x` such that `x^2 - a = 0`. The derivative of `x^2 - a` is `2x`. Plugging these into Newton's method:

```javascript
function squareRootNewton(a) {
  function f(x) {
    return x * x - a;
  }
  function df(x) {
    return 2 * x;
  }
  return findZero(f, df);
}

squareRootNewton(64);   // 8.0
squareRootNewton(25);   // 5.0
```

**Computing nth roots.** We can generalize to roots of any degree. The nth root of `a` is `x` such that `x^n - a = 0`, with derivative `n * x^(n-1)`.

```javascript
function power(x, n) {
  let product = 1;
  let k = 0;
  while (k < n) {
    product = product * x;
    k = k + 1;
  }
  return product;
}

function nthRootOfA(n, a) {
  function f(x) {
    return power(x, n) - a;
  }
  function df(x) {
    return n * power(x, n - 1);
  }
  return findZero(f, df);
}

nthRootOfA(2, 64);   // 8.0   (square root)
nthRootOfA(3, 64);   // 4.0   (cube root)
nthRootOfA(6, 64);   // 2.0   (sixth root)
```

Newton's method is powerful but not infallible. The initial guess must be close enough to the actual zero, and certain functions can cause the method to diverge. Despite this limitation, variants of Newton's method are used extensively in modern computing for logarithms, large integer division, and optimization.

### 1.6.6 Currying

**Currying** transforms a function that takes multiple arguments into a chain of functions that each take a single argument. Given `f(x, y)`, currying produces `g(x)(y)` which is equivalent.

```javascript
function curriedPow(x) {
  return (y) => Math.pow(x, y);
}

curriedPow(2)(3);  // 8
```

Currying is useful when we need a single-argument function for use with mapping patterns:

```javascript
function mapToRange(start, end, f) {
  while (start < end) {
    console.log(f(start));
    start = start + 1;
  }
}

// Print the first 10 powers of 2:
mapToRange(0, 10, curriedPow(2));
// 1
// 2
// 4
// ...
// 512
```

Instead of manually currying each function, we can define a general `curry2` function that transforms any two-argument function:

```javascript
function curry2(f) {
  return function g(x) {
    return function h(y) {
      return f(x, y);
    };
  };
}

function uncurry2(g) {
  return function f(x, y) {
    return g(x)(y);
  };
}

const powCurried = curry2(Math.pow);

powCurried(2)(5);              // 32
mapToRange(0, 10, powCurried(2));
// 1
// 2
// 4
// ...
// 512

uncurry2(powCurried)(2, 5);   // 32
```

`curry2(f)(x)(y)` is equivalent to `f(x, y)`. The `uncurry2` function reverses the transformation: `uncurry2(curry2(f))` is equivalent to `f`.

### 1.6.7 Lambda Expressions

In Python, `lambda` creates anonymous functions. In JavaScript, the equivalent is the **arrow function**:

```javascript
// Python: lambda x: f(g(x))
// JavaScript:
(x) => f(g(x))
```

Arrow functions are expressions that evaluate to function values. They are useful when a simple function is needed as an argument or return value and does not warrant a full `function` declaration.

Rewriting `compose1` with arrow functions:

```javascript
function compose1(f, g) {
  return (x) => f(g(x));
}

const squareSuccessor = compose1(
  (x) => x * x,
  (y) => y + 1
);

squareSuccessor(12);  // 169
```

Arrow functions can also be used directly without binding them to a name:

```javascript
const squareFn = (x) => x * x;
squareFn(12);  // 144
```

The most compact form of `compose1` uses arrow functions throughout:

```javascript
const compose1Arrow = (f, g) => (x) => f(g(x));
```

While concise, heavily nested arrow functions can be hard to read. As a guideline, prefer explicit `function` declarations for named functions and use arrow functions for small, single-expression functions passed as arguments or returned from other functions. Write code for the humans who will read it.

The term "lambda" is a historical accident from early mathematical notation. Alonzo Church originally wrote the square function as "ŷ . y x y" with a hat over the parameter. Frustrated typographers moved the hat to the left and changed it to a capital lambda, eventually arriving at the lowercase "λ" seen in mathematics and the `lambda` keyword in Lisp. JavaScript skips this history entirely and uses `=>` as its anonymous function syntax.

### 1.6.8 Abstractions and First-Class Functions

Higher-order functions let us represent general computational methods as explicit, manipulable elements in our programming language. This is a significant increase in expressive power.

As programmers, we should be alert to opportunities to identify underlying abstractions, build on them, and generalize them. This does not mean always writing at the most abstract level possible -- expert programmers choose the level of abstraction appropriate to their task. But it is important to *think* in terms of these abstractions so we can apply them in new contexts.

A programming element has **first-class status** when it enjoys these rights and privileges:

1. It may be bound to names.
2. It may be passed as arguments to functions.
3. It may be returned as the results of functions.
4. It may be included in data structures.

JavaScript awards functions full first-class status. You can store functions in arrays and objects, pass them as arguments, return them from other functions, and assign them to variables. This is enormously powerful:

```javascript
// Storing functions in a data structure
const operations = {
  add: (a, b) => a + b,
  sub: (a, b) => a - b,
  mul: (a, b) => a * b,
};

// Passing a function as an argument
[1, 2, 3, 4].map((x) => x * x);        // [1, 4, 9, 16]
[1, 2, 3, 4].filter((x) => x > 2);      // [3, 4]

// Returning a function from a function
function makeMultiplier(factor) {
  return (x) => x * factor;
}

const triple = makeMultiplier(3);
triple(5);  // 15
```

The combination of first-class functions and higher-order functions is the foundation for many powerful programming patterns including callbacks, event handling, middleware, and functional composition.

### 1.6.9 Function Decorators

Python provides special `@decorator` syntax for applying a higher-order function to a newly defined function. JavaScript has no equivalent syntax, but the same pattern is achieved by explicitly wrapping a function with a higher-order function.

A common example is a **trace** decorator that logs function calls:

```javascript
function trace(fn) {
  return function wrapped(x) {
    console.log('->', fn.name, '(', x, ')');
    return fn(x);
  };
}
```

In Python, decorators use `@trace` syntax above a function definition. JavaScript has no special syntax for decorators. Instead, you apply the decorator explicitly by calling it as a higher-order function and reassigning the name:

```javascript
function triple(x) {
  return 3 * x;
}

triple = trace(triple);

triple(12);  // Logs: "-> triple ( 12 )", returns 36
```

The key point is the same: `trace` takes a function and returns a new function with added logging. In Python you write `@trace` above `def`; in JavaScript you write `fn = trace(fn)` after defining `fn`.

Or equivalently, define and decorate in one step:

```javascript
const triple = trace(function triple(x) {
  return 3 * x;
});

triple(12);  // Logs: "-> triple ( 12 )", returns 36
```

The decorator pattern works because functions are first-class values. `trace` takes a function and returns a new function that adds logging behavior around the original call. The original function is preserved inside the closure of `wrapped`, and the name `triple` is rebound to the wrapped version.

**More decorator examples.** The same pattern can enforce access control, cache results (memoization), or transform inputs and outputs:

```javascript
// A decorator that caches results (memoization)
function memoize(fn) {
  const cache = {};
  return function cached(x) {
    if (x in cache) {
      return cache[x];
    }
    cache[x] = fn(x);
    return cache[x];
  };
}

function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}

// Note: to truly memoize fib recursively, fib must reference
// the memoized version. One way is to reassign:
const memoFib = memoize(fib);  // Only memoizes top-level calls

// A better approach for recursive functions:
// Reassign the original name after decoration
```

The decorator pattern is a direct application of higher-order functions: it takes a function, wraps it with additional behavior, and returns the enhanced version. In JavaScript, this is always done through explicit function application, not through special syntax.

## Python vs JavaScript Notes

| Topic | Python | JavaScript |
|---|---|---|
| **Higher-order functions** | Functions are first-class; can be passed and returned | Same; functions are first-class objects |
| **Lambda / anonymous functions** | `lambda x: x * x` (single expression only) | `(x) => x * x` (arrow function, supports full body with braces) |
| **Decorators** | `@trace` syntax; `@trace` above `def triple(x):` | No special syntax; use `const triple = trace(function triple(x) { ... })` or reassign after definition |
| **Closures** | Inner functions close over enclosing variables; use `nonlocal` keyword to rebind them | Inner functions close over enclosing variables; use `let` for mutable bindings that the inner function modifies |
| **`nonlocal` equivalent** | `nonlocal x` allows inner function to rebind `x` in enclosing scope | No `nonlocal` keyword needed; `let`/`const` in enclosing scope are accessible; reassign `let` variables directly |
| **`map` / `filter`** | Built-in functions: `map(fn, iterable)`, `filter(fn, iterable)` | Array methods: `arr.map(fn)`, `arr.filter(fn)` |
| **Default parameters** | `def f(x, tol=1e-15):` | `function f(x, tol = 1e-15) { ... }` |
| **Nested function definitions** | `def outer():` with indented `def inner():` inside | `function outer() { function inner() { ... } ... }` |
| **Exponentiation** | `pow(x, y)` or `x ** y` | `Math.pow(x, y)` or `x ** y` (ES2016+) |
| **Currying** | Manual or via `curry2` helper | Same; arrow functions make currying concise: `const curry2 = (f) => (x) => (y) => f(x, y)` |
| **Function `name` property** | `fn.__name__` | `fn.name` (e.g., `function triple(x) {}` has `.name === "triple"`) |
| **Printing / logging** | `print(value)` | `console.log(value)` |
| **Assert** | `assert condition, 'message'` raises `AssertionError` | `if (!condition) throw new Error('message')` (no built-in `assert`) |
| **Truthiness in conditions** | `while not close(guess):` | `while (!close(guess)) { ... }` |
